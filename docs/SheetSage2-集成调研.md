# SheetSage2 集成调研

结论先行：**SheetSage2 的调用面很窄，集成的难点不在模型，而在产物的解析和环境的坑。**
模型对外只有 `AutoModel.from_pretrained(...).transcribe(...)` 一个入口，返回 ABC / MIDI /
带时间戳的标注；剩下的工作是把这些产物读成上层能用的结构。

## 1. 模型身份

| 项 | 值 |
|---|---|
| 仓库 | `m-a-p/SheetSage2` |
| 基座 | `m-a-p/MERT-v2-FullSong`（2.5 GB，作为 adapter 的基座，加载时自动合并） |
| 本体重 | `model.safetensors` 约 218 MB |
| 加载方式 | `transformers.AutoModel` + `trust_remote_code=True`（仓库自带 `modeling_*` / `pipeline_*`） |
| 许可 | **CC BY-NC 4.0（非商业）**；基座 MERT 为 CC BY-NC 4.0 |
| 固定版本 | 快照 `398b22834dac7dd05e09b9c4e40a39fc479ec502` |

> 仓库在 2026-09-21 / 09-24 有过两次**只改和弦拼写**的代码更新（权重不变）。因为用了
> `trust_remote_code`，代码是联网拉取的，**结果会随上游代码变化**。要可复现就必须固定
> `revision`，或者把快照落盘后走 `local_files_only`。

## 2. 调用接口

```python
import torch
from transformers import AutoModel

model = AutoModel.from_pretrained("m-a-p/SheetSage2", trust_remote_code=True)
model = model.eval().to("cuda")

result = model.transcribe("song.flac", output_dir="output")
```

`transcribe` 的可用参数（来自仓库 `pipeline_sheetsage2.py` / `infer.py`）：

| 参数 | 默认 | 说明 |
|---|---|---|
| `dtype` | `"bf16"` | `bf16` / `fp32`，通过 autocast 生效，不是模型权重的 dtype |
| `preset` | `"default"` | `default` → overlap 200s / lookahead 100s；`paper` → 100s / 0s |
| `max_seconds` | `None` | 只转前 N 秒 |
| `overlap_seconds` / `lookahead_seconds` | 随 preset | 滑窗重叠与右向上下文 |
| `prompts` | 全任务 | 要解码的字段；`timestamp` 是导出时间标注的必要项 |
| `melody_only` | `False` | 丢和弦，只留人声/器乐旋律 |
| `progress` | `None` | 回调，收到 `{"stage": "encoding"/"decoding"/"window_complete", "window", "windows", ...}` |
| `output_dir` | `None` | 不给就全留在内存 |
| `export_logits` / `export_scores` / `export_embeddings` / `output_hidden_states` | `False` | 额外导出张量 |
| `render_audio` / `render_score` | `False` | 额外渲染试听音频 / 五线谱（另需依赖） |

音频可以是：路径、编码字节、二进制流，或 `(waveform, sampling_rate=...)` 数组。

### 长音频行为

`sliding_window_plan()` 按「窗口 = 模型 `hparams.input_audio_length`，hop = 窗口 − overlap」
切分；从第二个窗口起，会把已确认事件的 token 作为前缀传回去，保证跨窗口的调性/节拍连续。
`lookahead` 那一段只用于给模型右侧上下文，**不采信它的输出**。

## 3. 产物

`output_dir` 下会写出（本次实测全部命中）：

| 类别 | 文件 |
|---|---|
| 乐谱 | `score.abc`（beat < 2 或不含调性时**不生成**，并写 `abc_error`）；头部 `Q:1/4=N` 是模型自带的 BPM，见 §5.1 |
| MIDI | `transcription.mid`（旋律+和弦）、`melody.mid`、`melody_vocal.mid`、`melody_instrumental.mid`、`chords.mid`、`notation/song_melody.mid` |
| 音符 | `melody_full.lab`、`melody_vocal.lab`、`melody_instrumental.lab`（`start, end, pitch[, track]`） |
| 区间标注 | `chord.lab`、`key.lab`、`structure.lab`（`start, end, value`） |
| 节拍 | `beat.lab`（`time, position, num, den`）、`downbeat.lab`、`rhythm_events.lab` |
| 事件 | `events.json`（全量解码事件，含 `values` 各字段）、`events.tsv` |
| 回放 | `playback.json`（轨、音符、小节表） |
| 其它 | `tokens.txt` / `tokens.json`、`result.json` |

`result` 字典里同时给出内存版本：`abc`(str)、`midi`(bytes)、`midis`(dict)、`events`(list)、
`labs`(dict)、`playback`(dict)，以及统计量 `melody_notes / vocal_notes /
instrumental_notes / num_events / abc_measures / abc_error / warnings /
peak_gpu_mib / elapsed_seconds / windows`。

**和弦与调性拼写**会按局部调性做等音修正（`D#:major` → `Eb:major`），音高与时值不受影响。

## 5. 本机实测

（数据由 `scripts/verify.py` 产出，见 `reports/验证报告.md`）

- 硬件：RTX 3080 12 GB，驱动支持 CUDA 12.8；全程 bf16
- 模型加载：约 12 s（快照已在本地缓存后）
- 推理：约 **6–8 倍实时**
  - 195 s 的歌 → 27.8 s
  - 262 s 的歌 → 34.8 s
  - 182 s 的歌 → 26.7 s
- GPU 峰值显存：**约 3.4 GB**（单窗口，与歌曲长度无关）
- CPU 只作退路：8 s 音频要 143 s（约 **0.06 倍实时**），够验证正确性，不够日常使用

### 5.1 模型的 BPM 从哪里来，要不要自己解析

**先回答：模型会输出一个 BPM，但它不是预测任务，而是 ABC 生成器顺带算的，且不可无条件信任。**

#### 模型的任务字段里没有 tempo

`schema_sheetsage2.py` 定义了 8 个 prompt 任务，全部字段：

| prompt | 解码字段 |
|---|---|
| `timestamp` | `timestamp` |
| `downbeat_meter` | `rhythm`（`meter` + `eighth_position`） |
| `structure` | `structure` |
| `key` | `key` |
| `chord_majmin` / `chord_full` | `chord` |
| `melody_vocal` / `melody_full` | `melody` |

没有 `tempo`。`events.json` 的 value 字段实测也只有这 6 类。
`result.json`、`playback.json` 里同样找不到 `bpm` / `tempo` 键
（`playback.json` 只有小节表 `measures`：`start`/`end`/`score_start`/`score_end`）。

模型真正预测的是**绝对拍点时间**（光芒 339 个 `timestamp` 事件）。

#### 模型自带的 BPM 在 `score.abc` 的 `Q:1/4=`

`notation_sheetsage2.py` 里：

```python
def estimate_tempo(score):
    seconds = score.subbeat_times[-1] - score.subbeat_times[0]
    quarter_notes = score.subbeat_quarters[-1] - score.subbeat_quarters[0]
    return float(quarter_notes / seconds * 60.0)      # 四舍五入后写成 Q:1/4=N
```

这是**首尾两点法**：只用到第一个和最后一个 subbeat。端点一有异常就偏。

#### 实测：两者交叉校验

| 歌曲 | 模型 `Q:1/4=` | 我们的网格拟合 | 结论 |
|---|---|---|---|
| 凤凰传奇 - 光芒 | 104 | **104.000** | 一致（差 0.000） |
| 李晓杰/玉萨 - 朋友的酒 | 120 | **119.995** | 一致（差 −0.005） |
| 毛阿敏 - 相思 | **98** | **100.001** | **不一致（差 +2.001）** |

`相思` 的 Q 值错了：结尾 169s 之后散拍，把首尾两点法的末端拖偏。而它的前 565 个拍间隔
是完美的 0.30000s = 200 BPM（6/8 下的 100 四分音符 BPM），逐拍拟合不受端点影响。

`Q:1/4=` 是整数（模型自己 `round()` 过），精度只有 ±0.5，也不能当作精细值。

#### 所以怎么用

1. **不要从零造 BPM** —— 优先读 `score.abc` 的 `Q:1/4=`，它就是"模型原始产出的 BPM"。
2. **但必须交叉校验** —— 用 `tempo.reconcile(abc_bpm, estimate)`：节拍网格是时间的真源，
   且鲁棒拟合用到全部拍点，所以**优先采用拟合值**，Q 值作为独立校验；不一致时如实报警，
   不做静默取舍。
3. **必须保留兜底** —— beat 少于两个或不含调性时**根本不生成 `score.abc`**，没有 Q 可读。
   这时只能靠节拍网格拟合。

结论：BPM 不是"全靠我们解析"，而是"模型给了一个端点估计，我们做无偏拟合并交叉校验"。

#### 三层干预能力（`src/sheetsage2_webui/tempo.py`）

| 层级 | 手段 | 接口 |
|---|---|---|
| ① 估计 | 鲁棒最小二乘 + 稳定段识别 | `estimate_tempo(rows)` → `TempoEstimate` |
| ② 吸附 | 取整 / 半整数 / 指定候选值 | `snap_bpm(bpm, "integer"\|"half"\|"candidates")` |
| ③ 重排 | 用恒速网格替换模型网格，量化并施加位移 | `compare_to_constant()` / `constant_beat_times()` / `retime()` |

第 ③ 层是真正改内容的操作，所以 `tempo_report.py --apply` 会**另写** `beat.constant.lab`，
不动模型原始产物；`retime()` 同时返回每个拍点的位移量（`shift_max` / `shift_mean`），
调用方据此判断这次干预动了多少。

典型用量：

```powershell
# 报告：模型 Q 值、我们的拟合值、交叉校验、吸附值
.\.venv\Scripts\python.exe scripts\tempo_report.py --json reports\tempo.json

# 指定 104 BPM，看模型网格相对它的漂移
.\.venv\Scripts\python.exe scripts\tempo_report.py --bpm 104

# 把拍网格按 104 BPM 恒速化，另存为 beat.constant.lab
.\.venv\Scripts\python.exe scripts\tempo_report.py --bpm 104 --apply
```

要判断"该不该干预"，看 `compare_to_constant()` 的漂移量：`光芒` 对齐到自身速度网格后
平均漂移只有 0.0039s，说明模型网格本身就非常规整，干预收益很小；`相思` 的末拍漂移
3.81s 全部来自结尾那段丢拍的区间，**该修的是那段，而不是整首曲的速度**。

### 5.2 拍号也是模型给的，而且带弱起小节

**拍号不需要我们从音频里猜**，它由 `downbeat_meter` 任务预测，解码到 `rhythm` 字段：
`rhythm = {"meter": [分子, 分母], "eighth_position": k}`。

注意它是**稀疏编码**：`meter` 只在开头和变化处出现，后续事件只给 `eighth_position`，
拍号靠继承。实测（事件总数 / 带 `rhythm` 的事件数 / 其中显式带 `meter` 的）：

| 歌曲 | 事件数 | 有 `rhythm` | 显式带 `meter` |
|---|---|---|---|
| 光芒 | 571 | 339 | 2 |
| 朋友的酒 | 754 | 525 | 2 |
| 相思 | 593 | 592 | 1 |

`beat.lab` 的第 3/4 列**不是**我们算的，而是模型自己的 `rhythm_rows()` 把 `meter`
继承展开后的结果：

```python
position = Fraction(int(eighth) * int(meter[1]), 8)      # 换算成第几拍
rows.append([float(event["time"]), int(position) + 1, int(meter[0]), int(meter[1])])
```

#### 开头那个"短小节"是弱起，不是噪声

| 歌曲 | 第一个事件的 meter | 切到主拍号的位置 | 弱起时长 |
|---|---|---|---|
| 光芒 | `[1, 8]` | ev[1] @ 0.280s | 0.27s |
| 朋友的酒 | `[3, 8]` | ev[5] @ 0.690s | 0.68s |
| 相思 | `[6, 8]`（开头即主拍号） | — | 无弱起 |

这和 `playback.json` 的小节表互相印证：第 0 小节的 `leading_rest` 分别是 0.875 / 0.625
（补足成完整小节的空白），`score.abc` 把它写成一个占位小节。

**所以主拍号不能取"众数"**——众数会把弱起小节当成一个合法拍号段混进来。`estimate_meter()`
改为取**最长的拍号段**作为主拍号，并把开头"拍数少于主拍号分子"的那一段识别为弱起：

```python
{"meter": "1/8", "beats": 1, "start": 0.01, "end": 0.28, "seconds": 0.27}
```

这段秒数正是上层卷帘要的 `pickupSec`。如果开头是**完整小节**再转拍号，则记为真正的
转拍号（`changes`）而不是弱起。

#### 拍号也做交叉校验

`score.abc` 的 `M:` 是模型另一条独立的记谱输出，可以和 `beat.lab` 的主拍号对：

| 歌曲 | `beat.lab` 主拍号 | `score.abc` `M:` | |
|---|---|---|---|
| 光芒 | 4/4 | 4/4 | 一致 |
| 朋友的酒 | 4/4 | 4/4 | 一致 |
| 相思 | **6/8** | **6/8** | 一致 |

三首全部一致，拍号这一项可以放心采信模型。`summary.json` 里的
`meter` / `abc_meter` / `meter_consistent` / `pickup` 就是这组信息。

### 5.3 变速曲：单一 BPM 根本不够用

`萧敬腾 - 皮囊`（355s，4/4）暴露了前两首简单样例掩盖的问题：

```
拍点 722 个，但拍间隔只有 5 个取值：0.48s ×564、0.52s ×90、0.56s ×65、0.40s ×1、0.44s ×1
局部速度：120 → 126 → 124 → 114 → 110 → 118 → 124 → 125 BPM
```

**这不是模型抖动，是真的变速**（段落之间速度不同）。后果：

- 0.48s 占 78% 的间隔，但它们**不连续**，被慢速段落切成若干段；
- 所以"最长稳定段"只覆盖 **10.8%** 的拍点，整曲拟合无意义；
- 模型自己的 `Q:1/4=122` 是对整条速度曲线的时间加权平均，而逐拍拟合给出的是
  **占主导那一段**的速度 125——两个数都不错，但**都不足以描述这首歌**。

处理方式（`estimate_tempo` 现在会一并给出）：

| 字段 | 含义 |
|---|---|
| `is_constant` | 是否可当作恒速曲。`皮囊` 为 `false` |
| `bpm_dominant` | 众数拍间隔对应的"主速度"（皮囊 125.0） |
| `tempo_range` | 局部速度曲线的 min / max / median（皮囊 109.93–125.68，中位 124.0） |
| `local_tempo` | 32 拍滑窗的完整速度曲线，可用来画变速示意图 |

`reconcile()` 也据此改变行为：**恒速曲优先采用节拍网格拟合值**（`相思` 就是这样把
模型错误的 98 纠正成 100.001）；**变速曲则采用模型的 Q 值**（它是整条速度曲线的
平均），并把 `confident` 置为 `false`，明确告诉调用方"这个数只是摘要"。

给上层的建议：遇到变速曲，**不要用单一 BPM 去换算 tick**，直接用
`playback.json` 的小节表（每小节都有 `start`/`end` 秒数）逐小节换算。


## 6. 风险与后续

1. **许可**：CC BY-NC 4.0，非商业。若产品要商用，需要先解决授权。
2. **上游可变**：remote code 会被动更新。集成时应固定 `revision` 或预热快照 + `local_files_only`。
3. **ABC 可能缺失**：节拍不足两个或不含调性时 `score.abc` 不生成，调用方必须处理 `abc_error`，
   不能假定 `score.abc` 一定存在。
4. **显存**：单窗口约 3.4 GB，长曲靠滑窗不涨显存；但和别的模型（如 ASR）同时驻留会挤爆 12 GB，
   后续接服务时建议用一个全局 GPU 锁串行化。
5. **时间模型**：模型输出的是秒。上层卷帘要用 tick，需要自己做「小节表 → tick」的换算，
   并且**以模型给出的 `playback.json` 小节表为准**，不要自己拍 BPM。
   速度见 §5.1：别用中位间隔法，用 `tempo.estimate_tempo()`。
6. **未验证**：`render_audio` / `render_score` 渲染链（需额外依赖）、
   `export_embeddings` 等张量导出、多首并发。

## 7. WebUI 落地：一键流水线

产品形态是"丢音频 → 开始识别 → 下载产物"，**没有任何参数可调**。这反过来约束了集成层：
所有判断必须自动完成，并且把依据留在报告里。

### 7.1 关键设计：BPM 不参与时间换算

一旦用户不能调 BPM，"BPM 算得准不准"就变成了一个**不该阻塞出谱**的问题。解决办法是
把时间换算彻底从 BPM 上摘下来，改用模型自己的小节表：

```
playback.json.measures[] = [{start, end, score_start, score_end}, ...]
                    ↓ 逐小节分段线性（score 单位是全音符）
秒  ←──────────────────────────────────────→  tick（PPQ 1920）
```

四首样例实测：

| 歌曲 | 小节数 | 小节表缝隙 | 秒↔tick 往返误差 |
|---|---|---|---|
| 光芒 | 86 | 0 | 2.8e-14 s |
| 朋友的酒 | 132 | 0 | 3.6e-15 s |
| 相思 | 100 | 0 | 2.8e-14 s |
| 皮囊 | 181 | 0 | 5.7e-14 s |

**恒速曲、变速曲、弱起小节走同一套代码**，一个分支都不需要。BPM 降级成纯元数据：
显示用、写 `set_tempo` 用。它算错与否都不影响出谱正确性。

### 7.2 自动裁决与理由

| 决策 | 来源 | 报告字段 |
|---|---|---|
| 拍号 | `estimate_meter()` 取最长拍号段 | `meter`、`meter_consistent`、与 `M:` 是否相符 |
| 弱起 | 开头短小节 | `pickup_seconds` |
| 主速度 | `reconcile()`：恒速→网格拟合，变速→模型 Q | `bpm`、`bpm_source`、`bpm_confident` |
| 变速 | `tempo_range` / `local_tempo` | `tempo_constant`、速度范围 |
| 调性 | `key.lab` 分段 | `keys`（含转调） |

### 7.3 速度表按段落拟合，而不是逐小节

歌里的速度变化**几乎总是发生在段落边界上**。`萧敬腾 - 皮囊` 是一个得到人工核对确认的样本：

| 时间 | 模型 `structure.lab` | 我们拟合 | 人工核对 |
|---|---|---|---|
| 0:00–2:52.3 | `intro` → … → `interlude` | **124.311 BPM** | 124 可行 |
| 2:52.3–3:46.7 | `172.28–226.72s verse` | **109.994 BPM** | 2:53–3:47 是 110 |
| 3:46.7–5:55.0 | `chorus` → `outro` | **124.069 BPM** | 之后又是 124 |

速度变化点（172.28s / 226.72s）与段落边界重合到 1 秒以内，拟合值 109.994 对 110 的误差
是 0.006 BPM。所以 `sectional_tempo()` 的做法是：

1. 把结构段按序攒成"至少 8 拍"的组（`皮囊` 里夹着 `189.76–191.92s` 这种 4 拍的碎片，
   单独拟合会得到 111.94 这种噪声值）；
2. 逐组最小二乘拟合速度；
3. 相邻组速度相差 ≤ 1 BPM 就合并，合并后重新拟合；
4. **残差超过一整拍的组不算恒速区**，并进相邻段——`朋友的酒` 开头 16.7s 的自由前奏
   （残差 0.63s > 拍长 0.50s）、`相思` 结尾的散拍段（0.75s > 0.30s）都属于这类；
   合并时**保留可信那一段的拟合结果**，不要跨过去重拟合，否则会把好段拖坏。

效果：`皮囊` 36 个结构段 → 3 个速度段；其余歌曲 → 各 1 段。逐小节的 181 个速度点被
替换成 3 个，既是人描述一首歌的方式，也正好能写进 DAW。

#### 一个变速段要多少拍才算数

`门尼 - 巴拉莱卡（The Rod）` 给出过反例：结尾只有 9 拍、拟合出 57.59 对前面 59.00，
**经人工核对是噪声**。所以再加一条：**拍点数少于 `min_segment_beats`（默认 16）的段落
不能独立成段**，并进相邻段。该曲因此从 3 段收敛到 2 段：

| 区段 | 拍数 | BPM | ×2 |
|---|---|---|---|
| 0.01–67.84s | 68 | 57.504 | 115.0 |
| 67.84–225.25s | 155 | 58.986 | 118.0 |

（原来那个 9 拍的 57.591 段被吸收。）

#### 残差不够用：还要看"拍间隔一致性"

`一棵小葱/张曦匀 - 壁上观（伴奏）` 暴露了残差指标的漏洞。它中段是连续起伏的自由速度，
被切成 4 个"速度段"（91.38 / 95.35 / 89.95 / 94.15），而它们的**拟合残差都小于一拍**，
所以全都通过了残差判据。但拍间隔一致性只有：

| 区段 | 残差/拍长 | 拍间隔一致性 |
|---|---|---|
| 103.5–119.5s | 0.52 | **8%** |
| 119.5–167.5s | 0.42 | **24%** |
| 167.5–201.5s | 0.18 | **25%** |
| 201.5–249.5s | 0.53 | **23%** |

残差只回答"能不能被一条直线穿过"，对缓慢起伏的速度太宽松。所以判据补上
**拍间隔落在拟合拍长 ±5% 内的比例 ≥ 60%**，低于此的段落算"网格不可靠"。

一致性必须**按整段重算**：合并时为了不拖坏拟合，保留的是可信子段的拟合结果，若直接沿用，
报告就会拿一小段的自洽度去背书一整段（该曲会显示 95%）。

#### 不可靠区不能随便并进邻居

补上一致性判据后，第一次跑出来的结果是"**0–249.5s @ 90.005**"——仍然是错的。原因是相邻的
不可靠段被**逐个**当成"小段"并进了前面那个恒速段。人工核对（1:09 处由 90 变 120）说明这条
结论是假的。修法分三步：

1. **相邻的不可靠段先合并成一片**，再判断它有多大；
2. 占全曲拍数 **超过 25%** 的不可靠区**绝不并进邻居**，自己作为"网格不可靠"的一段报出来；
3. 被当作噪声吸收的小段（不可靠 **或** 拍点数少于门槛）**不参与拟合**，否则它会把好段的残差
   顶上去，反过来让好段也变成"不可信"，挡住后面本该合并的段。

修完后该曲是 3 段，且分窗核对完全吻合：

```
分窗看拍间隔：0–60s 全 0.67s（90 BPM，干净）
             60–90s 开始混乱
             90–210s 0.74/0.5/0.7/0.56… 全乱
            240–284s 全 0.50s（120 BPM，干净）

输出：0.0–71.5s    90.005 BPM   一致 93%
     71.5–249.5s  90.213 BPM   一致 15%  [网格不可靠]
     249.5–284.0s 120.000 BPM  一致 100%
```

干净的 90 在 71.5s 结束，和人工核对的 1:09 吻合；模型在 69–240s 没能锁住 120，
240s 才重新锁上——这一事实被如实报出来，而不是被掩盖成"整首都是 90"。

#### 过渡段：`2020伴奏` 的 110 → 75 → 110

人工核对确认该曲是 `110 → 75 → 110`。检测结果是 5 段，中间多出的 `77.443` 与 `108.010`
是速度回摆时的**加速过渡**。给它们打上 `is_transition` 标记（速度严格落在左右两段之间
且自身可信）后，`stable_tempos` 就正好是 `[110.0, 75.0, 110.0]`，而过渡细节仍留在
`tempo_segments_detail` 里。

#### 网格坏掉时：值能自动定，网格要人拍板

`壁上观` 71.5–249.5s 这段模型没锁住速度。要判断"是不是只能人工填数"，得把两件事分开：

**① 速度值 —— 不需要人工填。** 三路独立证据：

| 来源 | 结果 |
|---|---|
| 模型自己的干净尾部（249.5–284s） | **120.000**（59 个间隔全 0.5000s，一致性 100%） |
| 全局最佳网格搜索（拍长 × 相位全搜） | **0.500s = 120.00 BPM** |
| librosa 在音频上独立估计 | **117.45**（0–60s 给 89.10，对得上模型的 90.005） |

librosa 的分辨率只到 ±2%（117.45 vs 120），所以它能**分辨速度档位**但不能定值；
定值靠模型自己那段干净的 120。

**② 网格 —— 自动修不了，但不是因为缺速度值。**

搜遍所有相位后，最佳网格（0.500s）的命中率只有 **50%**（±50ms），**±20ms 内是 0%**；
而模型自己的干净尾部是 **100% / 100%**。也就是说这段的拍点**本身就错了或漏了 77 拍**，
不是相位猜错。把网格硬套上去会让约一半的音符挪位（中位 0.037s，最大 0.32s）。

所以人工要决定的**不是 BPM**（已经知道是 120），而是**这一段要不要按恒定 120 重新量化**。

`tempo.suggest_grid_recovery()` 把这个判断自动化成一次三角测量，输出放在
`report.json` 的 `tempo.segments[*].recovery`：

```
重建评估：最佳网格 120.0 BPM，命中 100%/100%，音符位移中位 0.0s 最大 0.0s -> 可自动重建
重建评估：最佳网格 90.0 BPM，命中 56%/4%，音符位移中位 0.037s 最大 0.317s -> 需人工确认
```

`confident` 的判据是**用模型自己的干净段校准过的**：六个干净段全部通过
（光芒 100%/99%、巴拉莱卡 97%/95%、相思 97%/96%、朋友的酒 99%/96%、皮囊 100%/72%、
壁上观尾部 100%/100%），三个问题段全部不通过。只有这样才敢让"自动重建"这条路径开闸。

一个坑：不加**网格密度约束**时，拍长越短命中率越高，会选出 240 BPM 这种假阳性
（命中 81%，但 ±20ms 内只有 18%）。约束是"网格线数量不能超过拍点数的 1.5 倍"。

#### 半速锁定只提示、不擅自纠正

同一首歌模型报的是 2/4、四分音符 59 BPM，而**模型自己的 `Q:1/4=59.0` 和我们的拟合值
58.999 一致**——说明解析没错，是模型的节拍脉冲落在了半速上（人工核对约 115–118）。
**慢歌本身也可能是对的**，所以集成层不做自动翻倍，只在 `halftime_hint` 里给出 ×2 的
候选值并在报告里提示：

```
速度偏低（58.986 BPM）：可能是模型的半速锁定，×2 = 117.972；如确认可用 --bpm 117.972 覆盖
```

`tempo_mode` 可选 `section`（默认）/ `measure`（逐小节，最精确但最啰嗦）/ `single`。

### 7.4 两个必须处理的失败模式

1. **没有 `score.abc` 就没有小节表。** `build_playback` 写的是
   `measure_map(score, ...) if score is not None else []`，而模型在"节拍不足两个"或
   "没识别出调性"时根本不生成 ABC。此时秒↔tick 没有真源，兜底方案是
   `timeline.from_beats()`：用 `beat.lab` 里 `position == 1` 的强拍构造小节边界。
2. **变速曲不能写单一 `set_tempo`。** 按 §7.3 的分段速度表写：`皮囊` 得到 3 个速度点，
   而逐小节的 181 个值既精确又没法用。反过来，恒速曲经过分段合并后自然只剩 1 个速度点，
   不需要额外开关。

### 7.5 弱起小节的 tick

模型的 ABC 把弱起**补成完整小节**（`z24z4a4` = 28/32 休止 + 1/8 音符，`leading_rest=0.875`），
隐含一个 888 BPM 的小节。默认按**实际长度**处理，把这一小节缩成它真实的时值：

| 歌曲 | 记谱 tick | 实际 tick | 弱起拍号 |
|---|---|---|---|
| 光芒 | 7680 | 960 | 1/8 |
| 朋友的酒 | 7680 | 2880 | 3/8 |
| 相思 | 5760 | 960 | 1/8 |

映射仍是分段线性，往返照样精确。`pickup="padded"` 可保留模型记谱。

### 7.7 BPM 该报几位小数：不是四舍五入，是测出来的

`beat.lab` 的时间戳量化到 0.01s，直觉上会以为这就是精度上限。**不是。** 自助法（把每个拍点
按 ±5ms 均匀扰动后重拟合 200 次）给出的标准差只有：

| 区段 | 只算量化误差 | 滑窗实测 σ | 该报几位 |
|---|---|---|---|
| 巴拉莱卡 67.8–225.2s | ±0.0003 | **±0.003** | **3 位（真的）** |
| 壁上观 原唱 71.6–284s | ±0.0000 | **±0.000** | **3 位（真的）** |
| 2020伴奏 98.6–265s | — | **±0.0004** | 3 位 |
| 皮囊 0–172.3s | ±0.0004 | **±0.30** | 1 位 |
| 皮囊 226.7–355s | ±0.0006 | **±0.11** | 1 位 |
| 巴拉莱卡 0–67.8s | ±0.0010 | **±1.50** | 1 位 |
| 不由己 255.7–284.4s | — | **±3.09** | 1 位 |

真正的误差来自**模型拍点自身的抖动**，不是量化。所以 `TempoSegment.bpm_sigma` 用滑窗
（切 3 份、每次拟合一个窗口）测标准差，再由 `bpm_decimals` 决定报几位：
σ ≥ 0.05 → 1 位，σ ≥ 0.005 → 2 位，否则 3 位。

一个具体的教训：`萧敬腾 - 皮囊` 两段报出来是 `124.311` 和 `124.330`，看着像两个不同的速度，
但它们的 σ 分别是 ±0.30 和 ±0.11——**差 0.019 远在噪声之下，是同一个速度**。
现在两段都报成 `124.3`。速度表（`tempo_map`）也改用取整后的值，避免在 MIDI 里写一个
暗示了更高精度的数字。

`巴拉莱卡` 第 1 段的 σ 高达 ±1.5，是因为它开头 4 个拍点是 **0.25–0.27s（222–240 BPM）**，
之后才落到 1.02–1.06s——那 4 拍把整段拟合拖偏了。这类段现在标 `bpm_uncertain`。

### 7.8 歌词识别：Qwen3-ASR + Qwen3-ForcedAligner

#### 环境兼容性：可以共存，因为 transformers 版本要求完全重合

|---|---|---|
| SheetSage2 | transformers **4.57.6** | 4.57.6 ✓ |
| `qwen-asr` 0.0.6 | `transformers==4.57.6` | 4.57.6 ✓ |

这是最关键的一点：**两个模型锁的是同一个 transformers 版本**。`pip install qwen-asr` 的
dry-run 显示 `transformers` 与 `torch` 都不在待装列表里，只新增：

```
accelerate-1.12.0  dyNET38-2.2  gradio-6.17.3  gradio_client-2.5.0
nagisa-0.2.11  qwen-asr-0.0.6  qwen-omni-utils-0.0.9  sox-1.5.0  soynlp-0.0.493
```

`accelerate` 会被降到 1.12.0（只装在 venv 里，不动 anaconda base）。**实测降级后
SheetSage2 照常加载**（12.8s，2.52GB），没有回归。

模型目录里没有 `.py`，`model_type` 是 `qwen3_asr`，走的是官方包而不是 `trust_remote_code`。

#### 为什么按 SheetSage2 的区间切片

| 切片长度 | GPU 峰值 |
|---|---|
| 30s | 3.41GB |
| 60s | 3.63GB |
| 120s | 4.08GB |
| 195s | 5.09GB |

常驻 3.18GB，增量约 **10MB/s**，所以切片确实能把上限钉死。另外官方文档写对齐器
"up to 5 minutes"，而样例里 `2020原唱` 是 392s（6.5 分钟），切片是安全路径。
区间直接用 `structure.lab`——段落边界本来就是音乐上的自然切点。

#### 一个必须设的参数：`max_new_tokens`

同一段 100s 音频：

| `max_new_tokens` | 耗时 |
|---|---|
| 2048 | 176.4s |
| 512 | 41.4s |

模型在**没什么人声的段落会空转**，生成到上限才停。所以按切片长度给额度
（`tokens_per_second=12`，上限 1024），而不是给一个大数。

#### 0.6B vs 1.7B：差 2.4GB 显存，专有名词全对

同一首《光芒》，同一套切片：

| 格桑花 | 漏了 ❌ | "**格桑花**开放" ✅ |

| GPU 峰值 | 3904MiB | 6299MiB |
| 逐字时间戳 | 320 条 | 324 条 |

耗时几乎一样，**多花 2.4GB 换到专有名词全对**。默认建议 1.7B。

逐字对齐的精度（两版一致）：

```

净  30.17 - 30.33s     鹰  31.77 - 31.93s
天  30.33 - 30.65s     在  31.93 - 32.09s
```

前 30s 是纯器乐，正确地产出了 0 个字。

#### 本地权重与 remote code 缓存

`models/` 放本地权重后优先使用，仓库 id 兜底；`HF_HUB_OFFLINE=1` 下验证过可完全离线加载。

但 transformers 4.57.6 对**本地目录**走 `trust_remote_code` 时有个坑：它只复制
`auto_map` 指到的那个文件**加它的直接相对导入**（`check_imports` 只扫一层），
**不递归**。所以 `modeling_sheetsage2.py` 的直接依赖会被复制，但
`exports_sheetsage2.py → chord_spelling_sheetsage2.py` 这条二级链就漏了，
运行时报：

```
FileNotFoundError: ...\transformers_modules\SheetSage2\chord_spelling_sheetsage2.py
```

用仓库 id 加载没这个问题——那条分支会递归复制整个仓库。

修法是显式补齐：`bootstrap.sync_remote_code_cache()` 在加载本地权重前，把模型目录下
所有 `.py` 同步到 `HF_MODULES_CACHE / transformers_modules / <名字>/`（实测补 25 个文件）。
注意目录要带 `transformers_modules` 这一层，少一层就会同步到隔壁去、症状一模一样。

#### 填词：先定所有字的头，再补转音

`lyrics.assign_lyrics()` 的规则是"一个字挂到起点落在 `[s − 容差, e)` 内的第一个音，
同字范围内后续音写转音标记"。但**一次遍历会出错**：处理第一个字时就把后面的音标成 `-`，
而那个音其实是下一个字的。实测《光芒》开头变成 `曾 - 天 空`，"经"被吃掉。

改成两遍：

1. 先把所有字的"头"定下来（每个音只能被一个字占用）；
2. 再补转音，范围是"从这个字的头往后，直到下一个字的头之前"，且音符起点必须
   严格落在字的时间窗内（**容差只用来找头，不放大转音窗口**）。

修复前后：

| | 挂字 | 转音 | 丢掉的字 | 前 20 个 |
|---|---|---|---|---|
| 一遍 | 256 | 31 | 68 | `曾 - 天 空 上 雄 鹰 在 飞 翔 守 - 着…` |
| 两遍 | 268 | 23 | 56 | `曾 经 天 空 上 雄 鹰 在 飞 翔 守 望 着 那 片…` |

#### 为什么还会丢字：对齐器有 16–20% 的字给不出时间

继续追剩下的 56 个丢字，发现**不是匹配规则的问题，是数据的问题**。直接打印对齐器的原始输出：

```
'纯'   0.0000 -  0.0000   (0.0000)     ← 整个切片第一条就是零长度
'净'  18.3200 - 18.4800   (0.1600)
'天'  18.5600 - 18.8000   (0.2400)
...
零长度条目 26 / 132  （20%）
```

`ForcedAlignItem` 的 `start_time == end_time` 表示**这个字没对齐上**。全曲统计
53/324 = **16%**。

而匹配窗口是 `[start − 容差, end)`——`end == start` 时它退化成空窗口，正好在字所在的
那一刻闭合，把这些字全漏掉。修法：零长度就当成"这个字发生在这一刻"，给它一个
**以它为中心的对称窗口** `[start − 容差, start + 容差)`，并用"起点最近"代替"重叠最多"
作为退路（点状的字算不出重叠）。

#### 还有顺序错乱：需要单调性约束

修完窗口后又冒出一个问题：`喜马拉雅山` 被排成 `喜 马 拉 山 雅`。原因是雅和山都是
零长度、同一时刻，退路各自找最近的音就颠倒了。

加一条**单调性约束**：字和音都按时间推进，后面的字不能挂到前面的音上。这对上之后：

| | 挂字 | 转音 | 没分到字的音 | 丢掉的字 |
|---|---|---|---|---|
| 一遍（原始） | 256 | 31 | 37 | 68 |
| 两遍 | 268 | 23 | 33 | 56 |
| + 零长度窗口 | 300 | 12 | 12 | 24 |
| **+ 单调性** | **295** | **15** | **14** | **29** |

单调性让丢字从 24 回到 29，但顺序对了——顺序比数量重要。

剩下的 29 个丢字仍然全部来自那 16% 的零长度时间戳：**这些字没有真正的时间信息，
只能按邻近音符猜**。所以 `AsrRun` 现在会报 `zero_length_chars` 并在比例超过 10% 时告警：

```
! 53/324 个字没有可用时间戳（16%），填词时这些字只能按附近音符猜位置
```

### 7.9 改 BPM 要不要动音符？不用，但要盯住播放时长

**不用。** 在我们的架构里音符的 tick 来自小节表，速度表只决定 tick 怎么变回秒——两者解耦。
把 `tempo_map` 从 124.3 改成 120，**音符的 tick 一个都不动**，谱面位置不变。

但有个必须量化的副作用：**改速度表会改播放时长**。实测十首歌：

| 歌曲 | 原曲 | 分段速度表播放 | 误差 | **逐小节速度表** | 误差 |
|---|---|---|---|---|---|
| 光芒 | 195.17s | 196.44s | +1.27s | 195.16s | **−0.01s** |
| 朋友的酒 | 261.69s | 262.77s | +1.08s | 261.68s | **−0.01s** |
| 相思 | 181.85s | 178.50s | −3.35s | 181.84s | **−0.01s** |
| 皮囊 | 355.00s | 355.76s | +0.76s | 355.00s | **0.00s** |
| 巴拉莱卡 | 225.25s | 229.60s | +4.35s | 225.24s | **−0.01s** |
| 壁上观原唱 | 284.00s | 287.41s | +3.41s | 284.00s | **0.00s** |
| 壁上观伴奏 | 284.00s | 294.92s | **+10.92s** | 284.00s | **0.00s** |

（±0.01s 就是时间戳的量化下限。）

结论分成两个口径：

| 口径 | 音符 tick | 播放时长 |
|---|---|---|
| `tempo_map`（分段，1–5 个速度点） | 不变 | 差 −3.4 ~ +10.9s（最大 3.8%） |
| `tempo_map_exact`（逐小节） | 不变 | **±0.01s，精确** |

所以设计定为：**`tempo_map` 给人看，`tempo_map_exact` 给导出用**。两者都写进
`project.json`，报告里同时给出各自的时长误差，超过 0.5s 就出提示。

一个反过来的提醒：如果你要保的是**音符的秒位置**（原始演奏时间）而不是谱面位置，
那改 BPM 就**必须**同时改 tick——这时候"谱面准"和"演奏时间准"只能选一个。
逐小节速度表之所以两者兼得，是因为它本来就是小节表的逆映射，没有被简化过。

### 7.10 输入必须是含人声的完整混音（实测 A/B）



同一首《壁上观》，只差"有没有人声"：

| | 伴奏版 | **原唱版** |
|---|---|---|
| 0–70s | 90.005（110 拍，一致 93%） | 89.908（110 拍，一致 94%） |
| 70s–结束 | 90.213（279 拍，**一致 15%**）→ 249.5s 才切到 120 | **120.000（425 拍，一致 100%）** |
| 切换点 | 249.5s（错） | **71.6s**（人工核对 1:09） |

用拍间隔逐 5 秒定位，原唱是干净的两条线：

```
  0.0s  ->  ~90.9 BPM
 70.0s  ->  ~117.6 BPM
```

伴奏版从 70s 起在 81 / 88 / 107 / 86 / 120 BPM 之间乱跳——**不是模型的节拍算法不行，
是缺了主唱这条线索，它锁不住网格**。

`2020` 同样受益：原唱是干净的 `109.956 → 74.999 → 109.988`（3 段），
伴奏版多出两段过渡（5 段）。

所以流水线现在会在检测到大片网格不可靠区时给出提示：

> 有 178s 的拍点网格不可靠（占 69% 拍点）；若输入是伴奏版/纯音乐，
> 换用含人声的完整混音通常能让节拍锁定明显变好

注意这**不能**简单用"人声轨音符数"判断：`壁上观` 伴奏版仍有 47 个人声旋律音符，
`2020伴奏` 有 298 个——模型会把主奏乐器也标成 vocal。可靠的信号是**节拍网格本身的一致性**。

另一个附带发现：同一首歌两个版本的调性标注是 `C#:minor`（伴奏）与 `E:major`（原唱）——
这是关系大小调，key signature 相同，但模式标注会随版本变化，调号本身可采信、mode 需留意。



`bpm` / `pickup` 仍是 `pipeline.run()` 的参数，也仍是 CLI 的开关，**但 UI 默认不渲染**，
塞进"高级"折叠区。默认路径零参数。
