## 1. 现状盘一遍（重构后）

| 需求 | 现状 | 依据 |
|---|---|---|
| 一批歌一起跑 | 能：逐个 `POST /api/jobs` 带 `plan=transcribe,lyrics` | `routes/jobs.py:75-98` |

| 批次（分组 / 统计 / 重试失败） | 没有 | — |

### 1.1 一次批量在现有代码里长什么样

```
POST /api/jobs (file, plan=transcribe,lyrics) × N
  └─ JobManager.create()          # 落盘 input/、建工程、claim 目录
       └─ Scheduler.submit(job_id) # queue.put
            └─ _work()             # 单线程取
                 └─ _run(job)      # transcribe → lyrics → _finish
```

也就是说：**「批量」在后端只差两件事**——一次建 N 个工程、以及把 N 个建工程的结果组织成
一个可查询的东西。调度这一环一行都不用改（除并行/暂停）。

## 2. 输入：一个文件夹 + 同名 LRC

### 2.1 目录怎么交给服务

| 方案 | 怎么做 | 优点 | 代价 |
|---|---|---|---|
| **A. 服务端扫描**（推荐 P1） | `POST /api/batches/scan {dir}` → 预览 → `POST /api/batches {dir,…}` | 零上传；同卷可硬链接（瞬间）；能先给预览与体检；40 首也不用浏览器扛 | 只适用于「文件和浏览器同一台机器」（本工具正是） |
| B. 拖文件夹（上传） | `webkitGetAsEntry()` 递归 → 逐个 `POST /api/jobs` | 远程（`--host 0.0.0.0`）也能用 | 40 首 × 40MB 全走 HTTP；配对得在前端做；进度要多一层上传进度 |
| C. 收件箱目录 | `data_root/_inbox/` 固定路径 + 「打开文件夹」+「扫描」 | 零输入、零上传、路径永远安全 | 用户得把歌搬进去 |

**我的决定：P1 只做 A**，B 留到「远程/移动端」真的有人用时再做。理由：用户原话就是
「新建一个文件夹，里面放歌曲与同名 LRC」——文件夹已经在资源管理器里建好了，让他**把路径告诉程序**
比让他**把 1.6 GB 再传一遍**合理。C 作为 A 的一个快捷入口（「或者丢进 `_inbox/` 点这里」），
成本几乎为零。

安全边界（A 必须有的，别省）：

- 只接受绝对路径或数据根内路径；必须是存在的目录；不能是数据根本身；
- **源目录不能在数据根里面**（否则 `JobStore.load_existing` 会把它当工程收编，`job_storage.py:55-68`）；
- 只认 `AUDIO_SUFFIXES`（`job_files.py`）；一次最多 N 首（默认 200）；
- 明确「只读源目录，不改不删」——音频是**复制**进 `.webui/input/` 的（同卷可选硬链接）。

### 2.2 配对规则（新模块 `webui/batch_scan.py`，纯函数）

1. 以音频 **stem** 为准（`casefold()` + 去首尾空白），同目录下找同 stem 的 `.lrc`；
2. 多个候选取排序第一个，预览里标黄并说明「用了哪一个」；
3. 顺带认 `.txt`：无时间戳 → **不会跳过 ASR**（`parse_lyric_text` 给 `start=-1`，
   `runner.py:316-320`），预览必须写「纯文本，仍会跑语音识别」；
4. 编码不用管：`asr.read_lrc` 已按 utf-8-sig / gbk / big5 / shift_jis / utf-16 试；
5. **日语 LRC 要提前拦**：`_transcribe_with_lrc` 遇到假名会抛 `JaAlignerMissing`，整首失败。
   扫描阶段用 `tifa_align.guess_language()` 判一次，命中假名就**不挂 LRC**、退回语音识别，
   预览里标「日语：LRC 对齐不支持，将用语音识别」；
6. 其余问题（非音频、超大、空文件、重名、没有 LRC）全部进 `problems[]`，界面列出来，**不静默丢**。

### 2.3 最大的那笔免费收益：LRC 模式下还在白加载 ASR（没修）

`asr.transcribe_sections()` 在拿到 `lyrics_source` 时直接走 `_transcribe_with_lrc` 并 return，
注释写得很清楚「识别模型完全不用加载」（`asr.py:939-946`）。但 `runner.lyrics()` 在调用前**无条件**：

```python
if self.free_between_stages and self.engine.loaded:
    self.engine.release()                     # 把扒谱模型放掉（runner.py:339-340）
engine = self.asr.get(progress, asr_config)   # 加载 6.3G 的 1.7B（runner.py:342）
```

批量下这会被放大 40 倍：每首白等一次 ASR 加载、每首把扒谱模型卸载一次（下一首重载 ~15s）、
平白多一个 6.3G 的显存峰值。**修法**：`lyrics_source is not None` 且 TIFA 可用时，不 load ASR、
也不 release 引擎，直接用一个「只做对齐」的 `AsrEngine`（它 `_model is None` 时 `transcribe_sections`
根本不会碰 `self._model`）。这一条同时把并行需要的显存从 9.7G 降到 3.9G（§4.2）。

### 2.4 新问题（重构带来的）：LRC 存进 `options` 之后，列表变重了

现在 LRC 是**全文**存在 `job.options.lyrics_lrc` 里（`job_options.py:61`），而
`Job.snapshot()` 会把它整份吐出来（`job_models.py:286`），`GET /api/jobs` 又是**全量快照**
（`routes/jobs.py:71-73`）。实测本机工程的 `job.json` 是 **12~16 KB/个**（LRC 1~2.6 KB 在内），
一次 40 首的列表 ≈ **0.5~0.6 MB**。

今天没问题——因为侧栏只在 `init()` 拉一次。**但批量视图一定要轮询**（40 行 × 每秒），
1 秒 × 0.6 MB 就是灾难。两个办法，建议都做：

1. `GET /api/jobs?view=rows`：只回 `id / name / batch / state / stage / stages.{phase}.{state,progress} /
   error / elapsed / audio_info.duration` —— 侧栏与批量表都只需要这些；完整快照仍按 `/{id}` 取。
2. 快照里 `lyrics_lrc` 换成摘要（`has_lrc` + 行数 + 字数），全文只在 `GET /{id}` 给（编辑抽屉用）。
   或者改成「落 `.webui/lyrics.lrc`，options 只存路径」——但那是 v1 的建议，现在改回来
   要动 `_validate_text_option` 和抽屉，**不划算**；摘要方案更小。

## 3. 调度：串行、跳过、暂停

### 3.1 串行自动接（已有，别重造）

`workers` 默认 1（`__main__.py:77-78`），`_work` 取一个 job_id 就把它的 plan 跑完。批量只需要
「建 N 个 + 都排上 `transcribe,lyrics`」。

### 3.2 失败级联（实测，必须修）

```
plan queued: {'transcribe': 'running', 'lyrics': 'queued'}
final state: failed
  transcribe: failed · 模型炸了
  lyrics: failed · 还没有扒谱工程：请先跑「扒谱」
```

`_run()` 循环没有任何「上一阶段失败就停」的判断（`job_scheduler.py:226-240`）。批量下这既是
双倍噪音，也可能用**上一版的 `project.json`** 填出新歌词（扒谱失败但旧产物还在）。

修法（3 行）：阶段结束若终态不是 `done` → 清空剩余 `plan`。只影响本轮，手动重跑不受影响。

### 3.3 暂停 / 继续

「暂停」不能靠逐个 `cancel()`：`run_stage` 有 5 秒冷静期（`CANCEL_COOLDOWN_SECONDS`），
一台机器上连点「暂停 → 继续」会被自己挡住；而且 cancel 会把 plan 清掉、阶段标 cancelled，
恢复时要逐个重排，语义变脏。

正确做法（`job_scheduler.py` 里约 15 行）：加一个 `self._gate = threading.Event()`（默认 set），
`_work()` 取到 job 后先 `self._gate.wait()`；`pause()` 清 Event、`resume()` set。
**正在跑的那一首不打断**，只是不再派发下一个——这正是「暂停」该有的语义。

### 3.4 磁盘

`_assert_disk` 是**按工程**算的（`job_scheduler.py:402-415`）。批量要加一道总账：
开跑前 `Σ(音频×3 + 50MB)` 比一次剩余空间，不够就别开；运行中撞到磁盘满 → **暂停批次**
（配合 §3.3 的闸门），而不是 40 首连着失败 40 次。

## 4. 并行：12G 单卡上能做到什么（结论没变，P2 冻结）

### 4.1 现在把 `--workers` 调大，结果是坏，不是慢

一个 `RunnerSession` = 一个 `EngineProvider` + 一个 `AsrProvider`，被**所有** worker 共享
（`app.py` 的组装 + `runner_models.py:23-159`）。两个 worker 同时跑时：

- A 进歌词阶段 → `self.engine.release()`：把 B **正在推理的**模型置 `None` 并 `empty_cache()`；
- B 进扒谱阶段 → `self.asr.release()`：把 A 的 ASR 扔掉；
- 同一个 `nn.Module` 被两个线程同时 forward 也不该指望。

`grep -r workers tests/` = 空。这个开关从来没被验证过。

### 4.2 显存账（数字全部来自项目自己的记录）

本机 RTX 3080 12G，桌面已占 2.2G → 约 10G 可用。扒谱峰值 3379MiB（bf16 权重，`engine.py:76-78`），
ASR 1.7B 峰值约 6.3G（`runner.py:14-16`，实测记录在文件头注释），TIFA 约 0.3~0.5G。

| 组合 | 峰值 | 2 路可行？ |
|---|---|---|
| 无 LRC：扒谱 3.4G + ASR 6.3G | ~9.7G | ❌ |
| 有 LRC：扒谱 3.4G + TIFA ~0.5G（§2.3 之后） | ~3.9G | ✅（2 路 ~7.8G，3 路危险） |

结论：**「优先并行」在这台机器上只在有 LRC 时成立**；没 LRC 的歌必须串行。

### 4.3 做法（P2，不建议进 P1）

| 方案 | 改动量 | 真并行？ | 风险 |
|---|---|---|---|
| A 全局推理闸门（还是单线程） | 小 | ❌ 只重叠 ffmpeg/IO | 低，收益 <10% |
| B 每 worker 一套 provider（线程 + 各自模型副本） | 中 | ✅ | 进程内两份模型、GIL、OOM |
| C 多进程 worker（spawn + IPC） | 大 | ✅ 且隔离 | 每进程 15s 加载 + 独立 CUDA context；进度/取消/日志全过 IPC |

**P1 不做并行**：批量真正的价值是「40 首丢进去，不用守着」，串行已经满足。并行是第二期，
而且必须先有「准入 + 自动降级」（`torch.cuda.mem_get_info()` + 峰值表 → 2 或 1；OOM → 降到 1
并把那首重排一次；批次视图里写明「已降级」）。

## 6. 前端要如何表现

### 6.1 先定信息架构：批次是「容器」，工程仍是「原子」

三种可能的摆法：

| 摆法 | 好处 | 坏处 |
|---|---|---|
| ① 40 首歌直接铺进侧栏工程列表 | 零新概念 | 侧栏 248px 直接被淹没，单曲找不到 |
| ② 批量单独一个「页」（顶栏多一个 tab） | 干净 | 和「工作台/编辑」的层级打架，用户得在两个页之间跳 |
| **③ 侧栏分组 + 主区一个批次视图**（推荐） | 侧栏加一行分组头就有进度；详细表格放主区；点行仍进现有工程页 | 多一个视图状态 |

③ 的具体形状：

```
侧栏                                        主区
┌────────────────────────────┐   ┌──────────────────────────────────────────┐
│ 工程 42      [+ 新建]       │   │ 11-24 批量 · 40 首      [暂停][停止][重试]│
│ 拖入音频… 或 批量导入文件夹… │   │ ████████░░░░░░░░  12/40 完成 · 2 失败      │
│ ┌────────────────────────┐ │   │ 剩 26 首 · 预计 1~2 小时 · 并发 2（有词的）│
```

### 6.2 「新建批次」弹层：两步，只回答一个问题

第一屏要回答的只有一件事：**「这 40 首里，哪些有词、哪些没词、哪些会出问题」**。

```
┌ 批量导入 ──────────────────────────────────── ✕ ┐
│ 文件夹  [D:\音乐\2026-11\            ] [浏览…]  │
│         [扫描]   最近：D:\音乐\2026-10           │
│                                                  │
│ 40 首 · 32 首带 LRC（逐行对齐）· 8 首走语音识别  │
│ 预计 2~3 小时（串行）                             │
│ ⚠ 8 首没有同名 LRC，会走语音识别，词可能不对      │
│ ─────────────────────────────────────────────    │
│ #  歌名            大小    时长  歌词源           │
│ 1  富士山下.flac   28 MB  4:12  LRC 48 行         │
│ 2  爱情转移.flac   27 MB  4:02  LRC 52 行         │
│ 3  皮囊.flac       42 MB  3:58  无 · 将走识别     │
│ 4  君が僕の…flac   31 MB  3:40  日语 · 退回识别 ⚠ │
│ …                                                │
│ ─────────────────────────────────────────────    │
│ 参数（这批统一）  ▾                               │
│   扒谱：BF16 · 自动GPU · 整首 · 网格               │
│   歌词：1.7B · 干声 · 只跑唱段 · 自动              │
│   歌词源：按文件夹里的同名 LRC（32/40）——只读       │
│                                    [取消] [开始 40 首]│
└──────────────────────────────────────────────────┘
```

几个刻意的设计：

- **「浏览…」**：本地工具可以走服务端的原生目录选择器（`tkinter.filedialog.askdirectory`，
  在服务进程里弹窗）。`tkinter` 不可用时按钮置灰、提示「手动粘贴路径」。这是对「在浏览器里
  填服务器路径」这个别扭点的补偿，值得做——但要能优雅降级。
- **文件名/大小/时长**：时长要 ffprobe，40 首约 1~2 秒，扫描时顺手做（还能算 ETA）。
- **「歌词源」列是这一屏的主角**，四态：`LRC 48 行` / `无 · 将走识别` / `TXT · 无时间戳` /
  `日语 · 退回识别 ⚠`。用户扫一眼就知道「我这批配对上了没有」。
- **参数只设一次**（批量语义），其中「歌词源」行**只读**、显示配对结果——不能被面板覆盖，
  否则每首不一样，批量就没有意义了。
- 底部按钮文案是 **「开始 40 首」**，不是「确定」。

### 6.3 运行中的批次视图：进度不许撒谎

- **总进度 = 完成首数 / 总数**，一条分段条：绿=完成、红=失败、灰=未跑、蓝（条纹+呼吸）=当前。
  **不做「加权平均百分比」**——两阶段耗时不可知，一个 47% 什么都不说明。
- **剩余时间**：`Σ 未完成行的 eta ÷ 并发档`，给 `eta.py` 现成的 low~high 区间。
- **当前行**：高亮 + 行内 `▮▮62%`；当前阶段名在「扒谱 / 歌词」列里。
- **并发徽标**：`并发 2`，悬停说明「两首有 LRC 的歌同时在跑；显存不够会自动降到 1」。
  P1 里它恒为 1，但位置先留好——不然 P2 又要改布局。
- **降级**：顶部黄条（复用 `warn-box`）「第 12 首显存不够，已改为串行，后面会慢一些」。
- **失败行**：行内只放一句人话（`errors.describe` 的 message）+ 那个数字标红；点行看完整
  错误/下一步——**不要**在批量表里复刻阶段卡的错误 UI。
- **停止**：文案「正在停止…」并自己轮询到落终态（沿用 `useJobEvents.watchCancellation` 的思路）。

### 6.4 结束之后：这是这一屏真正的出口（**已实现**）

```
40/40 完成 · 用时 2 小时 5 分 · 2 首失败
[打包下载 39 个 SVP]  [只重试失败的 2 首]  [打开工程列表]
```

批量跑 40 首，用户最后要的是 **40 个 .svp**，不是 40 次点击「下载」。后端接口已经有了：

```
GET /api/exports/batch?ids=<id,id,…>&kind=svp&parts=vocal,instrumental
  → application/zip
     ├─ 富士山下.svp …        （每首一个；同名自动 -2，绝不覆盖）
     ├─ _manifest.json        （导出的：音符数/轨数/语言；跳过的：原因）
     └─ 响应头 X-Batch-Exported / X-Batch-Skipped（前端做 toast 用）
```

口径（`webui/batch_export.py` + `routes/exports.py`）：

- **单个工程失败不拖累整批**：还没扒谱、没音符 → 进清单的 `skipped`，其余照导；
  一首都导不出来才回 **409**（不发空包）；`ids` 里有不存在的工程回 **404**（"少了三首"要当场知道）。
- `kind=files` 是另一种口径：每首的产物按 `<歌名>/<相对路径>` 摊开（不套娃 zip），
  只认 `manifest.json` 里这一版的产物，`job.json` / `.webui/` 不进包。
- **与单首下载共用 `ensure_svp()`**：缓存键带 `artifacts_rev`（重跑过必然重算），先写 `.part`
  再改名；统计另存 `<key>.svp.json`，所以第二次（命中缓存）下载时清单里仍有音符数。
- zip 落在 `tempfile.mkdtemp()` 里，`BackgroundTask(cleanup_dir)` 下完就删（与备份包同一套）。

前端只剩三行接线：批次页/结束小结的按钮 → `window.location = /api/exports/batch?...`
（或 `<a download>`），成功/失败数从响应头或清单里取。

### 6.6 拖拽：`classifyDrop()` 的三条岔路

现在拖 2 个文件就默认「第一个混音、第二个干声」（`drop.ts:21-36`），批量进来后这条规则会把
「第二首歌」吃掉，必须先分类：

| 拖进来的东西 | 判定 | 行为 |
|---|---|---|
| 1 个音频 | 单曲 | 现状不变 |
| 2 个文件，其中一个名字像干声（`vocal/干声/人声/…`） | 单曲 + 干声 | 现状不变 |
| ≥2 个音频，且没有干声命名 | **批量** | 提示「拖进来是上传（约 1.6 GB）；填文件夹路径更快」→ P2 再实现上传式 |
| 1 个文件夹 | **批量** | 同上（浏览器拿不到绝对路径，只能上传） |

P1 里后两种先给一句「批量请用侧栏「批量导入」填文件夹路径」并把音频列表展示出来——比默默
把第二首当干声强一万倍，也不欠技术债。

## 7. API

```
（全部已实现）
GET  /api/exports/batch?ids=&kind=svp|files&parts=     → 批量下载 zip（§6.4）
POST /api/batches/browse                                 → 服务端弹原生目录选择器（没有桌面回 501）
POST /api/batches/scan      {dir}                        → 预览（不落盘，可传 probe/对齐器状态）
POST /api/batches           {dir, options, plan, link}    → 建工程 + 入队（返回轻量行 + problems）
POST /api/batches/upload    (multipart)                  → 拖文件夹用：一次一个文件，带 batch_id 归一批
GET  /api/batches                                        → 批次列表（派生）
GET  /api/batches/{id}                                   → 明细：行 + 统计 + 闸门状态
POST /api/batches/{id}/resume                            → **继续剩余**（崩溃/停止后一键补跑）
POST /api/batches/pause     /resume                      → 派发闸门（**队列级**，不打断在跑的那首）
GET  /api/jobs?view=rows                                 → 轻列表（§2.4）
```

「重试失败的」没有专门端点：前端对失败的成员逐个 `POST /jobs/{id}/chain`——和单首的
「自动提取」是同一条路，后端不用为批量多一个状态。

批次实体化之后，`GET /api/batches/{id}/export` 只需把成员 id 转给
`batch_export.export_batch()`——**导出这一层不会变**。

**批次不做后端实体（P1）**：批次 id + 标题写进每个 `job.json` 的 `batch` 字段，
`GET /api/batches` 从工程列表**派生**（去重 + 计数）。这样：
不引入第二套状态机、不需要 `.batches/` 落盘、重启后分组自动还在（工程还在就还在）。
代价：没有「批次报告」，重启后未跑的不会自动续（要用户点「继续」）——这个代价在当时可接受，
**上线后要收回**：见 [`批量健壮性调研.md`](批量健壮性调研.md)（建议加「继续剩余 N 首」）。

> 如果以后要「批次报告 / 自动续跑 / 跨设备共享批次」，再升级成实体（`.batches/<id>.json`）。
> `job_storage.py:55-56` 会跳过点开头的目录，所以落盘位置是现成的。
