# 批量处理调研：把「一个文件夹」变成一条批量工作流

> 需求原话：**新建一个文件夹，里面放歌曲与同名 LRC（如有）；优先并行，降级串行，上一个结束自动接下一个。**

结论先行：

- **串行批量几乎是白捡的。** `JobManager` 就是个单线程 FIFO 队列，一次 `create(plan=("transcribe","lyrics"))`
  就已经是「跑完一首自动接下一首」。要加的是「批次」这层壳（进度 / 统计 / 失败跳过 / 重启续跑），
  不是重写调度器。
- **真正必须先修的三个坑**：① `lyrics_lrc` 参数现在**根本设不进去**（PATCH 直接 500，已实测）；
  ② 阶段失败后**队列里的下一阶段照跑**（已实测：扒谱失败 → 歌词继续跑 → 再失败一次）；
  ③ `--workers 2` 是个**没有测试的陷阱**：两个阶段共用一套模型持有者，会互相 `release()` 正在用的模型。
- **并行只在一种形态下成立**：带 LRC 的歌（歌词阶段只需 TIFA，不加载 1.7B 识别模型）在 12G 卡上能跑 2 路；
  没 LRC 的歌峰值 ~9.7G，**只能串行**。所以「优先并行、降级串行」要做成**显存准入 + 运行期自动降级**，
  不是把 `--workers` 调成 2。

---

## 1. 现状盘一遍

| 需求 | 现状 | 依据 |
|---|---|---|
| 一批歌一起跑 | 能：逐个 `POST /api/jobs` 带 `plan=transcribe,lyrics` | `app.py:312`、`jobs.py:1164` |
| 上一个结束自动下一个 | **已经有**：单工作线程 FIFO，一个 job 的阶段全跑完才取下一个 | `jobs.py:1769-1808` |
| 批次（进度 / 统计 / 重试失败项） | 没有 | — |
| 失败就跳过这首歌 | **没有，且行为是反的** | §3.2 实测 |
| 重启后接着跑 | 没有：`_load_existing` 只恢复工程，不恢复队列 | `jobs.py:889-914` |
| 同名 LRC 自动挂上 | 不能，参数层就是坏的 | §2.3 实测 |
| 并行 | `--workers` 存在，但会互相拆模型 | §4.1 |

### 1.1 「串行自动接」为什么已经成立

```
create() ──queue.put(job_id)──▶ _queue ──▶ _work() ──▶ _run(job)
                                                   ├─ _next_phase() 取 transcribe → _run_phase()
                                                   ├─ _next_phase() 取 lyrics     → _run_phase()
                                                   └─ _finish()
```

`workers` 默认 1（`__main__.py:74`），所以「上一个结束自动进行下一项」不需要任何新代码——
**批量 = 建 N 个工程、都排上 `transcribe,lyrics`**。缺的只是让用户一次建 N 个工程、看得到整批的进度。

### 1.2 门禁怎么办

现在是「丢音频只建工程（`draft`），用户选完参数才排队」（`jobs.py:49-57`）。批量不能为了省事跳过它，
做法是：**批次对话框里选一次参数**（默认值来自 `/api/env`），建工程时直接写进 `options`，然后
`plan=("transcribe","lyrics")` 一次排上。门禁的意图（先选参数再跑）保住了，交互从 N 次变成 1 次。

## 2. 输入：一个文件夹 + 同名 LRC

### 2.1 目录怎么交给服务

| 方案 | 怎么做 | 优点 | 代价 |
|---|---|---|---|
| **A. 服务器路径扫描**（推荐主入口） | `POST /api/batches/scan {dir}` 扫描 → 预览 → `POST /api/batches` 建批次 | 零上传；可硬链接/复制；能先给预览与体检；40 首歌也不用浏览器扛 | 只适用于「文件和浏览器在一台机器上」（本工具正是） |
| B. 浏览器拖文件夹 | `webkitGetAsEntry()` 递归 / `<input webkitdirectory>` | 远程（`--host 0.0.0.0`）时也能用 | 40 首 × 40MB 全走 HTTP；前端要分类配对 |
| C. 监视「收件箱」目录 | 定期扫 `data_root/_inbox/` | 无 UI | 隐式、难发现，且和 `_load_existing` 的语义容易打架 |

建议 **A 为主、B 为兜底**。理由：这是本机工具，安全层已经有回环 Origin/Host 校验（`security.py`，`__main__.py:158-162`），
而且 `lyrics_lrc` 早就能读本机任意文件（`runner.py:466-468`）——「接受一个本机路径」不是新增的攻击面种类。
但仍要收紧：只接受绝对路径或数据根内路径、必须存在、不能是数据根父链、不能是数据根的子目录（否则
`_load_existing` 会把源目录当工程收编，见 `jobs.py:900`）、只认白名单后缀、首数上限（如 200）。

### 2.2 配对规则（`webui/batch.py`，纯函数，好测）

1. 以音频 **stem** 为准（`casefold()` + 去首尾空白）；
2. 候选 LRC = 同目录下 `stem` 相同的 `.lrc`；多个候选取排序第一个并在预览里标黄；
3. 顺带认 `.txt`：无时间戳 → **不会跳过 ASR**（`parse_lyric_text` 给 `start=-1`，`runner.py:472-475`），
   预览里必须写明「纯文本，仍会跑语音识别」；
4. 编码不用管：`asr.read_lrc` 已按 utf-8-sig / gbk / big5 / shift_jis / utf-16 试（`asr.py:152`）；
5. **日语 LRC 要提前拦**：`_transcribe_with_lrc` 遇到假名会直接抛 `JaAlignerMissing`（`asr.py:734-738`），
   整首失败。扫描阶段用 `tifa_align.guess_language()` 判一次，命中假名就**不挂 LRC**、退回语音识别，
   预览里标「日语：LRC 对齐不支持，将用语音识别」；
6. 其余问题（非音频、超大、空文件、重名、没有 LRC）全部进 `problems[]`，界面列出来，**不静默丢**。

### 2.3 阻塞点：`lyrics_lrc` 现在设不进去（实测）

`PARAM_SPECS` 里它没有 `options` 字段：

```python
{"key": "lyrics_lrc", "label": "歌词LRC", "default": "", "widget": "text", "hint": "..."}   # jobs.py:146
```

而 `option_values()` 无条件读 `PARAM_INDEX[key]["options"]`（`jobs.py:170`），`validate_options` 也没有文本类特判
（`jobs.py:178-194`）。实测：

```
PATCH /api/jobs/{id}/options  {"lyrics_lrc": "[00:01.00]晚风停在旧站台"}
→ 500 Internal Server Error
validate_options({'lyrics_lrc': ...}) → KeyError: 'options'
```

即：页面上「歌词源」抽屉点「应用」本来就是坏的，LRC 功能只能靠手改 `job.json` 才用得上。批量必须先把这条修通：

- `widget: "text"` 的参数不走白名单，改校验「长度上限（如 200KB）+ 必须能解析出至少一行」；
- **别把 LRC 全文塞进 `options`**：`/api/jobs` 每次返回所有工程的快照（`snapshot()` 带 `options`），
  40 首 × 几 KB 就变成每次轮询几百 KB 的噪音。落盘到 `.webui/lyrics.lrc`，`options.lyrics_lrc` 只放路径。

### 2.4 最大的那笔免费收益：LRC 模式下还在白加载 ASR

`transcribe_sections` 在拿到 `lyrics_source` 时直接走 `_transcribe_with_lrc` 并 return，注释写得很清楚：
「识别模型完全不用加载」（`asr.py:845-852`、`asr.py:841`）。但 `runner.lyrics` 在调用前**无条件**：

```python
if self.free_between_stages and self.engine.loaded:
    self.engine.release()                    # 把扒谱模型放掉（runner.py:495-496）
engine = self.asr.get(progress, asr_config)  # 加载 6.3G 的 1.7B（runner.py:498）
```

后果（批量下会被放大 40 倍）：

- 每首白等一次 ASR 权重加载；
- 每首把扒谱模型卸载一次 → 下一首扒谱要重新加载（本机实测 ~15s）；
- 平白多出一个 6.3G 的显存峰值。

40 首 ≈ 20 分钟纯浪费。修法：`lyrics_source is not None` 且 TIFA 可用时，**不 load ASR、也不 release 引擎**，
直接拿一个「只做对齐」的 `AsrEngine`（它 `_model is None` 时 `transcribe_sections` 根本不会用 `self._model`）。
这一条同时把「并行」的显存账从 9.7G 降到 3.9G（见 §4.2），是并行能做的前提。

## 3. 调度：串行、跳过、重试

### 3.1 串行

不需要新机制。批次层只负责：建工程 → 排 `transcribe,lyrics` → 展示批次快照 → 暂停/取消/重试失败项。

### 3.2 失败级联（实测，必须修）

```
plan queued: {'transcribe': 'running', 'lyrics': 'queued'}
final state: failed
  transcribe: failed · 模型炸了
  lyrics: failed · 还没有扒谱工程：请先跑「扒谱」
```

`_run` 的循环没有任何「上一阶段失败就停」的判断（`jobs.py:1794-1808`）。批量下这既是双倍噪音，
也可能用**上一版的 `project.json`** 填出新歌词（扒谱失败但旧产物还在）。修法：阶段结束若终态不是 `done`，
清空剩余 `plan`（只影响本轮，手动重跑不受影响）。

### 3.3 磁盘

`_assert_disk` 是**按工程**算的（`jobs.py:1965`）。批量要加一道总账：开跑前 `Σ(音频×3 + 50MB)`
和剩余空间比一次，不够就别开；运行中撞到磁盘满 → **暂停批次**，而不是 40 首连着失败 40 次。

### 3.4 重启续跑

批次状态落 `.batches/<id>.json`（点开头 → `_load_existing` 不会扫它，`jobs.py:900-902`），
里面存 `job_ids`、每首的状态、参数、并发档位。恢复后**默认不自动续跑**，列表里给「继续批次」——
开机就把 GPU 占满不给选项是坏体验。

## 4. 并行：12G 单卡上到底能做到什么

### 4.1 现在把 `--workers` 调大，结果是坏，不是慢

一个 `RunnerSession` = 一个 `EngineProvider` + 一个 `AsrProvider`，被**所有** worker 共享
（`app.py:191-194`、`runner.py:344-362`）。两个 worker 同时跑时：

- A 进歌词阶段 → `self.engine.release()`：把 B **正在推理的**模型置 `None` 并 `empty_cache()`（`runner.py:495-496`）；
- B 进扒谱阶段 → `self.asr.release()`：把 A 的 ASR 扔掉（`runner.py:382-383`）；
- 同一个 `nn.Module` 被两个线程同时 forward 也不该指望（CUDA 流、显存峰值、内部 dtype 状态）。

`grep -r workers tests/` = 空。也就是说这个开关从来没被验证过。

### 4.2 显存账（数字全部来自项目自己的实测记录）

本机：RTX 3080 12G，桌面已占 2.2G → 约 10G 可用。扒谱峰值 3379MiB（bf16 权重，`engine.py:76-78` 引的实测），
ASR 1.7B 峰值约 6.3G（`runner.py:14-16`），TIFA 约 0.3~0.5G。

| 组合 | 峰值 | 2 路可行？ |
|---|---|---|
| 无 LRC：扒谱 3.4G + ASR 6.3G | ~9.7G | ❌ |
| 有 LRC：扒谱 3.4G + TIFA ~0.5G（§2.4 之后） | ~3.9G | ✅（2 路 ~7.8G，3 路危险） |

所以「优先并行」在你这台机器上**只在有 LRC 时成立**；纯 ASR 的歌占 6.3G，只能串行。
这不是保守，是显存决定的。

### 4.3 三种做法

| 方案 | 改动量 | 真并行？ | 风险 |
|---|---|---|---|
| **A. 全局推理闸门**（还是单线程） | 小 | ❌ 只重叠 ffmpeg / IO | 低，收益 <10% |
| **B. 每 worker 一套 provider**（线程 + 各自模型副本） | 中 | ✅ | 进程内两份模型、GIL、OOM |
| **C. 多进程 worker**（`spawn` + 队列 IPC） | 大 | ✅ 且隔离 | 每进程 15s 加载 + 独立 CUDA context；进度/取消/日志全要过 IPC；`spawn` 下 app 不能被子进程 import |

推荐 **B**（第一期并行），C 只在 B 在目标机器上不稳时才做。

### 4.4 「优先并行、降级串行」落到代码里

1. **开批次时算准入**：`torch.cuda.mem_get_info()` + 每阶段峰值表（新 `webui/vram.py`，探测函数可注入 → 纯函数好测）
   → `concurrency = 2 if 够 else 1`；
2. **运行期闸门**：一个可收缩的信号量（`Condition` 实现，收缩只影响「下一个」，不打断在跑的），
   控制同时进行的推理阶段数——降级不需要杀线程；
3. **OOM 兜底**：`engine._is_out_of_memory`（`engine.py:47`）命中 → 该阶段重排一次 + 闸门降到 1 +
   批次报告写一行「第 12 首 OOM，已降级串行重跑」；
4. **降级必须可解释**：批次快照里露出 `concurrency` 与 `degraded_reason`，否则用户只觉得「变慢了」。

## 6. API 草案

```
POST   /api/batches/scan        {dir}                      → 预览（不落盘）
POST   /api/batches             {dir, options, concurrency, plan?} → 批次快照（建工程 + 入队）
GET    /api/batches                                        → 批次列表
GET    /api/batches/{id}                                   → 快照：job 行 + 统计 + 实际并发 + 降级原因
POST   /api/batches/{id}/cancel                            → 取消剩余（在跑的走协作式取消）
POST   /api/batches/{id}/retry-failed                      → 只重排失败项
DELETE /api/batches/{id}                                   → 只解散批次，工程不删
```

批次快照里每行至少要有：`job_id, name, has_lrc, state, transcribe.state, lyrics.state, error,
elapsed, eta`。总进度 = 已完成 / 总数（再给一个 Σ eta 的剩余时间估计，`eta.py` 现成）。

## 10. 需要拍板的几件事

1. **入口形态**：服务器路径扫描（A）还是浏览器拖文件夹（B），还是两个都要？
2. **并行默认值**：`auto`（按显存自己决定）还是默认 `off`（要用户显式开）？
3. **「暂停批次」要不要**：暂停 = 不再派发新的，正在跑的不打断（实现很便宜，但没有它是「只能取消」）。
