# 批量健壮性调研：中途断掉、排队与恢复

> 起因：批量功能已推送（`b6c84d5`，beta 分支），但两类场景还没验过——**跑到一半断掉**、
> **排队是否真的在排**。这一篇只补批量新增的那几条，不改 `docs/健壮性保障评估.md` 的全局结论。
>
> 结论一句话：**队列是"进程内"的——进程活着就排队，进程一没就全没。** 批量把这一点放大成
> 「40 首跑完 12 首崩了，重启后没有任何一键继续」；再加上磁盘满会 28 连败。要补的不是推理，
> 而是**批次这一层的"人回来以后怎么办"**。

---

## 1. 先把「断掉」拆成六种

| # | 场景 | 现在会发生什么 | 用户感受 |
|---|---|---|---|
| A | 服务进程崩了 / 被任务管理器杀 | 队列丢；正在跑的那首阶段被标「上次运行被中断」；已完成的首保留 | "还有 28 首没跑？" |
| B | 关掉黑窗口（`00_start.bat`） | 同 A（进程退出） | 同 A |
| C | 断电 / 蓝屏 | 同 A，另外可能留下写了一半的产物（原子写保护了 json） | 同 A + 担心产物坏了 |
| D | 浏览器关掉 / 刷新（服务还活着） | **没影响**：服务端照跑；重开页面从 `/api/batches` 重新派生 | 正常 |
| E | SSE / 网络断（休眠唤醒、换网） | 单工程：自动重连 + 3s 兜底轮询；批量视图：1.5s 轮询 | 正常（会看到一次「进度流断开」日志） |
| F | 拖文件夹上传中途断（第 20 首传到一半） | 已建的 19 首是完整工程，第 20 首失败，后面的没建；`index` 出现空洞 | "我传了 40 首，怎么只有 19 首？" |

> A/B/C 是同一类（进程消失），F 是上传路线独有。

## 2. 现状逐条核对（带代码依据）

| 事实 | 依据 |
|---|---|
| **队列只在内存**：`queue.Queue`，重启即空 | `job_scheduler.py:77` |
| **`plan` 不落盘**：只在 `Job.plan` 里，`snapshot()` / `metadata()` 都不含它 | `job_models.py:149` |
| **恢复时把 queued/running 的阶段改成 `idle`**，并写「上次运行被中断（程序重启），可以重跑」 | `job_storage.py:127` |
| **恢复后的工程状态是 `draft`**（不是 queued） | `job_storage.py:144` |
| **暂停闸门也是内存里的 `threading.Event`**，重启默认恢复派发 | `job_scheduler.py:89-99` |
| **批次归属会恢复**：`job.batch` 落 `job.json`，重启后分组还在 | `job_storage.py` 的 `batch` 恢复 + `job_models.batches_of` |
| **磁盘不够只失败这一首**：`_assert_disk` 抛 `StageFailure` → 阶段失败 → 跳过剩余 → 下一首继续 | `job_scheduler.py:451` + `_run` 的失败分支 |
| **浏览器侧断线没问题**：SSE 带 `since` 重连、3s 兜底轮询；批量视图 1.5s 轮询；关页面不影响服务端 | `useJobEvents.ts`、`useBatch.ts` |
| **上传式批量逐个传**：客户端循环 `POST /batches/upload`，第一个铸批次 id，后面带上 | `useBatch.uploadFiles`、`routes/batches.py` |
| **存活探测**：3s 一次 `healthz`，连续 3 次失败显示「后台服务已停止」；批量页也显示 | `useStudio.probeHealth`、`App.vue` |

一个容易误判的点：**"排队 28" 只存在于当前进程**。界面上那行「排队 28」来自
`manager.env().queue.pending`（数内存里的工程状态），进程一没就归零——它不代表"落盘的待办"。

## 3. 风险排序（按用户的实际损失）

| 级别 | 风险 | 为什么会亏 |
|---|---|---|
| 🔴 P1 | **重启后剩余工程不会继续，也没有一键继续** | 用户以为还在排队，实际要手动点 28 次「自动提取」 |
| 🔴 P1 | **磁盘满 → 整批 28 连败** | 每首都走完 `assert_disk` 失败、写事件、刷日志，人还得逐个重试 |
| 🟠 P2 | **上传式批量中断 → 不知道差哪几首** | 没有"还应有多少首"的记录，只看到 19 个工程 |
| 🟠 P2 | **暂停被重启抹掉** | 崩在暂停状态 → 重启后继续跑满 GPU |
| 🟡 P3 | 批次页不汇总"中断过的那几首" | 要在 40 行里找那个「上次运行被中断」 |
| 🟢 P4 | 下载 zip 断掉 | 重下即可（SVP 有缓存，几秒） |

## 4. 建议的改法

### P1-1 批次「继续剩余」（前后端）

- 后端：`POST /api/batches/{id}/resume` → 把该批次里状态 ∈ `{draft, cancelled, failed}` 的成员
  按 `index` 依次 `run_chain()`，返回重排数量。**不要**动已完成的那几首。
- 前端：批次页在 `running === 0 && pending > 0` 时显示「继续剩余 N 首」；重启后打开批次就能点。
- 语义写清楚：失败的和用户主动停的一起重排（都是"没结果"的那一堆）；想只重试失败的，
  用现有的「重试失败的 N 首」。
- 验收：`test_batch_resume_remaining_after_restart`——建 3 首、只跑完 1 首，重建 `JobManager`
  （模拟重启）后调 resume，剩下 2 首都要进队列并能跑完。

### P1-2 磁盘满就暂停批次

- `_assert_disk` 失败时：如果这个工程属于批次 → `scheduler.pause()`（闸门）+ 该行落 `E_DISK_FULL`
  + 前端顶部黄条「磁盘满了，批次已暂停；清理后点继续」。
- 为什么必须暂停：磁盘不够是**整台机器**的状态，不是这一首的；不暂停就是 28 次同样的失败。
- 验收：`test_disk_full_pauses_the_batch`（把磁盘探测换成"永远不够"，断言第二个工程不再开跑）。

### P1-3 上传式批量的「还差几首」

- 第一个上传请求带上 `expected_total`（客户端知道拖了几首），服务端记进 `batch`；
  批次页 `total < expected_total` 时提示「还差 N 首——把同一个文件夹再拖一次会接着传」。
- 客户端把最近一次的 `{batch_id, expected_total, 文件夹名}` 存 `localStorage`；重拖同名文件夹
  自动带上 `batch_id` 续传（服务端已经支持复用批次）。
- 验收：手工（传到一半断网）+ 单测（`localStorage` 恢复逻辑）。

### P2（可以缓）

- **暂停状态持久化**：`paused` 落 `data/.paused` 标志，重启后仍暂停。配套：启动时如果发现
  `.paused` 就在界面顶部提示"上次是暂停状态"。
- **批次页「中断汇总」**：`interrupted` 计数进批次快照（数成员 message 以「上次运行被中断」
  开头的行），顶部一条 banner，点击定位到那几行。

## 5. 验收（手工清单，10 分钟能跑完）

1. 建 6 首的批次（假 runner 起服务，`tmp/serve_batch_demo.py`）；
2. 跑到第 3 首时 `Stop-Process -Name python -Force`（模拟崩溃）；
3. 重启服务 → 打开批次：应看到 2/6 完成、4 首「待开始」，且顶部有「继续剩余 4 首」；
4. 点继续 → 4 首依次跑完；
5. 把演示服务的磁盘探测换成 `return 0` 剩余 → 第二首应触发暂停，而不是继续失败；
6. 浏览器刷新 / 关页面再开：进度与队列不受影响（这条现在就成立，留作回归）。

## 6. 工作量与顺序

| 项 | 估时 | 状态 |
|---|---|---|
| P1-1 继续剩余 | 0.3 天 | ✅ 已做（`POST /api/batches/{id}/resume` + 批次页按钮） |
| P1-2 磁盘满暂停 | 0.2 天 | ✅ 已做（`_run_phase` 里 `E_DISK_FULL` → 闸门；批次页黄条） |
| P1-3 上传续传 | 0.3 天 | ✅ 已做（`expected_total` + localStorage 续传 + 「还差 N 首」） |
| P2 暂停持久化 / 中断汇总 | 0.3 天 | ⏳ 未做 |

落地时补的两处（都是"继续剩余"跑不通之后才暴露的）：

1. **僵尸阶段**：工程已经是终态（cancelled/failed），但某个阶段还挂着 `queued`——
   `run_stage` 的重复入队去重会直接早退，`resume` 看起来排上了、其实什么都没发生。
   现在去重条件加了 `job.state not in TERMINAL_STATES`，并补了回归测试。
2. **取消要清场**：`_run` 因取消 break 时，把 plan 里剩下的阶段标 `cancelled`（以前留着
   `queued`，就会产生上面那种僵尸）。

验收（2026-11-24 实测）：4 首被 `停止` 的批次 → 批次页显示「继续剩余 4 首」→ 点一下
4/4 跑完（20 秒，假 runner）；上传式批次声明 `expected_total=4` 只传 2 首 → 黄条
「还差 2 首没上传」。

顺序建议（已完成）：P1-2 → P1-1 → P1-3（磁盘满最伤：它会让一整批白跑；继续剩余是"人回来"的主路径）。
