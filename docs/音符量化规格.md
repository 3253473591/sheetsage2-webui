# 音符量化规格（P0）

> 实现：`src/sheetsage2_webui/quantize.py`
> **移植基准：`reference/Vocal2Midi V2/inference/quant/smart_quantize.py`**（Apache 2.0）
> 测试：`tests/test_quantize.py`（36 项）+ `tests/test_quantize_samples.py`（4 项真实样本）
> 验证脚本：`scripts/quantize_real_check.py`
> 对照文档：`docs/Vocal2Midi-对照与借鉴.md` §2⑤、§5

---

## 0. 一句话

`project.json` 的音符 tick 原本是秒的线性插值，落在任意 tick 上。量化把它们吸到
**网格**上，同时尽量不动原来的演奏，并且**让静音也参与对齐**——量化后整条旋律
头尾相接，不会凭空多出或少掉空拍。

---

## 1. 为什么必须做

| 不做 | 做了 |
|---|---|
| 卷帘上音符落不到格子 | 边界全在网格线上 |
| 导不进 DAW（时值不是任何音符） | 时值就是网格步长的整数倍 |
| 反复跑同一首歌，每遍 tick 都不同 | 已在网格上的旋律原样通过（幂等） |

**实测**（`output/` 里 13 个真实工程 / 26 条轨道 / 6927 个音，`scripts/quantize_real_check.py`）：

| 工程 | 拍号 | 量化前在网格上 | 量化后 | 失败轨道 | 平均位移 | p90 | 最大 |
|---|---|---|---|---|---|---|---|
| 忘川风华录（人声） | 4/4 | 98.3% | **100%** | 0 | 0.000s | 0.000s | 0.007s |
| 朋友的酒（人声） | 4/4 | 100% | **100%** | 0 | 0.000s | 0.000s | 0.000s |
| 光芒（人声） | 4/4 | 1.2% | **100%** | 0 | 0.002s | 0.005s | 0.007s |
| 江隐尘（人声） | 4/4 | 99.3% | **100%** | 0 | 0.000s | 0.000s | 0.003s |
| 巴拉莱卡（人声） | 2/4 | 34.9% | **100%** | 0 | 0.002s | 0.005s | 0.010s |
| 2020原唱（人声） | 4/4 | 39.3% | **100%** | 0 | 0.002s | 0.005s | 0.074s |
| 壁上观（人声） | 4/4 | 8.8% | **100%** | 0 | 0.004s | 0.010s | 0.010s |
| **相思（人声）** | **6/8** | 54.2% | **100%** | 0 | **0.002s** | **0.010s** | **0.010s** |
| 皮囊（人声） | 4/4 | 42.6% | **100%** | 0 | 0.006s | 0.020s | 0.030s |

**网格步长在全部工程上都是 20 tick**（一拍的 1/96 = 32 分 × 三连音），与拍号无关。
26 条轨道**没有一条量化失败**；**最大位移从 0.86s（V1）降到 0.12s**。
网格细了四倍（60 → 20 tick），所以"位移 ≥ 一个网格步"的计数天然变大（690/6927 = 10%）；
按**同样的 20 tick** 去衡量 V1，那个数会大得多（《忘川》单独一条就是 350/656）。

> **6/8 的那一行原来是坏的**：网格写成"一小节的 1/32"时，6/8 一小节 = 3 拍，
> 切 32 份是 **180 tick**，而模型给这首歌的 onset 本来就在 **60 tick** 的格子上，
> 两者对不上，于是 128/214 个音被搬了 ≥180 tick（均值 208.6 tick、最大 709）。
> 改成"一拍的 1/96"之后：**0 个音位移 ≥ 网格步，均值 7.3 tick、最大 10 tick**。
> 见 §3 与 §7。

## 2. 算法

### 2.1 记录链

音符按时间排序。**相邻音符之间的静音也做成一条 gap 记录**，音符和静音串成一条
头尾相接的链。重叠音符**不裁剪**——它们会让链不可行，此时判失败、音符保持原样。

### 2.2 锚点与列

- 第一条记录的起点就近取整到网格，作为链的原点 `anchor`（负数用对称取整）。
- 全链跨度 `span` 就近取整成列数 `col_count`。
- 每条记录只有一个自由度：占几列 `j ∈ [max(1, dcols-16), dcols+16]`，
  `dcols = floor(原时长 / 网格步长)`。起点列 = 上一条终点列 + 1。
- **末条记录的终点由 DP 自己挑最优列**（V2；V1 是强制在 `col_count-1`）。

### 2.3 打分（最大化）

| 项 | 式子 |
|---|---|
| 起点 | `M(pos_start) − 0.5·((pos_start−orig_start)/一拍)²` |
| 时长 | `−((j·GRID − orig_dur)/一拍)²` |
| 终点 | `M(pos_end) − 0.5·((pos_end−orig_end)/一拍)²` |

**三个距离全部按"一拍"归一，不是按小节**——这是 V1→V2 唯一实质性的改动（见 §3）。

`M(p)` 是节拍重要性阶梯（`p = 绝对位置 mod 一拍`）：

| 位置 | 分值 |
|---|---|
| 拍头 | 0 |
| 8 分 | −0.05λ |
| 16 分 | −0.1λ |
| 32 分 | −0.2λ |
| 64 分 | −0.4λ |
| **8 分三连音（1/3、2/3 拍）** | **−0.05λ** |
| **16 分三连音（1/6、5/6 拍）** | **−0.1λ** |
| 其余 | −0.8λ |

`λ = 0.5 × 10^(simplicity/5)`，`simplicity ∈ [0,5]` 是力度滑杆。

> **阶梯只看到"拍"，不看到"小节"**（V2 明确写了 "There is no bar/measure
> awareness"）。4/4 下这与 V1 的"按小节判级"完全等价（小节头/半小节/拍头在拍级上
> 本来就有序）；2/4、6/8 下则不再借用 4/4 的小节位置。

> **三连音两档是本项目加的**（参考 V1/V2 都没有）——它们是三连音能被保住的前提，
> 见 §8。另外还有一条**单音位移上限**兜底，见 §9：没有它，DP 会"挑最好的档"
> 而不是"就近吸附"。

> **`simplicity=0` 不等于"不动"。** λ=0.5 时阶梯仍然生效，DP 依旧会拿位移去换强拍
> ——单音位移上限把这件事限制在 ±40 tick 以内（§9），所以只有本来就贴着强拍的音
> 会被吸过去，已经在网格上的音不会被整体推走。

### 2.4 DP

两张表：`s0[r][c]`（记录 r **从**列 c 开始的最优分）、`s1[r][c]`（记录 r **到**列 c
结束的最优分）。`s0` 的前驱唯一（链是头尾相接的），`s1` 在 j 带里取最大。
回溯从**末条记录的最优格**（V2：不再强制最后一列）开始；分数低于 `-1e9` 视为失败。

## 3. 相对参考实现 V1 的改动（★ 本次修的就是这一处）

| 改动 | 原因 |
|---|---|
| **距离按"一拍"归一**（V2） | V1 按"一小节"归一（4/4 下 = 4 拍）。位移代价因此被摊薄 **16 倍**（平方关系），节拍阶梯的 O(0.1~0.3) 落差彻底压过它：λ=0.5 时挪一个 16 分音符在 V1 下只花 0.0039，而"其余位置升到八分"值 0.3——**收益是代价的 77 倍**，DP 必然去换。于是**本来就在网格上的音也被整体推走**：`忘川风华录` 656 个音里 350 个被搬走、最大 **1 拍**；`光芒` 324/324 全部被搬。 |
| **网格步长 = 一拍 / 96**（本项目） | 见 §7。参考实现（V1/V2）的 `GRID = QUARTER/32` 是"一拍/32"；本项目早期更写成"**一小节**/32"（4/4 下 240、6/8 下 **180** tick），与模型 onset 的 60 tick 格子对不上，《相思》128/214 个音因此被搬 ≥180 tick。现在改成"一拍/96"：既与拍号无关，又把三连音族（一拍/3、一拍/6）包进网格。 |
| **三连音两档**（本项目） | 见 §8。参考实现的阶梯只认"一拍 / 2^k"，1/3 拍落在兜底 −0.8λ，于是三连音被当成"最差位置"吸到直线列上（《巴拉莱卡》479/569 被搬、三连音全被抹平）。 |
| **单音位移上限**（本项目） | 见 §9。参考实现只有 ±16 列的搜索带宽；位移代价（0.0009~0.014）与档位落差（0.025~0.2）不同量级，DP 会"挑最好的档"而不是"就近吸附"，把整条链拖走。 |
| **末条终点自由**（V2） | V1 把末条终点强制在 `round(总跨度/网格)`，收尾时长不整齐时会把压缩量摊回整条链。 |
| **阶梯按拍、不看小节**（V2） | 参考 V2 的语义；4/4 下与 V1 等价。 |
| **失败诊断 + 空窗口预检**（本项目） | 参考实现在某条记录的窗口为空时，那张 DP 表一次都不填，回溯可能给出**越界结果**。现在先挡掉空窗口，失败时明确报告死在第几条记录（`_why_failed`）。 |

其余逐位一致：`QUARTER = 705,600,000`、`GRID = QUARTER/32 = 22,050,000`（V2 的引擎网格）、
`BAND = 16`、`NEG_INF = -1e10`、`FAIL_THRESHOLD = -1e9`。
内部一律用这套定点标度算，所以 PPQ=1920 / 960 的结果严格成比例。
本项目的**量化网格**另取 `QUARTER/96`（见 §7），那是网格参数，不影响引擎常数。

> **常量名**：V1 把 705,600,000 叫 `BAR`（当成 4/4 的一小节），V2 改名 `QUARTER`
> 并明确它是**一拍**，同时把 `TICKS_PER_QUARTER` 从 `BAR/4` 改成 `QUARTER`。
> 本项目的 `BAR` 数值就等于 `QUARTER`（数值没变，所以"任意 PPQ → 内部标度"的换算
> 与老版本逐位相同），但内部一律按**一拍**理解；`BAR` 只保留为旧关键字别名。

## 4. 接口

```python
from sheetsage2_webui.quantize import smart_quantize_musical, quantize_tracks

# 低层：任意 PPQ。网格步长 = 一拍/96，与拍号无关。
result = smart_quantize_musical(
    [(0, 1960), (2000, 3900)], simplicity=0.0, ticks_per_quarter=1920)
result.ok, result.notes, result.moved, result.message

# 想放开位移上限（回到参考实现的行为，一般不要）
smart_quantize_musical(notes, ticks_per_quarter=1920, max_shift=None)

# 项目层：直接吃 project.json 的分轨音符
new_tracks, stats = quantize_tracks(
    project["tracks"], tick_length=project["timeline"]["tick_length"],
    simplicity=0.0, ticks_per_quarter=1920)
stats.as_dict()   # -> enabled / notes / moved / moved_ratio / failed_tracks / grid_ticks
```

`smart_quantize()` 上有四个分开的概念，别混：

| 参数 | 含义 |
|---|---|
| `beat` | **一拍**的 tick 数：阶梯 `M(p)` 的周期（"什么位置算强拍"） |
| `grid_divisor` | 网格分辨率：网格步长 = `beat / grid_divisor`，默认 **96 = 32 × 3** |
| `grid_span` | 另一种给网格的办法：`grid_span / grid_divisor`；默认 = `beat`（即"一拍"） |
| `max_shift` | **单音位移上限（列）**，默认 `MAX_SHIFT_COLS = 2`（40 tick）；`None` 关掉 |
| （归一） | 固定用 `TICKS_PER_QUARTER` 一拍，与上面三个都无关 |

正常路径上 `grid_divisor` 用默认 96、`grid_span` 用默认值，即
**网格步长 = 一拍 / 96**，**单音最多挪 40 tick**。这些参数暴露出来主要是给单测
造别的网格、以及需要"回到参考实现行为"时对照。

`bar_quarters` 参数**已经不用了**（`smart_quantize_musical` / `quantize_tracks`
都还接受它，但传什么值都不影响结果）——量化不看拍号。`stats.bar_quarters` 仍然写进
报告，纯粹是给老 `project.json` 读者留的记录字段。
`quantize.bar_quarters_from_timeline()` 也还在（`lyric_diagnose.py` 用它做展示）。

`stats.grid_ticks` = **一拍 / 96**（PPQ1920 → 20 tick）。`stats.placement_ticks` 是
它的兼容别名，两个数相同（早期版本里两者不同：一个记"一小节/32"、一个记"一拍/32"，
现在统一成同一个数）。

## 5. 接入流水线

`pipeline.run()` 默认开启量化（`quantize=True, simplicity=0.0`）：

- 量化**只动 tick**，小节表不动——小节表仍然是唯一时间真源，BPM 依旧不参与出谱（§前言第 1 条）。
- `project.json` 新增：
  - `quantize`：统计（音符数 / 移动数 / 网格步长 / 失败轨道 / 每条轨道的消息）
  - `quantize_shift_seconds`：`mean / median / p90 / max`（秒）
  - 每个音符上的 `raw_tick` / `raw_dur`（量化前的位置与时长，**填词对齐必须用它**，见 §6）
- `report.json` 新增 `quantize` 段，含同样的统计与位移。
- 量化后 `start_sec` / `end_sec` 会按新 tick 重算，保持工程自洽。
- 命令行：`--no-quantize` 关闭，`--simplicity 0~5` 调力度。
- **WebUI 参数面板上的「量化」**（`128 分三连网格 / 不量化`）就是这里的开关
  （`job.options.quantize` → `pipeline.run(quantize=…)`）；改它会让已扒的谱与歌词作废，
  因为谱面本身变了。`simplicity` 仍然只在命令行可调。

**已知粒度下限**：跨度不足半个网格列（20 tick / 2 = 10 tick）的单独音符判失败；
16 分音符（240 tick = 12 列）只要本来就在网格上就原样通过。

**改网格会让老工程作废**：`grid_ticks` 240 → 20，同一个 `raw_*` 重跑会得到更贴的落点。
WebUI 里改「量化」本来就会让已扒的谱与歌词退回待开始（`runner` 的既有逻辑），
所以从面板点一下就能重算；已经落盘的旧工程文件不会自动重算。

**端到端实测**（`tmp/e2e`，30s 切片真跑流水线，含下载 `.svp`）：

| 网格 | `quantize.grid_ticks` | 位移 mean/p90/max | 导出 `.svp` |
|---|---|---|---|
| 240 tick（旧） | 240 | 0.011 / 0.030 / 0.060s | 119 音，`adjust` 全 0 |
| **20 tick（现在）** | **20** | **0.011 / 0.030 / 0.060s** | 119 音，`adjust` 全 0 |

这一片上两个网格给出**逐 tick 相同**的结果——因为模型 30 秒切片里的 onset 本来就
落在 20 tick 的格子上，网格再细也不会多搬动它。**细化网格只在"本来就在细格子上"的
素材上起作用**（《相思》6/8 那 128 个音就是这种情况）。

## 6. 量化会破坏填词对齐 —— 所以必须留下 `raw_tick` / `raw_dur`

**这是实测出来的一个坑，改动了流水线语义。**

逐字时间戳（Qwen3-ForcedAligner）是沿着**模型自己的音符时间轴**产生的：小节表
（秒 ↔ tick）也是按模型音符算出来的。量化把音符 tick 吸到网格上之后，音符的**秒位置
就变了**（半个网格步长 + 节拍阶梯换来的位移，实测最大 0.86s），字号时间戳随之对不上。

实测影响（`scripts/check_pipeline_contract.py`，"看不到的字"= 同音挤占 + 间隙丢弃）：

| 歌曲 | 速度 | 字/音 | 量化前 | 量化后（无 raw_*） | 量化后（有 raw_*） |
|---|---|---|---|---|---|
| 《光芒》 | 恒速 104 | 1.00 | 29 | **60** | **29（完全恢复）** |
| 《相思》 | 恒速 100 | 0.95 | 18 | **42** | **18（完全恢复）** |
| 《巴拉莱卡》 | **变速 57.5 → 58.999** | 1.36 | 233 | **238** | **233（完全恢复）** |

变速曲这一行是关键：秒↔tick 是**分段线性**映射，而 `raw_tick` 记的就是模型小节表上的
原始位置，所以这个机制与曲式无关——恒速、变速都严格成立。

> **"看不到的字"的基准随曲式而变**，别把不同曲式的绝对值直接对比：字/音 ≈ 1.0 时约
> 9%，而《巴拉莱卡》是快嘴（600 字 / 441 音 = 1.36），基准约 39%。
> `scripts/check_pipeline_contract.py` 的判据是
> `占比 ≤ 12% + 80% × max(0, 字/音 − 1)`。

所以 `quantize.quantize_tracks()` 现在会把量化前的值一并写进音符：

```python
{"tick": 960, "dur": 1000, "pitch": 60,
 "raw_tick": 940, "raw_dur": 940}       # 量化前的位置与时长
```

而 `lyrics.note_spans_seconds()` **优先用 `raw_tick` / `raw_dur`** 做匹配，
没有这两个字段（老工程、没开量化）时退回 `tick` / `dur`。

**分层原则**（这也是"量化只动 tick"的延伸）：

- `tick` / `dur`：**导出用**，落网格、进 DAW。
- `raw_tick` / `raw_dur`：**对齐用**，是模型认定的真实演唱位置。
- 两者都不是"真值"，各管一件事；不要拿其中一个去替另一个。

### 对齐本身坏了的时候，填词指标没有意义

《皮囊》是反例：它对齐器只给出 360/430 个字的时间戳，而且第一个字在 **10.4s**、第二个字
直接跳到 **48.4s**（中间 37.9s 没有字），直接跑对齐器也能复现。这时"看不到的字 19.4%"
说明不了任何事——它只是把坏时间戳算成了间隙。

所以判据里会把这个数一起报出来：
`scripts/check_pipeline_contract.py` 在指标越界时会附上"最大空白 @ 第几个字"，
让人先分辨是**段落字比音多**（快嘴，正常）还是**对齐坏了**（不是填词的问题）。

`asr.py` 也会记录 `max_gap_seconds` / `max_gap_at` / `text_coverage` 并在超过 15s 时告警，
但**不做判定**——慢歌的长句之间本来就有 15s+ 的正常停顿（实测《相思》19.0s）。

## 7. 网格步长 = 一拍 / 96（本次落地）

### 7.1 为什么不是"一小节 / 32"

早期实现把网格步长写成"**一小节**的 1/32"。4/4 下这是 240 tick（32 分音符），
看起来没问题，但**拍号一变就错**：

| 拍号 | 一小节 | 一小节/32 | 一拍/32 | **一拍/96（现在）** |
|---|---|---|---|---|
| 4/4 | 4 拍 | 240 tick | 60 tick | **20 tick** |
| 2/4 | 2 拍 | 120 tick | 60 tick | **20 tick** |
| 6/8（`bar_quarters=3`） | 3 拍 | **180 tick** | 60 tick | **20 tick** |

模型给出来的 onset **本来就在 60 tick 的格子上**（实测：《相思》的 onset 全落在 60 的
倍数上，《旷古回响》也是）。4/4 下 240 是 60 的倍数，所以"粗一点"还能忍；6/8 下
180 **既不是 60 的倍数也不是 20 的倍数**，两者对不上——《相思》因此 128/214 个音被搬了
≥180 tick（均值 208.6 tick、最大 709 tick）。

所以：**网格步长与拍号无关**，只看一拍。`bar_quarters` 参数对量化完全不起作用
（只剩记录意义），`grid_ticks` 在**所有拍号上**都是 `PPQ / 96`。

### 7.2 为什么是 96 而不是 32

`32 = 2^5` 只能表示"一拍 / 2^k"的位置（960、480、240…），**表示不了三连音**：
一拍/3 = 640、一拍/6 = 320 都不是 60 的整数倍。`96 = 32 × 3` 把三连音族也包进来
（640 = 32×20、320 = 16×20）。PPQ1920 时步长 20 tick。

| 位置 | tick（@PPQ1920） | 一拍/32 = 60 | **一拍/96 = 20** |
|---|---|---|---|
| 拍头 / 8 分 / 16 分 / 32 分 | 0 / 960 / 480 / 240 | ✅ | ✅ |
| 64 分 | 120 | ❌ | ✅ |
| **1/6 拍（十六分三连音）** | **320** | ❌ | **✅** |
| **1/3 拍（八分三连音）** | **640** | ❌ | **✅** |

`reference/Vocal2Midi V2` 用的是"一拍/32"。本项目在网格上走得更细一档，
**网格与阶梯都按两条支线分开**：直线支是 1/2^k，三连音支是 1/(3·2^k)。
本项目取 1/96 拍（两支的交点）作网格，并给三连音位置单独分档——见 §8、§9。

**效果**（`scripts/quantize_real_check.py`）：

| 工程 | 口径 | 均值 | 最大 | 位移 ≥ 一个网格步 |
|---|---|---|---|---|
| 相思（6/8，214 音） | 一小节/32（180 tick） | 208.6 tick | 709 tick | **128/214** |
| 相思（6/8，214 音） | **一拍/96（20 tick）** | **2.0 tick** | **10 tick** | 48/214（按 20 tick 衡量） |
| 全部 26 轨 / 6927 音 | 一拍/96 | — | — | 656（9.5%） |

> 注意"位移 ≥ 一个网格步"这个计数**随网格步长而变**：网格细了四倍，同一个物理位移
> 更容易超过一格。所以这一列不能跨口径比较——要比就比**均值/最大（秒）**。
> 用 20 tick 去衡量 V1，《忘川》单独一条就是 350/656。

### 7.3 为什么不是更粗的网格（与 Synthesizer V 的 SNAP 对齐）

[Synthesizer V 的 SNAP 菜单](https://svstudio.tech/) 是这套网格的**权威词表**，
它把两条支线分开列：

| SynthV 菜单 | = 一拍 × | tick（@PPQ1920） |
|---|---|---|
| 四分音符 | 1/1 | 1920 |
| 1/2 个四分音符（8 分音符） | 1/2 | 960 |
| 1/4 个四分音符（16 分音符） | 1/4 | 480 |
| **1/6 个四分音符（16 分三连音）** | 1/6 | 320 |
| 1/8 个四分音符（32 分音符） | 1/8 | 240 |
| **1/12 个四分音符（32 分三连音）** | 1/12 | **160** |
| 1/16 个四分音符（64 分音符） | 1/16 | 120 |
| **1/24 个四分音符（64 分三连音）** | 1/24 | **80** |
| 1/32 个四分音符（128 分音符） | 1/32 | 60 |
| **本项目：一拍 / 96** | 1/96 | **20**（= 64 分三连音的再 4 等分） |

要点：

- **直线支是 1/2^k，三连音支是 1/(3·2^k)**——两支混在一起就是"1/96"这一族
  （96 = 32 × 3 = 32 × 3）。**只用 2 的幂的网格永远表示不了三连音**。
- 实测过更粗的网格（同样用单音位移上限 2 列）：**一拍/48（40 tick）不行**——
  直线 32 分跑动会被拖动 80 tick；**一拍/24（80 tick）更不行**——直线 16 分也会被拖 160 tick。
  因为 32 分位（240 tick）在 40 / 80 的网格上都**不是整列**，DP 只能把它挪到最近的列上。
  20 tick 能整除 240（12 列）、320（16 列）、480（24 列）、640（32 列）、960（48 列）、
  1920（96 列）——**所有真实位置都是整列**，这才是判据能全过的原因。
- 常用工作网格 1/12 拍（160 tick）正好是 8 列，所以本项目的网格是它的**合法细分**。

### 7.4 代价

- **导出分辨率变细**：`grid_ticks` 240 → 20。落盘/SVP/MIDI 的 tick 可以细到"一拍的 1/96"。
  SVP 是 480 PPQ，20 ÷ 4 = 5，整数，**无精度损失**。
- **面板文案**改为「**128 分三连网格**」（`web/src/params.ts`、`webui/jobs.py`、
  `runner.QUANTIZE_LABEL`）；`runner.grid_note_name()` 也换成 SynthV 的词表（见 §7.3）。
- **老工程不自动重算**：同一个 `raw_*` 重跑会得到更贴的落点。WebUI 里改「量化」
  本来就会让已扒的谱与歌词退回待开始，点一下即可重算。

## 8. 阶梯要认三连音（本次落地）

只有网格还不够：**阶梯必须也给三连音位置分档**。

原来的 `metric_bonus` 只认"一拍 / 2^k"，于是 1/3 拍（640）与 1/6 拍（320）都落在
兜底的 −0.8λ。DP 眼里它们就是"最差的位置"——挪到最近的直线列只要 0.0009~0.0035
的位移代价，却能换到 −0.05λ 以上，**收益压倒代价**。

实测（去掉三连音档、其余保持现状）：

| 样本 | 结果 |
|---|---|
| `巴拉莱卡（The Rod）.mid`（569 音，三连音为主 + 四分） | **479 个被搬走**；126 个 1/3 拍 + 167 个 2/3 拍**全部**被吸到 3/8 / 3/4 上 |
| `皮囊.mid`（420 音） | 198 个三连音位里**只有 1 个**留在原地 |

现在的阶梯（与 §7 的网格配套）：

| 位置 | tick | M(p) |
|---|---|---|
| 拍头 | 0 | 0 |
| 8 分 | 960 | −0.05λ |
| **8 分三连音（1/3、2/3 拍）** | **640 / 1280** | **−0.05λ** |
| 16 分 | 480 | −0.1λ |
| **16 分三连音（1/6、5/6 拍）** | **320 / 1600** | **−0.1λ** |
| 32 分 | 240 | −0.2λ |
| 64 分 | 120 | −0.4λ |
| 其余 | — | −0.8λ |

即**三连音位置与对应的直线位置同级**：1/3 拍 ↔ 8 分、1/6 拍 ↔ 16 分。

加上之后：

| 样本 | 结果 |
|---|---|
| `巴拉莱卡（The Rod）.mid` | **567/569 原样通过**，最大位移 40 tick（= 单音上限） |
| `皮囊.mid` | **420/420 原样通过**（一个都不动） |

## 9. 单音位移上限（本次落地，★ 也是最关键的一条）

光有网格 + 三连音档还不够：DP 会**为了让音升一档而跨过整个 1/3 拍**，
把整条链一起拖走。根因是位移代价与档位落差**不同量级**：

| | 量级 |
|---|---|
| 位移代价 `0.5·(d/一拍)²` | 挪 80 tick = 0.00087；挪 160 tick = 0.0035；挪 320 tick = 0.0139 |
| 档位落差 | 0.05λ ~ 0.4λ（λ=0.5 时 0.025 ~ 0.2） |

于是 DP 实际在做"**挑最好的档**"而不是"**就近吸附**"：只要挪得动，它就去挪。

参考实现（V1/V2）没有位移上限，只有 `BAND = ±16 列`——在它们"一拍/32"（60 tick）
的网格上是 ±960 tick，在我们的细网格上等于**没有约束**。

**修法**：给每一列再套一层"不许离开原始列超过 `MAX_SHIFT_COLS` 列"的硬窗口。

### 怎么定的这个数

**实测真实音频的 onset 误差，不需要大位移**：把 `output/` 里 10 个工程的
`raw_tick`（= 量化前的模型输出）量一下"到最近 20 tick 网格点的距离"：

| 分位 | 距离 |
|---|---|
| p50 | 0 tick |
| p75 | 4 tick |
| p90 | 8 tick |
| p99 | 9 tick |
| **p100** | **10 tick** |

**6927 个音里没有一个超过 40 tick**（= `MAX_SHIFT_COLS = 2`）。所以 40 tick
对真实数据是 4 倍余量；而它小于"32 分位 → 1/6 拍"的 80 tick，也就挡住了跨族乱跑。

### 效果（`scripts/quantize_real_check.py`，26 轨 / 6927 音）

| 单音上限 | 平均位移 | 最大位移 | 位移 ≥ 一格 |
|---|---|---|---|
| 无上限（= 参考实现行为） | 33.5 tick | 295 tick | 1725 (24.9%) |
| ±4 列（80 tick） | 6.9 tick | 99 tick | 663 (9.6%) |
| **±2 列（40 tick，现在）** | **6.3 tick** | **59 tick** | **656 (9.5%)** |

按秒看（`quantize_shift_seconds`）：平均 **0.004s**、p90 **0.014s**、最大 **0.028s**，
26 条轨道**0 失败**、网格率 **100%**。

配套判据（`tests/test_quantize.py`）：

- `test_clip_criteria_straight_and_triplet_grids_pass_through_unchanged`：
  直线 8/16/32 分与三连音音型**全部原样通过**。
- `test_max_shift_cap_is_what_keeps_the_clip_criteria`：把上限关掉，同样的素材
  立刻被搬走——证明这条上限是必需的，不是装饰。

## 11. 踩过的坑：别用 PowerShell 改这些文件

改 `web/src/params.ts` / `webui/jobs.py` / `web/smoke.mjs` / `web/test/params.test.ts`
这类**含中文**的文件时，**不要**用
`Get-Content -Raw | Set-Content -Encoding UTF8`：

Windows PowerShell 5.1 的 `Set-Content -Encoding UTF8` 会按**系统 ANSI 代码页**
（中文机器上是 GBK）编解码，结果是整个文件的中文变成 mojibake，而且
GBK 里映射不到的字符（`—`、`→`、✅ 等）**被写成 `?`，不可逆**。

正确做法：用 `edit` / `write` 工具，或用 Python 的
`Path.read_text(encoding="utf-8")` + `write_text(..., encoding="utf-8")`。

补救路径（本次真用过）：`dist/SheetSage2-Studio-alpha1/` 里有一份打包快照，
可以先还原再用 Python 重新施加改动。纯 mojibake（没有 `?`）还能用
`line.encode("gb18030").decode("utf-8")` 逆转回来，但含 `?` 的行救不回。
