# 模块化拆分与重构计划

> 状态：计划稿，尚未开始重构。  
> 适用基线：`beta` 分支；制定日期：2026-11-13。  
> 核心原则：按职责和依赖边界拆分，控制单文件规模，同时保持现有产品行为、数据格式和调用契约。

## 1. 目标与判断

本计划针对本项目自有代码中职责过多、文件过大的部分，逐步提升内聚性、降低模块间耦合，并让运行时代码单文件尽量低于 1000 行。行数是提醒进一步审视职责的指标，不是要求把逻辑机械切碎的硬指标。

项目已有可复用的分层：算法模块大多各自负责明确领域，Web 前端已有 Vue 组件、composable、API、类型和单元测试。因此重构重点不是全面改写，而是把少数承担过多职责的边界拆清楚，并保持旧入口兼容。

本计划估算完整范围约 **10～16 人日**。若只完成后端 `jobs.py`，预计约 **2～4 人日**；实际工期取决于测试基线、历史兼容要求和重构中发现的耦合程度。估算不含新功能开发、重大产品行为变更或模型算法调整。

## 2. 范围与明确排除项

### 纳入范围

- `src/sheetsage2_webui/webui/jobs.py`：首要拆分对象，当前约 2016 行。
- `src/sheetsage2_webui/webui/app.py`：后续按路由职责拆分，当前约 696 行。
- `src/sheetsage2_webui/webui/runner.py`：评估阶段执行职责，当前约 747 行。
- `web/src/composables/useStudio.ts`：按前端状态与副作用职责拆分，当前约 650 行。
- `web/src/styles.css`：按样式职责拆分，当前约 1347 行。
- `tests/test_webui.py`：按被测职责拆分，当前约 1413 行。
- 其他本项目自有运行时代码：如重构时发现职责明显混杂，再按相同原则纳入，不为行数指标预防性拆分内聚的算法文件。

### 保持原样或另行决策

- `src/sheetsage2_webui/vendor/tifa/`：**整体保持上游目录和文件组织，不拆分、不重命名、不做本项目风格改写**，避免与上游产生无谓差异。若将来确需修改，另行记录上游来源、差异和同步策略。
- `web/package-lock.json`：生成的依赖锁文件，不手工拆分。
- `src/sheetsage2_webui/webui/static/`、`dist/` 等构建产物：通过构建生成，不按源码模块化标准拆分。
- 文档、调研记录、静态页面原型：不受运行时代码千行目标约束。未跟踪的 `编辑页.html` 是否纳入正式产品或归档，应在实施前单独确认其用途，不混入本轮重构。
- `asr.py`、`tempo.py`、`lyrics.py` 等算法文件：目前虽有数百行，但主要职责相对集中；除非基线测试或依赖分析显示边界问题，不单纯因为文件较长而拆分。

## 3. 设计约束

1. **行为不变优先。** 任务状态迁移、SSE 事件顺序与续传、上传校验、输出目录、metadata/manifest、备份兼容和 API JSON 形状都属于现有契约。
2. **保留兼容入口。** 初期保留 `webui.jobs` 中已有的公开类、常量和函数导出；调用方逐步迁移，确认无外部依赖后再考虑删除旧转发。
3. **依赖方向单向。** 值对象和纯函数不依赖调度器或 FastAPI；存储逻辑不直接管理工作线程；路由通过依赖注入使用服务；前端展示组件不自行复制全局作业状态。
4. **小步迁移。** 每个阶段只移动一类职责，并在该阶段通过对应测试后再继续。并发、文件恢复和历史数据等高风险逻辑最后迁移。
5. **模块边界以变化原因为准。** 一个模块尽量只有一类主要变化原因；避免仅按“每个文件 300 行”切分，也避免新模块之间互相导入形成循环依赖。
6. **TIFA 仅通过外围调用。** 本轮不动 vendor 实现。项目自己的 ASR/对齐代码继续负责配置、调用和结果转换；只有出现清晰的重复适配逻辑时，才在 vendor 外新增薄适配模块。

## 4. 建议目标结构

以下是目标职责示意，不要求一次性新增所有文件。实施时应先核对实际调用关系和测试夹具，再确定最终命名。

```text

  job_models.py           # Job、StageRun、Event、Progress 等领域对象与状态
  job_options.py          # 参数规格、默认值、校验和展示辅助函数
  job_files.py            # 上传流、音频校验、文件扫描、指纹和安全文件名

  job_scheduler.py        # 队列、worker、阶段执行、取消、超时和看门狗
  job_trash.py            # 软删除、恢复、永久删除和回收站清理
  backup.py               # 备份归档校验与读写（优先复用现有模块）
  routes/
    __init__.py
    jobs.py                # 工程、阶段、选项与 SSE 路由
    media.py               # 音频、波形和卷帘数据路由
    exports.py             # SVP、单文件与整包下载
    system.py              # 环境预检、诊断与备份路由
  app.py                   # FastAPI 应用创建、生命周期、依赖与路由注册
  runner.py                # 保持 RunnerSession 门面；内部阶段按需下沉

web/src/
  composables/
    useStudio.ts            # 兼容门面/组合入口，按迁移情况保留
    useJobs.ts              # 作业列表、当前作业和快照刷新
    useJobEvents.ts         # SSE 订阅、重连、事件去重与进度补丁
    useUploads.ts           # 文件拖放、上传和上传进度
    useTrashBackup.ts       # 回收站和备份/恢复状态
  styles/
    tokens.css              # 颜色、间距、尺寸和基础变量
    base.css                # 全局基础与排版
    layout.css              # 页面、侧栏和主要布局
    components.css          # 对话框、阶段卡、按钮等组件样式

  styles.css                # CSS 聚合入口，按稳定顺序导入

tests/

  test_webui_jobs.py
  test_webui_storage.py

  test_webui_routes.py
```

后端目标模块通常控制在约 200～700 行，复杂协调模块允许更大；本项目自有运行时代码以 800 行作为主动复查线，避免刚好低于 1000 行后又迅速超限。测试按职责拆分，方便定位和维护，不要求每个测试文件都采用相同大小。

## 5. 后端拆分策略

### 5.1 `jobs.py` 的职责边界

现有 `jobs.py` 同时承载参数定义、领域对象、上传与文件处理、工程恢复、队列调度、阶段运行、看门狗、产物门禁、回收站、备份和诊断。建议按以下顺序迁移：

1. **参数与纯函数**：先迁移参数规格、默认值、校验、标签转换、文件名和格式化等低副作用代码。
2. **领域对象**：迁移 `Event`、`StageRun`、`Job` 等数据结构及其序列化。`Progress` 若依赖队列取消检查，应通过窄接口或回调调用，避免领域对象导入整个 manager。
3. **文件与存储**：迁移上传、扫描、项目恢复/导入、metadata、manifest、阶段产物隔离和清理。文件写入继续复用原子写工具。
4. **回收站与备份**：将回收、恢复、永久清理与归档备份职责从 manager 中移出；复用现有 `backup.py` 的归档校验。
5. **调度与阶段生命周期**：最后迁移 worker、队列、阶段启动/完成、取消、看门狗和超时。调度器应通过 runner、存储和事件接口协作，不直接承接路由层逻辑。
6. **收敛门面**：`jobs.py` 负责构造并连接组件，维持已有 `JobManager` 行为和兼容导入；确认依赖稳定后再决定是否需要更换门面名称。

拆分期间重点审视 `JobManager` 的状态所有权。不要把同一个可变状态同时放在 manager、scheduler 和 repository 中；由单一组件负责状态迁移，其他组件接收明确命令或返回结果。

### 5.2 `app.py` 与 `runner.py`

`app.py` 后续拆为 FastAPI router，并由应用工厂统一注册。路由依赖通过明确的依赖对象取得 `JobManager`、runner、媒体缓存和配置；避免 router 模块在导入时创建线程、加载模型或访问用户数据目录。

`runner.py` 保留稳定的 `RunnerSession` 接口。若拆分，按扒谱阶段、歌词阶段和产物检查等职责下沉，并确保线程取消检查、进度事件和异常翻译保持原有语义。项目对 TIFA 的任何适配仍留在 vendor 外部。

## 6. 前端拆分策略

### `useStudio.ts`

把状态来源和副作用按职责拆分。作业快照与事件订阅只能有一个明确所有者；组件通过 composable 暴露的只读状态和动作交互。迁移过程中可由 `useStudio.ts` 聚合多个 composable，保持 `App.vue` 的现有调用接口，避免一次改写所有组件。

SSE 迁移需保持事件序号续传、旧事件过滤、进度只增不减、新运行归零、断线重连和页面卸载清理。上传、回收站和备份各自维护请求状态，但不应复制作业领域状态。

### `styles.css`

按视觉职责拆分，保留明确且固定的导入顺序。拆分前记录重复选择器、变量定义和媒体查询位置；拆分后检查级联覆盖顺序，保证最终产物与原样式一致。颜色/尺寸令牌集中管理，组件样式避免无必要的全局选择器。

## 7. 测试拆分与行为基线

测试重组不应改变测试断言的含义。先识别 `tests/test_webui.py` 中的 fixtures、临时目录、假 runner 和并发辅助函数，再决定抽到 `conftest.py` 还是测试支持模块；避免 `conftest.py` 变成新的大杂烩。

计划覆盖的关键行为：

- 作业状态迁移、排队顺序、单 worker 约束、取消与阶段超时；
- SSE `seq` 单调递增、断线后 `since` 补发、事件容量边界；
- 参数校验、上传大小/类型/内容、同名文件与并发创建；
- 旧工程恢复、导入产物、metadata/manifest 和失败重跑隔离；
- 回收站恢复、期限/容量清理、永久删除；
- 备份 zip-slip 防护、备份恢复和诊断包；
- FastAPI 路由的状态码、响应 JSON 和下载行为；
- 前端状态更新、SSE 补丁、上传拆分、回收站动作和 API 契约；
- CSS 构建和关键页面冒烟。

## 9. 验证命令与完成标准

执行时先以仓库 `docs/开发指南.md` 为准确认环境和命令。当前建议验证层次如下：

```powershell
# Python 单元与 WebUI 测试
.\.venv\Scripts\pytest.exe tests

# 前端检查、测试和生产构建
cd web
npm run typecheck
npm test
npm run build
npm run smoke
npm run smoke:pianoroll
```

涉及安装包或静态资源路径的变更，再运行相应打包/验证脚本。涉及模型推理的端到端验证作为单独、明确的验证步骤，不要求每个小阶段都重复下载或加载模型。

重构完成需满足：

- 既有 API、SSE、文件格式和任务状态行为保持兼容，或经单独批准记录行为变更；
- Python 测试、前端 typecheck/test/build 和相关 smoke 检查通过；
- 项目自有运行时文件不再因多职责而超过 1000 行，若个别文件超过则在文档中说明职责集中且拆分会损害内聚性的理由；
- `vendor/tifa/` 没有本轮引入的结构或格式变更；
- 新模块没有循环依赖、重复状态所有权或导入时副作用；
- `git diff` 确认构建产物、缓存、模型文件和用户数据未被意外纳入。

## 10. 风险与控制

| 风险 | 影响 | 控制措施 |
|---|---|---|
| `jobs.py` 的 manager 同时管理可变状态与线程 | 状态竞争、重复启动、取消语义变化 | 先明确状态所有权；调度部分最后拆；用确定性 fake runner 和并发测试覆盖 |
| SSE 事件由多个路径共同写入 | 前端丢事件、重复事件或进度回退 | 固定单一事件写入入口；保留序号和续传契约测试 |
| 工程恢复与清理直接操作磁盘 | 旧数据不可恢复或半成品被识别为完成 | 先固定目录/manifest 行为；使用临时目录测试原子性和失败恢复 |
| FastAPI 路由拆分产生循环依赖或导入副作用 | 服务启动失败或启动时提前创建资源 | 应用工厂集中组装依赖；router 只定义路由，不在模块导入时启动 worker |
| CSS 文件拆分改变级联顺序 | 页面出现细微布局/颜色回归 | 固定导入顺序；在合并前比较关键页面和生产构建样式 |
| 为达行数目标过度切分 | 文件变小但跨模块跳转和耦合增加 | 行数只作复查线；按变化原因、依赖方向和单一状态所有权验收 |
| TIFA vendor 与本地改动混淆 | 后续同步上游困难 | 明确排除 vendor；复核最终 diff，任何 vendor 变更单独处理 |

## 11. 开始实施前的工作区要求

制定本计划时，本地 `beta` 提交与 `origin/beta` 一致，但工作区存在已修改和未跟踪内容。开始实施前应先核实这些内容的归属，并确保重构提交只包含计划范围内的文件；不要覆盖或清理用户现有工作。

本计划本身只定义拆分方案和验收标准，不代表已开始代码改造。实际开始时按阶段提交，每个阶段可独立审阅、回滚和验证。
