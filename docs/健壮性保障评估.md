# 健壮性保障评估：一个不懂技术的用户，哪里会被这个程序坑到

> 评估对象：SheetSage2 Studio 本地 WebUI（V2）
> 评估方式：只读代码 + 已有文档交叉核对，不加载模型、不改代码。
> 结论按**用户会承受的后果**分级，不按实现难度分级：
> **P0 = 丢数据 / 给出错结果 / 永久卡住**，P1 = 会让人懵或用不下去，P2 = 体验毛刺。
>
> 相关文档：`docs/WebUI规格.md`（实现规格）、`docs/WebUI问题清单.md`（已修问题流水账）、
> `docs/打包分发待办.md`（分发与首次安装）。

---

## 0. 一句话结论

这个项目的**功能正确性**保障做得相当扎实（BPM 交叉校验、量化口径、八度修正、SVP 往返自洽，
每条都有真机数字），**安装层的幂等**也做对了（`tools/bootstrap.py` 六步幂等 + 续传 + sha256）。

但它是按"开发者自己会用"的样子长的，**"状态一致性 + 崩溃恢复 + 用人话报错"这三层是薄的**：

| 层 | 现状 | 缺口 |
|---|---|---|
| 功能正确性（谱面本身对不对） | ✅ 强 | 没有"完成门禁"：半成品也会被标成完成 |
| 单机幂等（重跑 / 重试 / 重复上传） | 🟡 一半 | 重跑之后**旧产物与缓存不失效**，用户会下到上一版 |
| 并发（线程 / 双开 / 双标签页） | 🟡 一半 | 进程内设计干净，**跨进程完全没有保护**（双开必踩） |
| 崩溃恢复 | 🟡 一半 | 会正确标记"上次被中断"，**残留半截文件不清理** |
| 长任务守护（僵尸/卡死） | 🔴 缺 | 无超时、无心跳、无看门狗，卡住就是永远转圈 |
| 报错可读性 | 🔴 缺 | 用户看到的是 `RuntimeError:` 加英文原文 |
| 数据安全 | 🔴 缺 | 删除按钮**无二次确认**，直接递归删目录 |

下面先还原工作流程，再逐条给结论与修法。

## 1. 这个项目的工作流程（保障措施要挂在哪些点上）

### 1.1 进程与线程模型

```
webui.bat ──> scripts/launch.py
                 │  ① 自检解释器   ② 前端产物缺失就 npm build
                 │  ③ 挑端口（首选 8000，被占就换随机口，scripts/launch.py:87）
                 ▼
        python -m sheetsage2_webui.webui        （一个 uvicorn 进程）
                 │
                 ├─ 请求协程：读快照 / 打包 / 算波形 / 导 SVP（run_in_threadpool）
                 └─ JobManager：**一个**工作线程，按队列顺序跑阶段（jobs.py:610/807）
                        └─ runner.py：transcribe（SheetSage2）/ lyrics（Qwen3-ASR）
```

- **并发设计是对的**：GPU 只有一块，`workers` 默认 1，任务在队列里排队（`jobs.py:635`）。
- **模型按需加载、阶段间释放**：切到歌词阶段前把 SheetSage2 放掉（`runner.py:433`），
  换模型/换精度会重载（`runner.py:194`）。
- **所有队列、任务状态都只在内存里**（`JobManager._jobs`），磁盘上只有 `job.json` 快照。

### 1.2 一次任务的完整链路

| # | 用户动作 | 后端 | 磁盘变化 | 失败会怎样 |
|---|---|---|---|---|
| 1 | 拖入音频 | `POST /api/jobs` → `manager.create`（`jobs.py:836`） | `output/<歌名>/.webui/input/<音频>` + `job.json` | 后缀/大小/空文件被拒（400），半截文件删掉 |
| 2 | 选参数 | `PATCH /options`（`jobs.py:948`） | 无（只改 `job.json`） | 怪值 400，阶段在跑 409 |
| 3 | 点「开始扒谱」 | `run_stage` → 队列（`jobs.py:884`） | `job.json` 状态 → queued | 只读工程 409 |
| 4 | 扒谱 | `pipeline.run` 写 ~30 个产物（`pipeline.py:443`） | `project.json` / `report.json` / `summary.json` / `*.lab` / `*.mid` | 异常 → 阶段 failed，**产物残留不清** |
| 5 | 点「开始识别歌词」 | 需 `transcribe.state == done`，否则 409 | — | 前端同一句话（`web/src/stageActions.ts`） |
| 6 | 歌词识别 | 切片 → ASR → 对齐 → 填词（`runner.py:391`） | `project.json` 重写 + `lyrics.json` | 无逐字时间戳 → 明确报错 |
| 7 | 下载 | zip 走 `manager.bundle`（`jobs.py:1134`）/ SVP 走 `svp.build_svp`（`app.py:505`） | `.webui/bundle.zip`、`.webui/export/*.svp` **缓存** | 见 G3 |
| 8 | 重启服务 | `_load_existing` 扫描 `output/`（`jobs.py:649`） | 上次 `running/queued` → `idle` + "上次运行被中断" | 残留半截文件不检查，见 G5 |

### 1.3 状态机（现在长这样）

```
job:   draft ──(点开始)──> queued ──> running ──> done | failed | cancelled
         ▲                                │
         └──── 参数/音源改变（作废旧结果）──┘

stage: idle ─> queued ─> running ─> done | failed | cancelled | skipped
```

**关键点：作废只发生在内存里**（`_invalidate_transcribe` / `_invalidate_lyrics`，
`jobs.py:1070-1089` 只是把 `StageRun` 换成一个新对象），**磁盘上的旧产物一个字节都没动**。
这是 G3 / G4 / G5 的共同根因。

### 1.4 磁盘契约

```
output/<歌名>/                      ← 工程目录 = 产物目录（和 CLI 同构）
├─ project.json report.json summary.json *.lab *.mid *.abc   ← 产物（30 个）
├─ job.json                        ← WebUI 元数据（不是产物）
└─ .webui/
   ├─ input/<原音频>
   ├─ stems/vocal/<干声>
   ├─ peaks-mix-1200.json peaks-stem-1200.json   ← 波形缓存
   ├─ export/<sha1>.svp                           ← SVP 缓存
   └─ bundle.zip                                  ← 整包缓存
```

### 1.5 谁会出错（失败面）

| 失败源 | 现在有没有拦住 | 用户看到什么 |
|---|---|---|
| 用户传了个不是音频的文件（改了后缀） | 只查后缀（`jobs.py:308`） | 几十秒后 ffmpeg 报错 |
| 文件能解码但不是歌（纯静音 / 讲话录音） | ❌ | "识别完了"，产物全是垃圾 |
| 显存不够 | ⚠️ 自动退 CPU（`engine.py:223`） | 界面写"识别音乐"，实际要跑几小时（G17） |
| 磁盘满了 | ❌ 无预检 | 写到一半 `OSError`，产物残缺 |
| 推理卡死（驱动/CUDA 挂住） | ❌ 无超时 | 进度条永远停在 62%（G6） |
| 用户手滑点了删除 | ❌ 无确认（`web/src/App.vue:153`） | 目录被递归删掉，**不可恢复**（G2） |
| 双击了两次 `webui.bat` | ❌ 无单实例锁 | 两个服务同时往 `output/` 里写（G1） |

## 2. 评估框架：一个"小白向"的本地 AI 工具该有哪些保障

按优先级从高到低，一共七层。每层下面的条目就是第 3、4 节要对照的东西。

| 层 | 要回答的问题 | 典型手段 |
|---|---|---|
| **L1 数据安全** | 会不会把用户的东西弄丢？ | 删除二次确认 / 软删除（回收站）/ 不覆盖 / 路径隔离 |
| **L2 结果可信** | 用户拿到的到底是不是"这一次"的结果？ | 产物版本与失效 / 完成门禁（写完才标 done）/ 自检报告 |
| **L3 一致性** | 崩溃、断电、双击、双标签页之后还自洽吗？ | 原子写（.part + rename）/ 单实例锁 / 产物清单 / 孤儿清理 |
| **L4 幂等** | 重复点、重跑、重试会不会叠加副作用？ | 幂等键、状态门禁、缓存失效、去重 |
| **L5 守护** | 卡住了谁发现？ | 阶段超时 / 心跳 / 看门狗 / 僵尸标记 / 一键中止 |
| **L6 可诊断** | 出事了用户能提供什么？ | 落盘日志 / 诊断包 / 错误码 / 一键复制 |
| **L7 可理解** | 用户看得懂吗？ | 人话错误 + 下一步建议 / 预检横幅 / 预计耗时 |

对照下来：**L1、L2、L3、L5、L6、L7 都有明显缺失，L4 缺一半**。

## 4. 缺口清单（P0：会丢数据 / 给错结果 / 永久卡住）

### G1 · 双击两次就双开，两个进程互相踩 🟥P0

**现象**：`webui.bat` 没有任何单实例检查。两次双击 → `launch.py` 的 `pick_port` 发现 8000
被占（`scripts/launch.py:87`），**换个随机端口再起一个服务** —— 看起来"一切正常"，
实际是两个 uvicorn + 两个 JobManager 盯同一个 `output/` 目录。

**用户会怎么撞上**：第一次双击没反应（窗口被挡住/浏览器没弹），再双击一次。
这是小白最常见的操作。

**后果**（按严重度）：
1. 两个进程**都会**扫描 `output/` 并恢复出**同一批 project id**（id 来自目录名/`job.json`）；
2. 同一个工程在 A 窗口跑扒谱、在 B 窗口跑歌词 → 两套 writer 写同一个 `project.json`；
3. 两个进程各有自己的 `_jobs` 内存状态，界面上"我这边显示完成了，那边显示在跑"；
4. 两个进程同时加载 torch 模型 → 显存翻倍，直接 OOM（`engine.py` 会退 CPU，然后再跑一遍）；
5. 更糟：A 窗口删除工程 → 删的是 B 窗口正在写的目录。

**根因**：进程级没有互斥（`grep` 全项目没有 `msvcrt.locking` / 端口文件 / PID 文件）。

**建议**（改 `scripts/launch.py` + `__main__.py`，约 80 行）：
- 数据根下放 `<数据根>/.webui.lock`（JSON：`pid`、`port`、`started_at`、`exe`）。
  起服务前用 `msvcrt.locking(fd, LK_NBLCK, 1)` 独占加锁；拿不到锁就**读锁里的 port 直接开浏览器**
  （"已经有一个在跑了，帮你打开了 → http://127.0.0.1:8xxx"），然后 `exit 0`。
- 进程退出（含异常）时删锁；锁文件残留时用 `pid` 是否存活兜底（`psutil.pid_exists` 已在依赖里）。
- `webui.bat` 侧再把"已经开过了"这句话打出来（中文都在 `launch.py` 里）。

**验收**：连点两次 `webui.bat` → 只起一个服务、浏览器只开一个标签；第二个进程退出码 0 并说明原因；
新增 `tests/test_singleton.py`（可以只测锁函数，不真起服务）。

### G2 · 删除按钮没有二次确认，直接递归删工程目录 🟥P0

**现象**：`ProjectHead.vue:29` 的「删除」和侧栏 `AppSidebar.vue:87` 的 `×` 都是**单击即删**，
`App.vue:153` 直接 `remove(active.id)` → `manager.delete` → `shutil.rmtree(job.root)`
（`jobs.py:1130`）。没有确认框、没有回收站、没有撤销。

**用户会怎么撞上**：想点「下载 ▾」或「新建工程」，手指偏了 20 像素。

**后果**：几小时的扒谱 + 歌词 + 手改的参数，**一次误点全没**，且无法恢复
（`.webui/input` 里的原音频也一起没了，用户还得回头找歌）。

**建议**（两层，都要做）：
1. **前端**：`confirm` 换成项目自己的确认弹层，文案带上"这将删除 N 个产物 / 原音频，
   不可恢复"，且要求点满 1 秒才可点确认（防连点）。
2. **后端**：`delete()` 改成**软删除** —— 目录 `rename` 到 `<数据根>/.trash/<id>-<时间戳>/`，
   `/api/trash` 列表 + "恢复"/"彻底删除"；`.trash` 超过 7 天或超 2GB 再真删。
   `rename` 是原子的，且立刻把工程从列表里去掉，用户感知和"删了"一样。
3. 顺带：`delete` 期间**不释放** `job.lock` 之外的任何东西；已在 `running` 时拒绝（现有行为保持）。

**验收**：误删后能在"回收站"里一键恢复；`tests/test_webui.py` 增补"删除→恢复→产物仍在"。

### G3 · 重跑之后，下载到的还是上一版（缓存永不失效） 🟥P0

**现象**：三处缓存都是"文件在就直接返回"，**键里没有产物版本**：

| 缓存 | 位置 | 键 | 何时会脏 |
|---|---|---|---|
| 整包 zip | `jobs.py:1140-1142` | 只有路径 `bundle.zip` | **任何一次重跑** |
| SVP | `svp.cache_key`（`svp.py:553`） | `parts + version + EXPORT_REVISION + language` | **任何一次重跑** |
| 波形（干声） | `media.peaks_for`（`media.py:86-100`） | `peaks-stem-<buckets>.json` | **换干声**（`attach_stem` 删了旧音频、没删旧缓存） |

`job.rev` 在重跑扒谱时确实 +1（`jobs.py:920`），但**没有任何缓存读它**，界面上只拿它当
"rev N" 显示（`ProjectHead.vue:23`）。

**用户会怎么撞上**：参数选错 → 重跑 → 点「下载 SVP」→ 拿到的还是旧参数那一版。
他没有任何办法看出来，直到把 SVP 拖进 SynthV 发现音高/歌词不对。

**根因**：作废只发生在内存（`_invalidate_lyrics`、`jobs.py:1082`），磁盘缓存无失效机制。

**建议**：
1. 给 `Job` 加一个**产物版本戳** `artifacts_rev`（扒谱完成时 +1，歌词完成时 +1，写进 `job.json`），
   并落一个 `<工程>/.webui/manifest.json`：`{rev, files: {路径: {size, mtime, sha256?}}}`。
2. `bundle()` 缓存键改成 `bundle-<artifacts_rev>.zip`（或读 manifest 比对，不符就重打）；
   `svp.cache_key` 的入参加 `rev`；`peaks` 缓存键加 `source_mtime`（或干脆换成
   `peaks-stem-<mtime>-<buckets>.json`）。
3. 阶段**开始**时清掉派生缓存（`bundle*`、`export/*`、`peaks-*`），因为这些一定是旧的。
4. 下载响应头带 `X-Artifact-Rev`，页面在 rev 不一致时提示"有新结果，请重新下载"。

**验收**：重跑后立刻下载，zip/SVP 内的 `project.json` 与磁盘上的一致；
`tests/test_webui.py` 增补"重跑→缓存必然更新"（用假 runner 改 payload 即可验）。

### G4 · 没有"完成门禁"：半成品也会被标成成功 🟥P0

**现象**：`pipeline.run` 里 `summary["artifacts_ok"] = True` 是**硬编码**的（`pipeline.py:420`），
真正的体检函数 `result.inspect_output_dir`（`result.py:194`，15 个文本产物 + 6 个 MIDI 的
完整性/自洽性检查）**只有 CLI 的 `service.transcribe_to_directory` 会调**（`service.py:91`）；
WebUI 的 `runner.transcribe` 直接调 `pipeline.run`（`runner.py:371`），**从不体检**。

于是：`StageRun.state = "done"` 的唯一依据是"runner 没抛异常"（`jobs.py:1231-1237`）。

**用户会怎么撞上**：模型中途吐了半套产物但没报错（磁盘满、编码器异常、被杀毒软件锁文件），
界面显示✅完成，下载的 SVP 少了一半音符，或者卷帘是空的。

**建议**：
1. `runner.transcribe` 结尾调 `inspect_output_dir`，把结果塞进 `detail.artifacts`；
   `ok=False` 时把阶段标成 **`degraded`**（新增状态，非终态失败）或直接 `failed`，
   并把缺失清单用人话列出来（"缺 3 个文件：chords.mid、notes.tsv…"）。
2. `_finish` 里再兜一次底：`done` 的前提是产物清单非空 + `project.json` 可解析
   + 关键文件在（`project.json`、`report.json`、`summary.json`）。不满足就 `failed`。
3. 前端在 `done` 旁边显示"自检：21/21 产物通过"；有警告时给个黄色感叹号，点开看明细。

**验收**：`tests/test_webui.py` 里让假 runner 故意少写一个产物 → 阶段不得为 `done`。

### G5 · 写盘不是原子的，中断后残留"半截文件 + 旧文件" 🟥P0

**现象**：`project.json` / `report.json` / `summary.json` / `job.json` 都是
`write_text` 直接盖（`pipeline.py:443-448`、`jobs.py:1274`），没有 `.part + rename`。
而 `output/<歌名>/` 里**同时**躺着上一轮的全部产物 —— 重跑时是**覆盖写**，
不是"先清空再写"。

三种典型坏状态：
1. **进程在写 JSON 时被杀**（Ctrl+C、任务管理器、断电）→ 文件是半截。
   `job.json` 有 `ValueError` 兜底（`jobs.py:681`）；`project.json` 没有，
   而 `/lanes`、`/exports`、`/download?kind=svp` 全靠它 → 用户看到 500 或"还没扒谱"。
2. **重跑扒谱失败在中途** → 磁盘上混着上一轮的 `lyrics.json`、这一轮新的 `project.json`。
   界面把歌词阶段标成 `idle`（内存），但 `/download` 打出来的 zip 里**有旧歌词**。
3. **取消后**同样的混搭：`cancel` 只置标志（`jobs.py:1097`），不清理这一轮已写的文件。

**建议**：
1. 所有产物写盘统一走 `_atomic_write(path, text)`：写 `<path>.part` → `os.replace`。
   （zip 和 SVP 已经这么做了，`project.json` 只是漏了。）
2. 阶段开始前，把"这一阶段产出的旧文件"移进 `.webui/prev/<rev>/`（或直接删），
   保证 `output/` 永远只表示"当前这一版"。阶段成功后再清 `prev/`。
3. 完成时写 `<工程>/.webui/manifest.json`（rev + 文件清单 + 时间 + 参数快照），
   `/files` 与 `/download` 只信 manifest，不信目录扫描 —— 这样"残留文件"再也进不了下载包。
4. 前端"正在写入，请稍后重试"的提示保留（`app.py:399`），但要配上限（比如 3 次 × 0.2s 后
   回 409 + "产物正在重写，请等这一轮跑完"）。

**验收**：杀掉进程后重启 → 列表能打开、不 500；重跑中途失败 → 下载包里没有旧歌词。

### G6 · 没有超时与看门狗：卡住就是永远 🟥P0

**现象**：全项目**没有一处阶段级超时**。
- `_run_phase` 直接 `payload = runner(job, progress)`（`jobs.py:1217`），没有 deadline；
- `media.compute_peaks` 的 `subprocess.run` **没有 timeout**（`media.py:60`）——
  ffmpeg 卡住会永久占用一个线程池线程（`asr.py:315` 有 300s，对比明显）；
- 取消是协作式的：`Progress.check()` 只在回调里检查（`jobs.py:600`），
  而**模型加载阶段**（`engine.load()`，实测 15~30s，大模型更久）和 **CUDA 卡死**时
  一个回调都不会来 → 点了「停止」也没用；
- SSE 有心跳（15s），但心跳只证明**HTTP 连接活着**，不证明**任务在推进**。

**用户会怎么撞上**：进度条停在"识别音乐 62%"半小时。他刷新页面，还是 62%。
他不敢关窗口（怕白跑），只能一直等。这就是"僵尸任务"。

**建议**：
1. **阶段 deadline + 无进展看门狗**：`Progress` 记录 `last_advance_at`（step/progress 任一变化时刷新）。
   工作线程另起一个 watchdog 线程（daemon，1 个进程一个就够），每 10s 扫一遍：
   - 无进展 > `STALL_TIMEOUT`（扒谱 15min，歌词 10min，可 CLI 配）→ 阶段标 `failed`，
     错误文案"卡住了 N 分钟没有进展"，并**杀掉相关子进程**（见第 3 条）；
   - 总时长 > `HARD_TIMEOUT`（扒谱 2h / 歌词 1h）→ 同处理。
2. **取消要能打断加载**：把 `engine.load()` 拆成可检查点（或者在 watchdog 里允许
   "用户已取消且超过 60s 未响应" → 直接落 `cancelled` 状态并让工作线程在下个检查点自行退出）。
   宁可留一条"任务被强制中止"，也别让用户面对一个停不下来的服务。
3. **子进程要有超时 + 进程组 kill**：`media.py:60` 的 ffmpeg 加 `timeout=`，
   Windows 上用 `creationflags=CREATE_NEW_PROCESS_GROUP` + `taskkill /T /F /PID`，
   避免 Python 死了 ffmpeg 变成孤儿继续吃 CPU（`tools/downloader.py` 同理，加 socket 超时）。
4. UI：阶段卡上加"已运行 mm:ss / 上次进展 xx 秒前"，**停滞 > 60s 变黄**，
   并出现「强制中止」按钮。

**验收**：假 runner 里 `sleep(9999)` → 超时后被标失败并给出人话；点停止在 60s 内生效。

### G7 · 报错直接吐给用户：`RuntimeError: ...` 加英文原文 🟥P0

**现象**：`jobs.py:1224`：

```python
message = f"{type(exc).__name__}: {exc}"
run.error = message
```

这条字符串**原样**进快照（`StageRun.as_dict`）、进 SSE、进 `job.json`，最后显示在页面上。
于是用户看到的是：

- `RuntimeError: 没有拿到任何逐字时间戳，填词无法进行`（还算能读）
- `TranscriptionError: 转写失败：RuntimeError: CUDA error: an illegal memory access was encountered`
- `OSError: [Errno 28] No space left on device`
- `HTTPException: 500: ...`（从一个 handler 漏出来的）

而 `ffmpeg` 的报错（不带 `-loglevel error` 时会吐几十行）也可能被塞进界面。

**用户会怎么撞上**：任何一次失败。他看不懂，只能放弃或来问你"这是什么意思"。

**建议**：
1. 建一张**错误码表** `webui/errors.py`：`code` + `人话` + `下一步怎么做` + `技术细节`。
   例：
   | code | 人话 | 下一步 | 技术细节 |
   |---|---|---|---|
   | `E_DISK_FULL` | 磁盘满了，写不进结果 | 清理 `output/` 或换个大点的盘（还差约 X MB） | `errno 28` 原文 |
   | `E_VRAM_OOM` | 显卡内存不够 | 把「精度」改成 BF16、或「范围」改成前 30 秒再试 | `CUDA OOM` 原文 |
   | `E_AUDIO_UNREADABLE` | 这个文件听不了，可能不是音频 | 确认是 wav/mp3/flac，或先转成 mp3 再传 | ffmpeg stderr 前 3 行 |
   | `E_ASR_EMPTY` | 没听到人声 | 换干声 / 确认不是伴奏版 | 逐段字数 |
   | `E_STALLED` | 卡住了 | 重启后重跑；把诊断包发我 | 最后一条进展 |
2. 快照里同时返回 `error`（人话，给横条显示）和 `error_detail`（技术原文，折叠在"详情"里）。
   日志抽屉里再给"复制诊断信息"按钮。
3. 未知异常统一兜底成"程序内部出错了"，附带错误码 `E_INTERNAL-<8位hash>`，
   并在日志里记全堆栈（配合 G12）。

**验收**：构造 5 类失败（磁盘满/显存/坏音频/无人声/超时），页面横条都必须是中文人话 + 一个可点的下一步。

## 5. 缺口清单（P1：会让人懵、或者用不下去）

> ✅ **本节 G8–G17 已全部落地**（第二期，见 §7）。下面的"现象 / 建议"保留作历史记录，
> 每条的实际修法与验证见 §8 与 `docs/WebUI问题清单.md` §15–24，测试在
> `tests/test_webui_p1.py`（20 项）。落地位置速查见附录 A。

### G8 · `rev` 没当乐观锁用，两个标签页会互相覆盖 🟧P1

**现象**：`Job.rev` 只在重跑扒谱时 +1（`jobs.py:920`），**从不参与并发控制**。
`PATCH /options` 是"整块 patch 覆盖"（`jobs.py:970-972`），没有 `If-Match` / `expected_rev`。
前端 `setOptions` 只发变化的那一项（`useStudio.ts:381`），但**不知道自己是基于哪一版改的**。

**用户会怎么撞上**：开了两个标签页（或者同一台机器的浏览器 + 手机），
A 页把「精度」改成 FP32，B 页（还停在旧快照）点了「语言=日语」→ A 的改动被**静默回滚**。

**建议**：
1. 快照里已经有 `rev`，改成**写操作都带版本**：`PATCH /options` 接受
   `If-Match: <rev>` 或 body 里的 `expected_rev`，不匹配回 **409 + 当前快照**，
   前端收到 409 就"你这页是旧的，已帮你刷新"而不是覆盖。
2. `rev` 的语义改成"任何影响结果的变更都 +1"（改参数、换音源、重跑阶段），
   和 G3 的 `artifacts_rev` 分开：一个管并发，一个管产物。
3. 顺带把 SSE 事件的快照也带上 `rev`，前端丢弃 `rev` 更旧的事件（现在只按 `seq` 排）。

**验收**：两个客户端并发 PATCH 同一工程 → 第二个拿到 409，且最终状态与第一个一致。

### G9 · 并发上传同名文件会撞进同一个工程目录 🟧P1

**现象**：`unique_project_dir`（`jobs.py:274`）先 `while candidate.exists()` 再返回，
`create` 里随后 `mkdir(parents=True, exist_ok=True)`（`jobs.py:853`）——
判断与创建之间有窗口，而 `create` 跑在 `run_in_threadpool` 里（`app.py:234`），**是并发的**。

**用户会怎么撞上**：把同一个文件拖两次（或者拖进侧栏两次），或者一次拖入两个同名文件。

**后果**：两个任务写同一个目录、同一个输入文件名 → 文件互相覆盖、产物混在一起，
两个工程 id 都指向同一目录 → 删一个等于删两个。

**建议**：`mkdir(exist_ok=False)` + 冲突重试循环（最多 50 次），拿不到就报错；
输入文件用 `uuid` 前缀落盘（展示名仍存 `job.audio`），彻底避免同名互踩。

**验收**：并发 10 次 `create` 同一个名字 → 生成 10 个不同目录、10 个不同工程。

### G10 · 上传只查后缀，不查"是不是音频、是不是歌" 🟧P1

**现象**：`_check_audio`（`jobs.py:308`）只看后缀是否在 `AUDIO_SUFFIXES` 里。
内容、可解码性、时长、采样率、是否静音，**一概不查**。
`attach_stem` 更是明说"不做内容校验"（`jobs.py:996`）。

**用户会怎么撞上**：
- 把 `.mp4` 视频当音频传（后缀在允许列表里，`AUDIO_SUFFIXES` 含 `.mp4`）→ 可能能跑，也可能炸；
- 传了个改名成 `.mp3` 的 Word 文档 → 40 秒后才炸；
- 传了伴奏版 → 谱面质量明显变差（README 里自己都提醒"请用含人声的完整混音"）→ 用户不知道；
- 干声栏传了别的歌 → 歌词全错位，只在报错里提一句（`runner.py:463`）。

**建议**（上传后**立刻**做，亚秒级，不加载模型）：
1. `ffprobe -v error -show_format -show_streams` 读一次：容器是否认得、有没有音频流、时长、
   采样率、声道数、码率。失败 → `E_AUDIO_UNREADABLE`。
2. 时长阈值：`< 10s` 提示"太短，可能不是一首歌"；`> 15min` 提示"很长，可能要跑 40 分钟"（配合 G20）。
3. 音量体检：抽 20 秒算 RMS / 静音比例，全静音 → 直接拒（省得白跑半小时）。
4. 内容去重：算前 1MB + 文件大小的指纹，命中已有工程就提示"这个文件已经导出过了，
   要直接打开旧工程吗？"（顺便省磁盘）。

**验收**：5 种坏文件（改名文档 / 纯静音 / 0 字节 / 视频 / 20 分钟长音频）都在 2 秒内给人话提示。

### G11 · 没有磁盘空间预检，也没有产物回收 🟧P1

**现象**：`src/` 里**没有任何** `disk_usage` / 剩余空间检查（只有 `tools/bootstrap.py:107`
在安装时体检过）。而一次扒谱的产物可能几十~几百 MB，`.webui/input` 里还留着整首原音频
（无损 flac 动辄 30~50MB），`bundle.zip`、`export/*.svp`、`peaks-*` 都留着。

**用户会怎么撞上**：笔记本电脑 256G 硬盘，跑到第 5 首歌时磁盘满 →
`OSError: [Errno 28]`，阶段 failed，界面一句英文（叠加 G7）。

**建议**：
1. 阶段开始前 `shutil.disk_usage(数据根)`：剩余 < 预估需求 × 3 就**拒跑**并说明
   （预估 = 音频大小 × 3 + 50MB，够粗就行）。
2. `/api/env` 里带 `disk: {free, total}`，顶栏显示"剩余 12.3 GB"，< 2GB 变黄。
3. 「清理」页：列出每个工程的 `.webui/` 占用，可一键清 `bundle.zip` / `export/` / `peaks`
   （这些都能重算），以及"删除原音频副本"（用户手上还有原文件的话）。

**验收**：把数据根指到一个 100MB 的小盘上 → 上传时/开跑前给出中文提示而不是中途炸。

### G12 · 日志只在内存里，崩溃之后什么线索都没有 🟧P1

**现象**：`job.json` 只留最后快照；事件流上限 4000 条（`jobs.py:58`）；
**没有 log 文件**（`__main__.py` 只有 uvicorn 的控制台输出，且有 `log_level` 可关）。
进程被强杀 / 蓝屏 / 显卡驱动重置 → 现场全丢。用户能提供的只有"它转圈了"。

**建议**：
1. 用 `logging` + `RotatingFileHandler` 写 `logs/studio-YYYYMMDD.log`（10MB × 5），
   uvicorn 的 access/error 也接进去；保留最近 7 天。
2. 「诊断包」按钮：一键打包 `job.json` + 最近日志 + `/api/env` + `bootstrap-state.json`
   + 系统信息（GPU/驱动/内存/磁盘）+ 该工程的 `summary.json`，下载成一个 zip，
   名字带错误码（`diagnose-E_VRAM_OOM-20261005.zip`）。
3. 崩溃时（`sys.excepthook` + `threading.excepthook`）写 `logs/crash-<时间>.txt`，
   下次启动在界面上提示"上次异常退出，已保存崩溃日志（可一键发送）"。

**验收**：kill -9 之后重启，`logs/` 里有完整日志，且能从界面导出诊断包。

### G13 · 没有 CSRF / Origin 校验；`--host 0.0.0.0` 时裸奔 🟧P1

**现象**：所有接口无鉴权、无 token、无 `Origin` 校验。默认 `127.0.0.1` 还行，但：
- 用户访问的**任意网页**都能向 `http://127.0.0.1:8000` 发**简单请求**
  （`POST /api/jobs/{id}/cancel`、`POST /api/jobs/{id}/stages/transcribe` 都不需要自定义头
  → 不需要预检），于是"打开网页 → 后台悄悄开始扒谱 / 取消任务 / 删除工程"
  （`DELETE` 需要预检，但 `POST` 不需要）；
- DNS rebinding 也能绕过同源限制读到 `/api/jobs` 的响应；
- 有人为了"手机也能用"加了 `--host 0.0.0.0`（README 没禁止）→ 同一 WiFi 下任何人可上传/删除/导出。

**建议**：
1. 服务端中间件：非 `GET` 请求校验 `Origin`/`Referer` 必须是 `http://127.0.0.1:<port>`
   或 `http://localhost:<port>`；`GET /api/*` 也校验 `Host` 头（防 DNS rebinding）。
2. 启动时生成一次性 `pair_token` 写进 URL（`/?t=...`）或 cookie，前端所有请求带上；
   没 token 的 API 一律 403。这对本地用户是**无感**的（浏览器自动带）。
3. `--host` 非回环时**强制**要求 token，并在控制台大红字警告。
4. 别忘 CORS：现在是默认关，加鉴权后继续保持关。

**验收**：从 `http://evil.example` 页面向本服务发 `fetch(..., {mode:'no-cors'})` 的 POST →
任务状态不变。

### G14 · 重复点击会重复入队；取消可能被"复活" 🟧P1

**现象**：
- `run_stage` 只在 `job.state == "running" and job.stage == phase` 时早退（`jobs.py:905`），
  **`queued` 状态下不早退** → 连点两次「开始扒谱」= 同一个 `job_id` 被 `queue.put` 两次；
  工作线程会把同一个任务"跑完 → 再收尾一遍"（`_finish` 再算一次状态，多一条终态事件）。
  单 worker 时只是多余事件，`--workers 2` 时就可能**同一阶段并发跑两份**。
- 更隐蔽：第二次点击会把 `cancel_requested = False`（`jobs.py:923`）——
  用户在两次点击之间点了取消，取消被抹掉。

**建议**：
1. `run_stage` 早退条件改成 `job.stages[phase].state in ("queued", "running")`；
2. 队列里存 `(job_id, phase)` 而不是只有 `job_id`，`_next_phase` 只跑确实在 plan 里的；
3. `cancel` 之后加一个"墓碑"标记，同一工程 5 秒内的 `run_stage` 直接 409（防手抖连点）；
4. 前端按钮在请求进行中禁用（现在只有 `busy`（上传中）会禁用）。

**验收**：10 次并发点「开始扒谱」→ 只入队一次、只有一个终态事件。

### G15 · 启动不做完整预检，缺模型/缺 ffmpeg 要等第一个任务才炸 🟧P1

**现象**：`launch.py:177` 只检查 `models/SheetSage2/config.json` 并在**控制台**打一行提示；
浏览器里没有任何提示。`/api/env` 有 `ffmpeg` 字段（`app.py:189`），但前端只用来显示吗？
（现在没有 banner 逻辑）。缺 Qwen 权重、CUDA 不可用、驱动过旧，都要到用户点了「开始」才知道。

**建议**：启动时做一次 `preflight()`，结果进 `/api/env.preflight`：
| 检查 | 不通过时的表现 |
|---|---|
| ffmpeg 可执行 | 红色横幅"缺 ffmpeg，扒谱会用不了"+ 修复指引 |
| SheetSage2 权重 | 黄色"还没下载模型，点这里下载"（走 `tools/bootstrap.py`） |
| Qwen 权重（可选） | 灰色"歌词识别不可用，只能扒谱" |
| CUDA 可用 / 显存 | 蓝色"没检测到显卡，会用 CPU 跑，一首歌约 30~60 分钟" |
| 磁盘剩余 | 见 G11 |
| 数据目录可写 | 红色（这个最致命，先测一次写盘） |

**验收**：把 `models/Qwen3-ASR-1.7B` 改名 → 打开页面立刻看到"歌词识别不可用"，而不是点了才炸。

### G16 · 服务重启/崩溃后，打开着的页面静默冻结，不告诉用户发生了什么 🟧P1

**现象**：任务状态全在进程内存里，`job.json` 只在阶段边界落盘（`jobs.py:1267`）。
如果用户**正开着页面**的时候服务没了（关掉了黑色命令行窗口、进程崩溃、显卡驱动重置、笔记本睡眠后进程被杀）：

- `EventSource` 断开 → `api.ts:248` 停下流；
- `useStudio.ts:220-232` 走重连，最多 10 次、退避 0.5s×n（约 27 秒），期间的
  `refreshArtifacts()` 全部 `catch` 掉（`useStudio.ts:161-166`，注释写着"快照拉不到不影响事件流"）；
- 重试耗尽后只往日志抽屉里塞一句"进度流断开，刷新页面可继续查看结果"
  （`useStudio.ts:227`）—— **日志抽屉默认是收起的**。

**用户会怎么撞上**：他拖了歌、点了「自动提取」，看着进度到 62%，然后不小心关掉了那个黑色窗口
（或电脑睡了一觉）。回到浏览器，进度条**还是 62%**，页面看起来一切正常，只是不动了。
他可能就这么等下去。

**建议**：
1. 前端加服务存活探测：SSE 断开后 `GET /api/healthz`（已存在但没人用，`app.py:168`），
   连续 3 次失败 → 顶部**红色横幅**"后台服务已停止（可能被关闭或崩溃了），
   点这里重新启动 / 查看上次日志"，并把阶段卡整体置灰 + 标"未知"。
2. 服务启动时，把"上次被中断的阶段"这件事**推到页面**：恢复的工程已经在阶段消息里写了
   "上次运行被中断（程序重启），可以重跑"（`jobs.py:721`），但前端只在**选中该工程时**才拉快照。
   打开页面就应该在列表项上标一个角标 ⚠，并在主区提示一次。
3. 页面加载时若 `jobs` 里存在 `state == "running"` 但 SSE 连不上，直接按第 1 条处理
   （现在会一直显示"运行中"）。

**验收**：跑任务时 `taskkill` 掉服务 → 30 秒内页面出现红色横幅并说明；重启服务后角标提示可重跑。

### G17 · 显存不够时静默退 CPU，跑几小时也不说 🟧P1

**现象**：`engine.transcribe` 捕获 OOM → `_move_to_cpu()` → **重新跑一遍**
（`engine.py:223-237`）。这条 fallback 只写进 `engine.records`，**没有进 `warnings`、
没有进进度事件**。用户以为在用 GPU。

**为什么要紧**：README 自己写了"CPU 退路已验证"，但一首 4 分钟的歌在 CPU 上可能是
**30~90 分钟**。用户看到进度条缓慢爬升，会以为卡死。

**建议**：
1. OOM 触发时立刻 `progress.log("显存不够，已自动改用 CPU 重跑（会慢很多，约 X 分钟）")`
   并发一条 `warning` 事件，前端阶段卡变色 + 横幅提示。
2. 退 CPU 后**重算进度上限**（总时长预期 × 10），或者干脆在开始前预估：
   `预估耗时 = f(音频秒数, 设备)`，写进快照 `eta_seconds`，UI 显示"预计还需要 12 分钟"。
3. 给用户一个"别自动退 CPU"的开关（4G 特供模式默认关掉？）——有些人宁可直接失败重来。

**验收**：模拟 OOM（改配置强制小显存）→ 界面出现"已改用 CPU"横幅；`detail.fallback` 可查。

### G18 · SSE 进度会倒退 / 事件乱序打到旧快照上 🟨P2 ✅

**原现象**：`applyEvent` 直接 `run.progress = event.data.progress`，而后端只保证事件 `seq`
单调。切换工程 / 改参数 / 重跑之后前端**没有重置 `lastSeq` 的时机约束**（`select` 里重置了，
但 `setOptions` 之后没有），重连补发的事件可能把进度从 0 拉回到 80%。

**修法**（`web/src/progress.ts`，纯函数 + 单测）：
1. **只增不减**：`monotonicProgress(当前, 事件)` 取 `max`，并把值夹在 0~1。
2. **旧事件不算数**：`isStaleEvent(event.time, run.started_at)`——比这一趟开始还早的事件
   只可能有日志价值，不许动进度。
3. **只有新一轮的 `phase` 事件才能归零**：`startsNewRun` 用时间戳判定，重跑时
   `phase` 事件（带 `eta`）就是新一轮的起点。
4. 不用"改参数后把 `lastSeq` 归零"：那会把整段历史重放一遍，反而更容易把旧快照打到新状态上。

**验证**：`web/test/progress.test.ts` 13 项（含"从 12% 跳回 80%"这条真实场景）。

---

### G19 · 前端请求没有超时、没有取消 🟨P2 ✅

**原现象**：`api.ts` 全是裸 `fetch`，没有 `AbortController`/超时。服务卡住（G6）时页面会
**永远 pending**，用户只能刷新。

**修法**（`web/src/api.ts`）：
1. 所有非 SSE 请求走 `fetchWithTimeout()`：普通请求 **30s**，上传/导入 **10 分钟**
   （XHR 的 `timeout`），存活探测单独 **5s**（服务没响应时要尽快判定，不能陪着等 30s）。
2. 超时文案是人话：`服务没响应（已等 30 秒），可能还在忙：稍等一下重试；一直这样就把后台
   窗口关掉重启一次`；连不上是另一句（`连不上后台服务…可能已经关闭或崩溃了`）。
3. 超时用 `AbortController` 真的掐掉，不会留下一个 pending 的 Promise。

**验证**：`web/test/api.test.ts` 5 项（用一个"永不 resolve、只响应 abort"的 fetch 造场景）。

### G20 · 没有耗时/显存预估 🟨P2 ✅

**原现象**：用户拖进一首 6 分钟的歌，不知道要等 3 分钟还是 40 分钟；进度条第一次长时间
不动时，他没有参照物判断"是我该等，还是它卡死了"。

**修法**（`webui/eta.py` 纯函数 + 快照字段 + 阶段卡一行）：
1. 口径：`扒谱 = 音频秒数 × 0.6（GPU）/ × 8（CPU）`，`歌词 = × 0.5 / × 4`，再加固定开销
   （模型加载 25s / 45s），区间按低估 20%、高估 30% 给。选了「前 30/60 秒」就按截断后的
   时长算。
2. 音频时长来源按可信度排：上传体检（`audio_info`）> 产物 `summary` > `highlights`；
   都没有就**不给预估**（`eta: null`，界面不显示）——比编一个数字强。
3. 快照里 `stages.<phase>.eta = {seconds, low, high, label, device, audio_seconds}`，
   `phase` 事件也带上它；`done/failed/cancelled` 之后不再给（进度 100% 了没什么好猜的）。
4. 设备口径：工程的「设备」优先；`auto` 时用启动时探测的结果（`preflight.cuda_available()`），
   都不知道就按显卡估（有卡的机器远多于没卡的，而且**低估**比高估更不吓人）。
5. 界面（`StageCard.vue`）：还没跑显示「⏱ 预计 2~4 分钟」，跑起来显示
   「⏱ 预计还需约 3 分钟」，估得比实际快时说"预计快好了"（不编"还需 0 分钟"）。

**显存预估**没有单独做：`detail` 里已经有实测的 `peak_gpu_mib`（跑完之后），
事前预估显存的收益比不高（真正会 OOM 的用户已经被 G17 的"已退 CPU"告知兜住了）。

**验证**：`tests/test_webui_p2.py` 里 6 项（GPU/CPU 系数不能写反、范围截断、缺时长不给、
快照字段、设备优先级、跑完就撤）。

### G21 · 没有阶段级断点续跑 🟨P2 ⏸ 未做（有依据）

**现象**：进程被杀 → 阶段从头再来（模型要重载 15s + 重新推理 3 分钟）。

**为什么先不做**（实测确认，不是偷懒）：

1. **窗口循环不在我们这一层**。`engine.transcribe()` 只是把参数透传给
   `self._model.transcribe(audio, output_dir=..., progress=...)`（`engine.py:253-256`），
   窗口怎么切、中间结果写哪儿，全在 SheetSage2 的 remote code 里。我们只能收到
   `progress({"stage": "window_complete", "window": i, "windows": n})` 这种**通知**，
   拿不到那一段的中间结果，也就没法"跳过已完成的窗口"——硬做等于改上游代码。
2. **能做的只有歌词阶段的切片续跑**：`asr.transcribe_sections` 的循环确实在我们手里
   （`asr.py:354`），落 `.webui/ckpt/<rev>/s<idx>.json` 是可行的。但它要引入
   "缓存与参数/音源/切片边界的一致性校验"一整套（错了就是**给错结果**，比慢严重得多），
   而收益只覆盖两个阶段里的一个。
3. 评估里本来就写了"收益大、改动也大，放最后"（§6 原文）。**排期建议：单独一期**，
   先只做歌词切片续跑 + 一致性校验，扒谱等上游给了窗口级接口再说。

**现状兜底**：进程被杀不会白跑——重启后阶段标成"上次运行被中断（程序重启），可以重跑"
（`_job_from_meta`），超时/卡死有 G6 的看门狗收尸，产物不会再混搭（G5 的 `.webui/prev/`）。

### G22 · 数据目录迁移与备份无引导 🟨P2 ✅

**原现象**：`SHEETSAGE_WEBUI_DATA` 能改，但小白不会用；换电脑就是整个 `output/` 目录拷走，
而 `job.json` 里有**绝对路径**（`_job_from_meta` 已经做了兜底重建 `upload` 路径——这条做得很好，
但没人指望用户知道这件事）。

**修法**（新增 `webui/backup.py` + 顶栏两个按钮）：
1. **「备份」**（`GET /api/backup`）：所有工程打成一个 zip，内含
   `backup.json`（版本 / 时间 / 工程清单 / 参数）+ 产物 + `job.json` + `.webui/input` 里的原音频
   + `manifest.json`。**不带**可重算的缓存（`bundle.zip` / `peaks-*.json` / `export/*.svp` / `prev/`），
   除非显式 `?include_cache=true`——那些都能从产物重算，带着只是让包翻倍。
2. **「导入备份」**（`POST /api/backup/restore`）：解到临时目录 → 逐条目校验 → 每个工程走**和
   重启恢复完全相同的那条路**（`_restore`：原音频绝对路径对不上就按布局重找）。
   重名**绝不覆盖**（`claim_project_dir` 的 `-2`），同一个包导两次还会换 id，删一个不会连坐另一个。
3. 导入是不可信输入，所以：拒绝绝对路径 / `..` / 盘符 / 符号链接条目（zip-slip）、
   条目数与解压总量有上限（zip 炸弹）、必须有 `backup.json` 且版本认得出，
   不认识的包直接说"这个压缩包里没有备份清单：它可能不是本程序导出的备份"。
4. 临时文件随下载结束自动清（`BackgroundTask`），不在数据根里堆几百 MB 的包。

**验证**：`tests/test_webui_p2.py` 里 8 项（清单与内容、缓存默认不带、换数据根后产物/原音频/
参数都在、导两次不覆盖、非本程序包 400、zip-slip 整包拒绝、版本不认拒绝）。

## 附录 D：两个"以为是坑、实测不是"的（别再花时间修）

评估过程中我实际跑了一遍命名逻辑与 Windows 目录创建，结论与直觉相反，记下来免得后人重走：

| 怀疑 | 实测 | 结论 |
|---|---|---|
| 中文歌名会被 `project_folder_name` 洗成 `_` | `project_folder_name("凤凰传奇 - 光芒") == "凤凰传奇_-_光芒"`——`str.isalnum()` 对 CJK 返回 True，中文是**保留**的 | ✅ 不是坑。内测包 README 说"解压到无中文路径"针对的是打包/解压链路与 ffmpeg 参数，不是这里 |
| `CON` / `NUL` / `AUX` 这类 Windows 保留名会创建失败 | Python 3.12 在本机 **成功** 建出 `tmp\CON`、`tmp\NUL.mp3`、`tmp\AUX`（已清理），`Path.mkdir` 没抛 `OSError` | ⚠️ 现代 Python 走长路径/`\\?\` 语义，基本不炸；**但**第三方工具（ffmpeg、模型代码里的 C 层打开文件）不一定这么宽容 |

仍然值得做的一条（低优先级）：**超长歌名**（>180 字符）会让
`output/<歌名>/.webui/input/<原名>` 逼近 `MAX_PATH`，此时 Python 通常还行、外部工具会莫名报错。
建议 `project_folder_name` 截断到 60 字符 + 4 位短 hash，`safe_name` 同样处理（顺带解决
"两个长名字只差后缀、截断后撞车"的问题）。反例已知：`project_folder_name("..") == "audio"`，
`"a/b"` 与 `"a_b"` 都会变成 `a_b` —— 这些由 `unique_project_dir` 的 `-2` 兜住（前提是 G9 的竞态先修）。
