# 对齐器泛化：要多少数据、要不要补粤日韩

> 调研对象：`lyrics.assign_lyrics` / `_align_latin_words` + TIFA/Qwen 时间戳这条链路。
> 结论日期：2026-11-18。文中的数字是**工程估算 + 统计判据**，不是已经跑出来的实验结论；
> §3 给了可复现的「多少算够」判据，§8 给了分期。
>
> 口径：**一首 = 一个工程 = 一份 2~5 分钟完整歌曲 + 一份自动产物 + 一份人工精修 SVP**。
> 不是 30 秒切片，也不是「只修了歌词没修音符」的半成品。

> **范围收窄（2026-11-18 追加）**：如果目标只是优化挂字层（`assign_lyrics` /
> `_align_latin_words`），不改 TIFA/Qwen/ASR，按 §11 的 **B 层**执行即可：
> 中英各 **80 首金标 + 100~200 首自动**，自动侧只留 `project.json` + `lyrics.json` + SVP；
> 音频只需 **20~30 首/语言**做试听与争议仲裁（约 1.5~2 GB），不需要 10~18 GB 全量音频。
> 每次算法改动只重跑挂字，不碰模型，迭代成本最低。

## 0. 结论先行

**中/英各：自动池 200 首、人工金标 80 首**（30 首调参 + 50 首留出）。
这是「能撑起泛化结论」的推荐值；最低可用的下限是 **120 自动 + 50 人工**；
要报到「按曲风/语种分桶都可信」才需要 **300 自动 + 150 人工**。

| 语言 | 自动池（最低/推荐/强） | 人工金标（最低/推荐/强） | 推荐 dev/test | 判断 |
|---|---:|---:|---|---|
| 中文 | 120 / **200** / 300 | 50 / **80** / 150 | 30 / 50 | **必做** |
| 英文 | 120 / **200** / 300 | 50 / **80** / 150 | 30 / 50 | **必做** |
| 粤语 | 30 / **60** / 100 | 20 / **30** / 50 | 10 / 20 | **建议补，成本低** |
| 日语 | 40 / **80** / 120 | 20 / **40** / 60 | 15 / 25 | **只有做日语才补；是独立工程** |
| 韩语 | 30 / **50** / 80 | 10 / **20** / 30 | 10 / 10 | **暂缓；先修 G2P** |

一句话回答：

- **中、英**：各 **200 首自动 + 80 首人工精修**；预算紧就 **120 + 50**，别低于 50 首人工。
- **粤语**：**要补**，但只需 30 首人工 + 60 首自动；它和中文同一条字级分支，主要是词典/OOV/繁简与 ASR 文本问题。
- **日语**：**要补，但先补工程**（分词 + 汉字读音 + モーラ + `+`/`-` 语义）；不是「多收 80 首歌」就能解决。做日语就收 40 首人工，不做就明确不支持。
- **韩语**：**暂缓**。TIFA 1.0 没有韩语 G2P，界面上的「韩语」现在会静默落到中文 G2P；先修通路，再谈 20 首人工。
- 优先级：**中 ≈ 英 > 粤 > 日 > 韩**。
- **拍号/变速不影响挂字评测**（2026-11-19 追加）：挂字在秒域做，tick→秒 映射完拍号就不可见；
  6/8、2/4、变速 留在 `scripts/verify.py` 的集成验证里，不收进 alignment-only 样本集。

## 1. 先把「对齐器」拆成三层

现在这条链路不是一个模型，而是三层误差叠在一起：

| 层 | 由谁决定 | 典型错误 | 该用什么数据评 |
|---|---|---|---|
| ① 音符层 | SheetSage2 | 漏音、多音、音符边界粗、转音没扒出来 | **人工音符**（SVP） |
| ② 字时间层 | TIFA / Qwen ForcedAligner | 零宽度、长跨度吞字、局部漂移、G2P OOV | 音频 + 参考文本 |
| ③ 挂字层 | `lyrics.assign_lyrics` / `_align_latin_words` | 词头晚一个音、`+`/`-` 判错、字被 absorbed/dropped | **人工音符 + 人工挂字** |

三层必须分开评，否则「对齐变差」会被误判成「扒谱变差」，反过来也一样。
当前 `tmp/score_fill.py` 是拿**自动音符**去对**人工歌词**，把①和③混在一起；
做正式评测时应先固定一套**人工音符**，只换字时间与挂字算法，才能单独看对齐器。

> 代码位置：`src/sheetsage2_webui/lyrics.py:527`（`assign_lyrics`）、
> `lyrics.py:209`（`_align_latin_words`）、`src/sheetsage2_webui/tifa_align.py:29`
> （TIFA 语言表）、`src/sheetsage2_webui/asr.py:692`（`_labels_for`）。

## 2. 现有数据盘点：为什么现在还不能谈「泛化」

仓库里目前能拿出来的东西：

| 项 | 数量 | 说明 |
|---|---:|---|
| 已跑通的工程 | **14 个** | `reports/锚定对齐对照.md`：4810 字，greedy hit 70.4% |
| 完整成对（自动 + 人工） | **4 对** | 中文 2（王朝《我本将心向明月》、忘川《旷古回响》）；英文 2（Poison、Oracle） |
| 不成对 | 若干 | The Phoenix 只有人工；《爱情转移》有 3 个自动版本但没有人工；Wellerman 只有自动、没有人工 |
| 日语人工 SVP | **0 份** | 只有 2 个 LRC；日语路径目前走 Qwen 对齐器 |
| 英语 DP 的规则来源 | **4 首歌** | The Phoenix（422 音 / 46 个 `-` / 59 个 `+`）归纳，Poison/Oracle/Wellerman 验证 |

这意味着两件事：

1. **英文 `_align_latin_words` 的一组超参是 4 首歌上调出来的**（`HEAD_TRUST_SECONDS`、
   `RUN_EXCESS_COST`、`SKIP_COST` 等十来个），过拟合风险很高；换一个歌手/曲风就可能掉。
2. **中文的 70%~85% 是「对自动音符的重叠率」，不是对人工挂字的准确率**；
   真正的人工对照只有 2 首。现在的「泛化」是没有留出集支撑的。

另外有两个已经能看到的结构性缺口：

- **日语**：`asr._labels_for()` 对非英语是 `list(text)`，一个假名一个 token；
  `lyrics._align_latin_words()` 把每个 token 当「词」，`_mora_count()` 只数 token 内的假名。
  所以「ありがとう」到不了「ありがとう + + + +」，而是 5 个 token，每个 token 的后续音都写 `+`。
  要实现用户要的语义，必须先有**词级 token + モーラ数**。
- **韩语**：`tifa_align.tifa_language("Korean")` 会走 `default="zh"`（`tifa_align.py:68-78`），
  即韩文歌词拿中文 G2P 去对齐。界面上有「韩语」选项（`asr.py:331-338`），
  但实际是「看起来支持、实际不支持」。这属于必须先修的bug，不是数据量问题。

## 3. 需要多少：统计依据

### 3.1 评估单位是「首」，不是「字」

一首歌有几百个字/词，但同一首歌内的错误高度相关（同一个对齐漂移会影响整句）。
所以置信区间要按**歌**算，或用 cluster bootstrap；不能拿 4800 个字当 4800 个独立样本。

歌级均值（每首歌 hit 率的平均）的 95% 区间，用 `1.96 × sqrt(p(1-p)/n)` 粗算：

| 歌数 | p=0.5 时 | p=0.9 时 |
|---:|---:|---:|
| 30 | ±17.9pp | ±10.7pp |
| 50 | ±13.9pp | ±8.3pp |
| 80 | ±11.0pp | ±6.6pp |
| 100 | ±9.8pp | ±5.9pp |
| 150 | ±8.0pp | ±4.8pp |
| 200 | ±6.9pp | ±4.2pp |

实际报告要用观测到的**歌间标准差**做 t 区间/bootstrap，通常比二项式窄一些；
但量级就是这个：**50 首才能把「90% 左右」说到 ±8pp，80 首到 ±6~7pp，150 首才到 ±5pp。**

### 3.2 调参集可以小，留出集不能小

- **dev（调参）30~40 首**：足够做 5 折交叉验证、扫 6~8 个超参；
  再多也不会让规则更对，只会增加过拟合面。
- **test（留出）50~100 首**：锁死，只在版本发布时看一次；
  低于 50 首，A/B 的 ±1~2pp 波动分不清是算法还是抽样。
- **配对比较**比绝对区间更敏感：同一批歌跑旧/新算法，用 McNemar 或配对 bootstrap；
  50 首通常能看出 **~10pp** 的差，80 首约 **7pp**，100 首约 **5~6pp**。

### 3.3 「多少算够」用学习曲线回答，不要拍脑袋

建议先做一次学习曲线，而不是先收 300 首：

1. 从 10 首开始，按 10 首递增（10/20/30/40/60/80）；
2. 每个点用固定流程调参、在固定留出集上评；
3. 画「dev 歌数 → test hit」曲线；
4. **当再加 10 首带来的提升 < 1pp 时，就到了平台**——继续收数据不如改算法。

这条曲线还能回答「80 首够不够」：如果 40 首就到平台，80 首是浪费；
如果 80 首还在涨，说明需要的是**更多样的现象**，不是更多同质歌。

### 3.4 长尾现象覆盖

平均值会被「普通流行歌」拉平，真正让用户出戏的是长尾。每个语言至少覆盖：

| 现象 | 最低首数 | 说明 |
|---|---:|---|
| 快嘴 / rap | 8~10 | **按字密度判定：≥3 字/秒（10s 窗≥30 字）**，最容易 absorbed。「字/音 > 1.3」是另一回事（字多音少，如巴拉莱卡 1.39），不能当 rap 判据 |
| 转音 / melisma | 8~10 | 一个音节跨 3+ 音，考 `-` |
| 现场 / 混响大 | 5~8 | 考时间戳稳定性 |
| 对唱 / 伴唱 | 5~8 | 考主旋律选择与重叠。**这类样本只标 `split=stress`、不进 alignment-only 主指标**：音符层就可能选错旋律，挂字层对不了 |
| 6/8、2/4、变速 | 各 5 | 考小节/切片边界，不是挂字本身。**不进秒域评测集**：挂字在秒域做，拍号/变速映射完就不可见，留给 `scripts/verify.py` 的集成验证 |
| 中英混唱 | 5~10 | 考语言判定与 token 切分；**必须带 `parts`**，否则 `_align_latin_words` 走不到 |
| 日语汉字多 / 假名多 | 各 10 | 考分词与读音（做日语才需要） |

> 2026-11-19 修正：上表原来写「快嘴 = 字/音 > 1.3」，实测《快乐崇拜》是 rap 但字/音只有
> 0.97（692 字 / 711 音）→ 判据改为字密度。另：「拍号 / 变速」与「对唱 / 合唱」的定位也改了，
> 前者不进秒域评测集，后者只标 stress。详见
> [`docs/对齐器评测集缺口评估.md`](对齐器评测集缺口评估.md) §3。


这些应该单独做 **stress set**，不参与调参，报告里单独列 worst-slice。

### 3.5 两条数据池：自动池 vs 金标池

「扒谱产物」和「人工精修产物」不是二选一，而是两个池子：

| 池 | 成本/首 | 用途 | 推荐量 |
|---|---|---|---|
| **自动池** | 10~20 分钟（跑 pipeline + 粗看） | 失败挖掘、覆盖率、回归冒烟 | 200/语言 |
| **人工金标** | 2~3 小时（修音符 + 挂字） | 指标、调参、验收 | 80/语言 |
| **半自动银标** | 30~45 分钟（自动音符 + 人工挂字 + 抽查边界） | 回归、扩充 test | 50~100/语言 |

自动池便宜，应该远大于金标池；但**只有金标能支撑「泛化」这句话**。
如果预算只够 50 首金标，就把 50 首做成「30 dev + 20 test」，别把 50 首全用来调参。

## 4. 推荐配比与成本

### 4.1 分层矩阵（每语言 80 首金标的构成）

| 维度 | 取值 | 建议首数 |
|---|---|---:|
| 曲风 | 流行 30、抒情 20、摇滚 10、民谣/民族 10、rap 8、R&B/音乐剧 2 | 80 |
| 速度 | <80 / 80~120 / >120 | 20 / 40 / 20 |
| 拍号 | 4/4 60、6/8 10、2/4 5、其它 5 | 80 |
| 人声 | 独唱 60、对唱/合唱 12、伴唱 8 | 80 |
| 录音 | 录音室 60、现场 20 | 80 |
| 语言混合 | 含英文夹词 10~15 | 80 内 |
| 难度 | 易 20、中 40、难 20 | 80 |

切分规则：

- **按歌手切**，不按歌切：同一歌手的歌不能同时出现在 dev 和 test；
- 翻唱/同曲不同版本只进一个集合；
- stress set 单独，不参与调参；
- test 锁定后，只有 major version 才看。

### 4.2 成本估算

| 语言 | 金标 h/首 | 80 首 | 30 首 |
|---|---:|---:|---:|
| 中文 | 2.0 | 160h | 60h |
| 英文 | 2.5 | 200h | 75h |
| 粤语 | 2.0 | —（30 首 60h） | — |
| 日语 | 3.5 | —（40 首 140h） | — |
| 韩语 | 3.0 | —（20 首 60h） | — |

中英各 80 首 ≈ **360h**，加 15% 质检 ≈ **414h**；一个人 6h/天约 **3.5 个月**，
三个人约 **5~6 周**。这是「推荐值」的真实代价。

**精简版（更现实）**：中英各 **30 首金标 + 50 首银标**：
30×2.25 + 50×0.6 ≈ **97.5h/语言**，两语言约 **195h**（一个人约 5 周）。
银标只用于回归，最终对外声称的数字仍用 30 首金标（±10pp 级别，够看大改，不够看 1~2pp 微调）。

### 4.3 外部量级参考

公开歌声语料通常是「百首~千首」量级：OpenCpop 约 100 首、M4Singer 约 700 首、
MIR-1K 约 1000 个片段。这些是**训练/研究语料**，不是对齐评测集；
对齐评测一般从中取 50~150 首做留出。所以「80 首金标/语言」在学术口径里不算少，
真正缺的是**分层**和**留出纪律**，不是绝对数量。

### 4.4 如果走「学习型对齐器」而不是规则/DP

上面的数字是**规则/DP 路线**的评测与调参数据量。如果要做的是训练一个排序器/指针网络/
序列标注模型，量级要另算：

| 路线 | 每语言数据 | 说明 |
|---|---:|---|
| 规则/DP + 超参 | **80 金标** | 本文推荐；TIFA 已给音素边界，规则天花板还没摸到 |
| 轻量学习后处理（GBDT/逻辑回归） | 100~200 金标 | 特征：词头距离、音节数、前一词结束、音符密度等 |
| 深度序列模型（指针/seq2seq） | **500~1000+ 金标** | 需要音级对齐标签；标注成本是本文的 6~10 倍 |

当前建议：**先不训模型**。先把 80 首金标的留出集和误差分层做出来；如果规则/DP 在留出集上
卡在 90% 以下、且错误模式是「特征不够」而不是「规则写错」，再考虑轻量学习。

## 5. 语言矩阵：中/英/粤/日/韩

### 5.1 先纠正一个直觉：标注粒度相似 ≠ 工程相似

用户的分组在**标注语义**上是对的：

| 组 | 语言 | 一个 token 对应 | 词内后续音写 |
|---|---|---|---|
| 多音节词 | 英、日 | 一个词 = N 个音节/モーラ | `+` |
| 一字一音节 | 中、粤、韩 | 一个方块字/谚文块 = 1 音节 | `-`（延长） |

但**工程实现**差别很大：

- **英语**：词有空格，词边界白送；难在音节切分（CMUdict + LSTM G2P）、缩写/复合词；
- **日语**：词没有空格，难在分词、汉字读音（君→kimi 不是 kun）、モーラ切分（きょ=1 拍、
  っ/ー/ん 各 1 拍）；「ありがとう」要先被当成一个词，才谈得上按モーラ写 `+`；
- **粤语**：和中文一样是字级，难在粤拼 OOV、繁体/简体、口语字、入声；
- **韩语**：和中文一样是「一块一音节」，难在 TIFA 没有韩语 G2P、받침/连音，
  以及现在会静默落到中文 G2P。

所以：**数据量按「工程难度」分配，不按「逻辑相似」分配。**

### 5.2 逐语言判断

#### 中文（必做）

- 单元：1 汉字 = 1 音节；多音字（了/着/得/长/行）、儿化、中英夹词是边界情况。
- 现状：TIFA zh pinyin 词典 6.5KB，14 工程 4810 字；插值后 hit 84.6%。
- 主要误差：ASR 同音字、音符比字少（absorbed）、rap/快嘴、切片边界。
- 数据：**200 自动 + 80 金标**；至少 10 首中英混唱、10 首快嘴。
- 不需要新算法分支；需要的是**留出集**和**按歌手切分**。

#### 英文（必做）

- 单元：1 词 = N 音节；`computer` 3 音节 → `computer + +`；词内拖长 → `-`。
- 现状：`_align_latin_words` 的规则从 4 首歌归纳；Poison 上词头 95%、标记 80%。
- 主要误差：音节切分（尤其专有名词/复合词）、rap、melisma、ASR 重复词、TIFA 词时间漂移。
- 数据：**200 自动 + 80 金标**；至少 10 首 rap/快嘴、10 首重转音、5 首音乐剧/现场。
- 这是当前**最需要留出集**的语言：4 首歌调出来的超参，换曲风就可能崩。

#### 粤语（建议补，低成本）

- 单元：1 汉字 = 1 音节，和中文同一条字级路径；`-` 表示延长。
- 现状：TIFA yue jyutping 可用；《富士山下》端到端 99.6%（`docs/TIFA-对齐后端.md`）。
- 主要误差：粤拼 OOV（如「调」的 `eu`）、繁体/简体、口语字、ASR 听错（「拦」→「難」）。
- 数据：**60 自动 + 30 金标**；10 首传统粤语歌、5 首粤语 rap/快歌、5 首中英夹词。
- 工程：**1~2 周**（词典/OOV 兜底、繁简归一、语言判定）；不需要新算法分支。
- 结论：**要补**，ROI 最高；但它是中文分支的「方言回归集」，不是第三套算法。

#### 日语（做才补，独立工程）

- 单元：1 词 = N モーラ；`ありがとう` 是 **5 モーラ**（あ・り・が・と・う），跨 5 个音时写
  `ありがとう + + + +`（4 个 `+`）；`きょう` 是 2 モーラ（きょ + う）→ `きょう +`。
  用户例子里的「ありがとう + + +」只有 3 个 `+`（4 个音），可能是把尾音 う 当成了拖长，
  也可能只是示意；**标注按实际唱出的モーラ数，不按示例的加号个数**。
  促音 っ、长音 ー、拨音 ん 各 1 拍。
- 现状：TIFA ja 配置里有 `japanese-mecab`，但随包的 `japanese_dict_full.txt` 只有 1.5KB
  （一张假名表，不是 MeCab 词典），实际不可用；日语走 Qwen 对齐器（`asr.py:876-884`）。
- 当前代码的日语：Qwen 给逐字时间戳；`_labels_for` 按字切；`_align_latin_words` 把每个
  假名当独立 token；某个 token 后面的音一律 `+`。所以「ありがとう」不是「一个词头 + 4 个
  `+`」，而是 5 个 token 各自找音、各自补 `+`——**不是**用户要的词级写法。
- 要做对，三选一：
  1. **TIFA ja 打通**：随包带 unidic-lite（~50MB）+ import shim，拿到 phones 后推モーラ边界；
  2. **Qwen + 本地分词/读音**：nagisa 分词 + pykakasi 读音 + モーラ切分，把词级 token 与
     モーラ onset 喂给 `_align_latin_words`（它已经支持 `parts`）；
  3. **换 RomajiASR**（Vocal2Midi 路线）：输出罗马音モーラ，一モーラ一音，最干净，
     但要新模型 + ONNX Runtime + 权重（Apache-2.0）。
- 数据：**80 自动 + 40 金标**；汉字多/假名多各 10、快歌 10、演歌/动画/ボカロ各 5。
- 工程：**3~6 周**（分词 + 读音 + モーラ + `+`/`-` 语义 + 回归）。
- 结论：**如果日语是目标市场，值得补；如果只是「顺便支持」，先明确标注不支持**，
  不要用 80 首歌去掩盖 G2P 缺失——数据治不了分词/读音。

#### 韩语（暂缓）

- 单元：1 谚文块 = 1 音节；`사랑` 2 块 → `사 랑`，延长写 `-`。
- 现状：TIFA 1.0 没有韩语 G2P；`tifa_language("Korean")` 返回 `"zh"`，
  韩文会被中文 G2P 处理，结果不可用；UI 却提供「韩语」选项。
- 要做对：g2pk 之类的韩语 G2P + TIFA 音素映射，或 Qwen 字级 + 零长度插值；
  前者更稳，但要新依赖；后者只能算「结构正确、时间戳待验证」。
- 数据：**50 自动 + 20 金标**（只有在修好通路后才值得收）。
- 工程：**2~4 周**（G2P + 音素表 + 回归）。
- 结论：**暂缓**。优先级低于日语：日语至少有 Qwen 兜底 + 明确的 `+`/`-` 语义，
  韩语现在是「静默用错 G2P」，先修 bug 再谈数据。

### 5.3 优先级与决策树

```
日语/韩语是产品目标吗？
├─ 否 → 只做中英 + 粤语回归；日/韩在 UI 上明确“实验/不支持”，不计入泛化声明
└─ 是 → 先修 G2P/分词（日 3~6 周，韩 2~4 周），再各收 40/20 首金标
```

| 优先级 | 语言 | 理由 |
|---|---|---|
| P0 | 中文、英文 | 主场景；现有规则最需要留出集验证 |
| P1 | 粤语 | 与中文同分支，30 首就能覆盖，ROI 最高 |
| P2 | 日语 | 独立工程；有明确用户需求再做 |
| P3 | 韩语 | 通路未修，先别收数据 |

## 6. 人工精修到底修什么

### 6.1 三层标注

| 层级 | 内容 | 时间/首 | 用途 |
|---|---|---|---|
| **金标** | 音符边界 + 词头 + `+`/`-` + 行切分 + 文本 | 2~3h | 指标、调参、验收 |
| **银标** | 自动音符 + 人工挂字 + 抽查边界 | 30~45min | 回归、扩充 test |
| **铜标** | 自动产物 + 人工判「可用/不可用」 | 5~10min | 冒烟、失败挖掘 |

### 6.2 规则示例（写进标注手册）

| 语言 | 原文 | 音数 | 写法 |
|---|---|---:|---|
| 中文 | 爱情 | 2 | `爱` `情` |
| 中文 | 爱（拖 3 个音） | 3 | `爱` `-` `-` |
| 英文 | computer | 3 | `computer` `+` `+` |
| 英文 | lighting（拖 2 个音） | 3 | `lighting` `-` `+`（按实际音节边界） |
| 日语 | ありがとう | 5 | `ありがとう` `+` `+` `+` `+` |
| 日语 | きょう | 2 | `きょう` `+` |
| 粤语 | 富士山下 | 4 | `富` `士` `山` `下` |
| 韩语 | 사랑 | 2 | `사` `랑` |

边界情况必须写清楚：

- 促音 っ / 长音 ー / 拨音 ん：各算 1 モーラ；
- 中文儿化「花儿」：按唱出来的音节数，不按字数；
- 英文缩写 `don't` / `we're`：按实际音节，不按字母；
- ASR 重复词（`I know I know`）：人工判断是否真唱了两遍，重复的进 `absorbed`；
- 伴唱/和声：只标主旋律，伴唱单独记 `backing`，不混进主轨；
- 一个字被唱成多个音但听不出新音节：`-`，不是 `+`。

### 6.3 质控

- **双标 10~15%**：至少两人独立标，算 Cohen's kappa；
  目标：词头 > 0.9、`+`/`-` > 0.8；
- **黄金集校准**：每月用 5 首已定稿的歌重标，防止标准漂移；
- **争议仲裁**：第三人听原曲 + 看波形，记录到 `adjudication.md`；
- **标注工具**：直接用 Synthesizer V Studio 改 SVP，导出后用脚本对比；
  不建议自研编辑器（成本高于收益）。

## 7. 评测口径与验收线

### 7.1 两套指标

| 指标 | 输入 | 回答的问题 |
|---|---|---|
| **对齐-only** | 人工音符 + 自动字时间 + 自动挂字 | 对齐器本身好不好 |
| **端到端** | 自动音符 + 自动字时间 + 自动挂字 | 用户拿到的 SVP 好不好 |

对齐-only 是算法迭代的主指标；端到端是产品指标。两个都要报，且要分开报。

### 7.2 具体指标

1. **Token hit**：字/词头挂到的音 == 人工音（exact；另报 ±1 音容差）；
2. **Marker accuracy**：`+`/`-` 逐音一致率；
3. **Hidden/absorbed**：没显示出来/被挤掉的比例；
4. **Boundary error**：匹配上的词头，|自动 onset − 人工 onset| 的 p50/p90，及 >1s 比例；
5. **Line exact**：一行里所有 token 命中且标记全对的比例；
6. **Mora/syllable count accuracy**（日/英）：预测音节数 == 人工；
7. **Note F1**（单独报）：SheetSage2 音符的准确率，不与对齐混淆；
8. **ASR CER/WER**（单独报）：文本错误，不与对齐混淆。

### 7.3 验收线（建议）

| 语言 | Token hit | Hidden | \|Δ\|>1s | Line exact |
|---|---:|---:|---:|---:|
| 中文 | ≥95% | ≤3% | ≤1% | ≥85% |
| 英文 | ≥95%（词头） | ≤3% | ≤1% | ≥80% |
| 粤语 | ≥92% | ≤5% | ≤2% | ≥75% |
| 日语 | ≥90%（モーラ） | ≤5% | ≤2% | ≥75% |
| 韩语 | ≥90%（音节） | ≤5% | ≤2% | ≥75% |

附加纪律：

- **worst-slice ≥ 总体 − 10pp**（不能只报平均）；
- **dev 与 test 差距 ≤ 3pp**（否则就是过拟合）；
- **跨歌手/跨曲风**至少各留 10 首，单独报；
- 所有数字带 cluster bootstrap 95% 区间。

## 9. 风险与反例

1. **小样本过拟合**：英文 DP 的 6~8 个超参是从 4 首歌调出来的；没有 50 首留出，
   任何「提升」都可能是记住了这 4 首。
2. **数据泄漏**：同一歌手/同一翻唱跨 dev/test，指标会虚高；必须按歌手切。
3. **标注漂移**：三个月后同一首歌标法变了；用黄金集 + 双标控制。
4. **口径混淆**：自动音符 vs 人工音符、对齐-only vs 端到端、ASR 文本 vs 挂字；
   不分开报就会得出「换对齐器没用」或「换对齐器万能」的错误结论。
5. **日语伪支持**：UI 有日语不等于能用；当前是 Qwen 逐字 + 每假名 `+`，
   与用户要的词级 `+ + +` 不是一回事。
6. **韩语静默错 G2P**：`tifa_language("Korean") → "zh"` 是当前代码事实；
   不修就收数据，等于给 bug 做标注。
7. **版权**：人工 SVP 是衍生作品；内部评测可以，对外分发要确认音频/歌词授权。
8. **「多收歌」不解决工程问题**：日语分词、韩语 G2P、粤语 OOV 都是代码/词典问题；
   数据只能验证，不能替代。

## 11. 交付物与存储：SVP 对够不够？音频几个 G

### 11.1 三种交付层级

| 层级 | 每首给什么 | 能做什么 | 不能做什么 |
|---|---|---|---|
| **A. 结果对** | `auto.svp` + `manual.svp` | 产物级对比：音符/歌词/`+`/`-` 差异；回归 | 重跑对齐器/ASR；分离误差层；验证标注 |
| **B. 可迭代** | A + `project.json` + `lyrics.json` | 固定音符与字时间，离线调 `assign_lyrics`/DP；对齐-only 指标；看 `parts` | 改 TIFA/Qwen/ASR；换新歌；端到端重跑 |
| **C. 可复现** | B + 音频 | 全链路重跑、换模型、重新识别、人工试听 | 只有版权/存储成本 |

**直接回答**：只做「自动 SVP vs 人工 SVP」的对比，**A 就够**，400~900 首不到 1 GB；
但要「优化挂字算法」，至少 **B**——**B 不需要全量音频**，只要
`project.json` + `lyrics.json` + 人工 SVP，音频留 20~30 首/语言做试听与争议仲裁即可。
要动 TIFA/Qwen/ASR 或换新歌，才必须 **C**（全量音频）。
SVP 是结果，`lyrics.json` 才有逐字时间/`parts`，`project.json` 才有
`raw_tick/raw_dur`；这三个缺一个，就只能看现象，不能换算法重跑。

### 11.2 存储估算

假设：3.5~4 分钟/首；FLAC 16/44.1 立体声约 25 MB；WAV 16/44.1 约 40 MB；
MP3 320 约 9 MB；Opus 96 约 3 MB；SVP + JSON 约 0.5 MB/首。
数量：**400** = 中英各 200（人工是自动的子集）；**590** = 加粤 60 + 日 80 + 韩 50；
**900** = 强泛化（中英各 300 + 粤 100 + 日 120 + 韩 80）。

| 内容 | 每首 | 400 首 | 590 首 | 900 首 |
|---|---:|---:|---:|---:|
| 仅 SVP×2 + JSON | ~0.5 MB | ~0.2 GB | ~0.3 GB | ~0.45 GB |
| + FLAC 单轨 | ~25.5 MB | ~10 GB | ~15 GB | ~23 GB |
| + FLAC 双轨（混音+干声） | ~50.5 MB | ~20 GB | ~30 GB | ~46 GB |
| + MP3 320 单轨 | ~9.5 MB | ~4 GB | ~6 GB | ~9 GB |
| + Opus 96 单轨 | ~3.5 MB | ~1.4 GB | ~2.1 GB | ~3.2 GB |

结论：

- **只交 SVP 对**：**0.2~0.5 GB**，几乎不占地方；
- **只做挂字（B 层）**：SVP+JSON 约 **0.2~0.3 GB** + QA 音频 20~30 首/语言约 **1.5~2 GB**；
- **中英核心 + FLAC 单轨**：**10~12 GB**；
- **加粤日韩 + FLAC 单轨**：**15~18 GB**；
- **混音 + 干声双轨**：**30~36 GB**（粤日韩齐）或 **20~24 GB**（中英）；
- **压缩格式**：MP3 320 约 4~6 GB，Opus 96 约 1.4~2.1 GB；
  但 lossy 可能改变 ASR/TIFA 结果，**金标别用 lossy**。

### 11.3 推荐：按目标分层

**只做挂字层（B 层）**：

| 项 | 建议 |
|---|---|
| 金标 80/语言 | `project.json` + `lyrics.json` + `manual.svp`；**不强制音频** |
| QA 音频 | 20~30 首/语言 FLAC，用于试听、争议仲裁、标定 `+`/`-` |
| 自动池 200/语言 | 只留 `project.json` + `lyrics.json` + `auto.svp`，不存音频 |
| 存储 | 中英约 **1.5~2.5 GB**；加粤日韩约 **2.5~3.5 GB** |

**要复现/换模型（C 层）**：

| 层 | 音频 | 理由 |
|---|---|---|
| 金标 80/语言 | **FLAC 16/44.1 单轨**（有干声就加干声） | 要复现、要试听、要重跑 |
| 自动池 200/语言 | **Opus 96 或 MP3 320**，或只存元数据 | 只做失败挖掘，不追求逐位复现 |
| stress set | FLAC | 要反复听难例 |

按 C 层分层，中英核心约 **5~6 GB**（160 首金标 FLAC + 400 首自动 Opus），
加粤日韩约 **8~9 GB**；比全量 FLAC 省一半，且不影响结论。
**只做挂字的话，按 B 层存，别为 80 首全配 FLAC——除非你还要用它们重跑 ASR。**

### 11.4 最小交付清单（每首）

```
<id>/
  meta.json          # 语言、曲风、BPM、拍号、难度、split、来源/授权
  auto/
    project.json     # 自动音符（含 raw_tick/raw_dur）
    lyrics.json      # 逐字时间 + parts + 语言/对齐器
    export.svp       # 自动产物
  manual/
    manual.svp       # 人工精修（音符 + 挂字 + +/-）
    notes.json       # 可选：归一化后的音符/歌词，便于 diff
  audio.flac         # C 层才需要；A/B 层可省略
```

如果人工不是自动的子集（即 80 首人工是额外收的），每语言再加 80 首的音频；
按 FLAC 单轨算，中英多 **4 GB**，粤日韩多 **2.3 GB**。

> **`meta.json` 现在会自动生成并刷新**：扒谱完成时由 `pipeline` 先落一份最小版，
> 歌词识别完成时由 runner 刷新成完整版（`sheetsage2_webui.meta.write_meta`）；
> WebUI 后台会轮询数据根和 `samples/对齐`（若存在；`--meta-watch-dir` 可再加别的目录），
> 手动加/改 `auto.svp` / `manual.svp` 后自动刷新，**不需要再跑命令**。
> 打开工程时也会顺手刷新一次。已有 `meta.json` 会保留手填的
> `split` / `genre` / `difficulty` / `tags` / `notes`。
> `tmp/make_meta.py` 只用于**历史样本批量补/刷新**，不随离线包发布。
> 目录也不必强制 `auto/`、`manual/` 子目录——像这个样本一样平铺
> （`auto.svp` / `manual.svp` / `project.json` / `lyrics.json` / `meta.json`）同样能跑。

## 附：一句话回答用户

> **中、英各 200 首自动 + 80 首人工精修**（最低 120 + 50；强泛化 300 + 150）。
> **粤语要补，30 首人工 + 60 首自动就够**；**日语要补但先补分词/读音/モーラ工程，40 首人工**；
> **韩语暂缓，先修 G2P**。日语和英语只是「标注语义」相似，工程上日语更难；
> 粤/韩和中文是「一块一音节」相似，但粤语缺词典覆盖、韩语缺 G2P，不能只靠加歌。
